# Forge Debugging Tooling — Proposal

**Author's framing.** Tonight's debugging cost hours not because any single bug was
hard, but because *the tools stop at the tier boundary*. Forge's debug surface today
is excellent **within one process or one cluster** — `forge debug` (Delve),
`forge introspect handlers`, `forge api curl`, `forge doctor`, `forge cluster
status/logs`. But a Reliant user action crosses **browser → api-server (host go-run)
→ NATS → daemon-gateway (k3d `control-plane-dev`) → daemon pod (k3d `cp-daemon`)**,
and *nothing* follows a request, a version, or a connection across those hops. We
manually stitched 4 log sources, hand-diffed image digests, and ran cross-context
`kubectl` by memory.

Notably, the existing `forge/debug/multi-cluster-e2e` skill **already documents this
exact pain in prose** — "read pod status across BOTH clusters *directly with kubectl*
because `forge cluster status` resolves a single cluster," the gateway `write
envelope: EOF` loop, "no `<peer>` connected." That skill is a hand-written workaround
for missing tooling. These proposals turn that prose into commands.

---

## The keystone: a declarative **topology** model

Four of the seven proposals below need the same missing thing: a machine-readable
description of the app's *tiers* — for each tier, **where it runs** (host process vs.
`kube context + namespace + selector`), **how to read its logs**, **what image/build
it's running**, and **who it talks to**. forge.yaml already knows services, envs, and
`K8sCluster` contexts (`deploy/kcl/<env>`); today that knowledge is scattered and
single-cluster-biased.

Proposal 0 (implicit, do first): add a `topology:` block to forge.yaml (or derive it
from the KCL `deploy` blocks the multi-cluster-e2e skill already reads). One example:

```yaml
topology:
  tiers:
    - name: api-server
      runtime: host          # go-run on the host
      log: { source: file, path: api.log }
      image_label: false
    - name: daemon-gateway
      runtime: k8s
      cluster: k3d-control-plane-dev    # kube context
      namespace: control-plane
      selector: app=daemon-gateway
    - name: daemon
      runtime: k8s
      cluster: k3d-cp-daemon
      namespace: daemons
      selector: app=daemon
  bus: { kind: nats, url_from: compose }   # or forge.yaml services[]
```

This one block is the enabling abstraction for `trace`, `versions`, `daemon status`,
and `cluster daemons`. Build it once; four commands read it. **Every proposal below
assumes it and degrades gracefully without it** (falling back to today's
single-cluster / single-log behavior).

## P0-1 — `forge trace <request-id>`

**Pain (scenario #1).** A single "open terminal / GetFileTree" crosses browser →
api-server → NATS → daemon-gateway → daemon. There is no single view. Tonight we
`grep`'d `api.log`, `reliant.log`, `kubectl logs` on the gateway pod, and `kubectl
logs` on the daemon pod (different context) — by hand, correlating on timestamps.

**Why it's tractable now.** The pieces already exist: forge emits structured JSON
logs with `request_id` / `trace_id` / `traceparent` keys (confirmed in the
`observability` skill and via grep — `requestID`, `request_id`, `traceparent` are all
in the tree), and every tier's log location is exactly what the topology block
describes. This is **log-stitching by `request_id`**, not distributed tracing — more
robust than Tempo here because `traceparent` propagation across the NATS hop is
itself unproven (that's part of what made tonight hard).

**CLI shape**

```bash
forge trace 7f3a9c            # stitch every tier's logs for this request id
forge trace 7f3a9c --since 10m --json
forge trace 7f3a9c --tier daemon-gateway   # one tier only
forge trace --follow 7f3a9c  # live, as the request is in flight
```

**Example output**

```
request 7f3a9c  (GetFileTree)                    span 214ms   ✗ FAILED

  ts            tier             event
  12:04:31.010  browser          POST /terminal.v1.TerminalService/GetFileTree
  12:04:31.012  api-server       rpc recv  request_id=7f3a9c user=alice
  12:04:31.014  api-server       nats publish  subj=daemon.terminal.subscribe  traceparent=00-…-01
  12:04:31.019  daemon-gateway   nats recv  subj=daemon.terminal.subscribe  → route daemon=cp-7
  12:04:31.021  daemon-gateway   write envelope: EOF   ← reconnect loop  ⚠
  12:04:36.021  api-server       rpc error  code=unavailable "no daemon connected"

  gaps: daemon tier produced NO log lines for 7f3a9c
        → request never reached the daemon pod (stops at gateway). See `forge daemon status`.
```

The **gap detection** ("daemon produced no lines → request died at the gateway") is
the highest-value part: it points at the broken hop directly, which is exactly the
inference we made by hand tonight.

**Implementation in forge's model.** New dir-nested cobra group
`internal/cli/trace/` (self-registered via `factory.Register`, blank-imported in
`groups.go`), mirroring `internal/cli/debug/`. Pure `runTrace(w io.Writer, id string,
opts)` function under the command (the `introspect.go` / `api.go` testability
pattern). For each topology tier: `runtime: host` → grep the file; `runtime: k8s` →
`kubectl --context <cluster> -n <ns> logs -l <selector> --since=<x>` and filter by
`request_id`. Merge by timestamp, render a timeline. Reuses the JSON-log attribute
keys the `observability` skill already standardizes (`request_id`, `trace_id`,
`procedure`). Ship a companion `forge/debug/trace` skill telling the agent **how to
get a request id** (browser devtools `x-request-id` response header / the failing RPC).

**Priority: P0.** Rationale: the highest-leverage single tool — collapses the
4-source manual grep that dominated tonight into one command, and its gap-detection
localizes the broken hop for free.

## P0-2 — `forge versions` / `forge doctor --skew`

**Pain (scenario #2 — the biggest time sink).** Figuring out *which tier runs stale
code*. Host go-run rebuilds on restart; k3d images are digest-pinned; the
workspace-base DAEMON image used a **reused tag** and went 5 days stale silently. We
had no way to see "here is the build/digest each tier is actually running vs.
HEAD/working-tree."

**Why it's tractable now.** forge already owns both halves of the equation:
- It computes the canonical image tag (`git describe --tags --always --dirty`,
  `internal/cli/image_tag.go`) and records `BuildState{Image, Tag, Registry, Commit,
  GitTag, Dirty, PushedAt}` (`internal/cli/build_state.go`).
- It has `buildinfo` (git commit / version) for the running binary.

The missing link is **reading what's actually deployed and comparing**. The reused-tag
bug is precisely the case a *tag* comparison misses and a *digest* comparison catches.

**Two-part fix:**

1. **Runtime hook — stamp provenance into every forge-built image.** forge controls
   the image build, so at `forge build` bake `org.opencontainers.image.revision`
   (git SHA) + build time as OCI labels (and/or a `/version` env). This makes any
   running image self-identifying — you can map a digest back to a commit.
2. **`forge versions` — the drift table.** For each tier: read the running
   image ref **and digest** (`kubectl get pod -o jsonpath='{…imageID}'` for k8s tiers;
   `buildinfo` for the host binary), read the baked revision label, and compare
   against working-tree HEAD and the local `BuildState`.

**CLI shape**

```bash
forge versions                    # table, all tiers
forge versions --env dev --json
forge doctor --skew               # gated check: non-zero if any tier drifts
```

**Example output**

```
tier             running                              built-from   vs HEAD        state
api-server       go-run (host)                        a1b2c3d      == HEAD        ✓ fresh
daemon-gateway   …/gateway:v0.4.1  @sha256:9f2…       a1b2c3d      == HEAD        ✓ fresh
daemon           …/daemon:workspace-base @sha256:4c8… e7d9f10      12 commits ⤵   ✗ STALE (built 5d ago)
                 └ tag 'workspace-base' was reused; digest predates HEAD by 5 days

HEAD a1b2c3d (working tree clean)
✗ 1 tier stale — rebuild: forge build --service daemon --push && forge deploy dev
```

**Implementation in forge's model.** Extend the `internal/cli/image_tag.go` +
`build_state.go` machinery with a "resolve running image" reader per tier (topology
gives the context/selector). New `forge versions` cobra command; the `--skew`
variant is a `doctor` check registered like the existing `runPkgPinDoctorChecks` /
`runExternalBuildDoctorChecks` (`internal/cli/doctor.go` already composes checks this
way and returns `errDoctorFailed` non-zero). The OCI-label stamping is a small
addition to the docker build step. `forge doctor --skew` in CI catches stale tags
before they ship.

**Priority: P0.** Rationale: directly kills the single biggest time sink; forge
already has the build-side truth, so this is mostly wiring the "what's running" read
and a digest (not tag) comparison.

## P0-3 — `forge daemon status` (a generic component-status probe)

**Pain (scenario #3).** Answering "is a daemon connected, to which gateway, and is
its lease/heartbeat alive?" required cross-cluster `kubectl` + DB queries + log
greps. Reliant *already has the state* — `internal/daemonliveness`,
`internal/daemonstate`, `internal/daemonquery`, `internal/daemonactivity` — it's just
not reachable from one command.

**Design tension (worth stating).** "daemon" is a Reliant concept, not a forge
primitive — so `forge daemon` hard-coded into forge would be a layering violation.
The forge-correct design is a **generic operational-status probe**: a project declares
a status RPC per component in forge.yaml; `forge status <component>` calls it and
pretty-prints. The daemon becomes the *first consumer*, not a special case. This is
the same instinct as `forge api curl` (descriptor-driven, app-agnostic), extended
from "here's a curl" to "call it and render."

```yaml
# forge.yaml
components:
  - name: daemon
    status_rpc: daemon.v1.DaemonAdminService.Status   # returns connected daemons + lease/heartbeat
```

**CLI shape**

```bash
forge status daemon               # generic: calls the declared status_rpc, renders it
forge status daemon --watch       # re-poll
# convenience alias when the component is named 'daemon':
forge daemon status
forge daemon logs cp-7            # → forge cluster logs, resolved to the daemon's pod+context
```

**Example output**

```
DaemonAdminService.Status  (via daemon-gateway, k3d-control-plane-dev)

  daemon   gateway        lease          heartbeat        state
  cp-7     gw-2 (dev)     valid 41s left  8s ago           ✓ connected
  cp-9     —              expired 2m ago  —                ✗ orphaned (no gateway)

  1 connected, 1 orphaned.  Orphaned daemon cp-9: pod Running but gateway dropped it
  → cross-check: forge trace <req>  |  forge cluster logs --context k3d-cp-daemon -l app=daemon
```

**Implementation in forge's model.** `forge status` is a thin caller built on the
*same* descriptor + port resolution `forge api curl` already does
(`internal/cli/api.go`: `resolveServiceMethod`, `lookupServicePort`) — but instead of
printing curl, it executes a Connect unary call and renders the response. The
`daemon` subcommand is a project-local convenience alias. The heavy lifting (the
actual connectivity truth) stays in Reliant's existing `daemon*` packages behind one
admin RPC; forge just needs a declared endpoint to hit. **Fast path if P0 speed
matters:** ship the Reliant-side `DaemonAdminService.Status` RPC first and reach it
today via `forge api curl` + a skill; promote to `forge status` once the generic
mechanism lands.

**Priority: P0.** Rationale: the connectivity question recurred all night; the state
already exists in-app, so the cost is one admin RPC + a generic caller — and the
generic `forge status` pays off for every future component.

## P1-4 — `forge cluster daemons` / `forge cluster status --all-contexts`

**Pain (scenario #4).** Daemon pods live in k3d `cp-daemon`; the controller lives in
`control-plane` and doesn't even watch the remote pods. `forge cluster status`
resolves **one** cluster from config, so just *seeing* remote pod state meant knowing
the right context by hand. The multi-cluster-e2e skill explicitly tells you to run
`kubectl --context <secondary>` yourself — that's the tell.

**CLI shape**

```bash
forge cluster status --all-contexts     # pods across EVERY topology cluster
forge cluster daemons                    # focused: just the daemon-tier pods, all contexts
forge cluster pods --context k3d-cp-daemon -n daemons
```

**Example output**

```
context                     namespace       pod              status     image (digest)          age
k3d-control-plane-dev       control-plane   daemon-gateway   Running    gateway @sha256:9f2…    3h
k3d-cp-daemon               daemons         daemon-cp-7      Running    daemon  @sha256:4c8…    5d ⚠ stale
k3d-cp-daemon               daemons         daemon-cp-9      Running    daemon  @sha256:4c8…    5d

⚠ daemon image digest differs from HEAD build — see `forge versions`.
```

**Implementation in forge's model.** Pure extension of the existing `cluster`
command tree (`internal/cli/dev.go` assembles it; `dev_status.go` /
`dev_logs.go` do the kubectl work). Today those resolve a single context; add an
`--all-contexts` path that ranges the topology's `cluster` values (the KCL `deploy`
blocks the multi-cluster-e2e skill already reads: "the `cluster` field IS the
context"). No new engine — just iterate contexts and tag each row. Cross-links to
`forge versions` (digest column) for free.

**Priority: P1.** Rationale: small, self-contained extension of an existing command,
removes a real "know the magic context" tax on every multi-cluster session.

## P1-5 — `forge nats tap <subject-pattern>`

**Pain (scenario #5).** "Did `terminal.subscribe` actually reach the daemon?" was
unanswerable without instrumenting code. The subjects are real and namespaced
(`daemon.terminal.subscribe`, `daemon.terminal.output`, `tools.request`,
`terminal.create`, … — all present in the tree), so a live tap is directly useful.

**CLI shape**

```bash
forge nats tap 'daemon.terminal.>'       # live, wildcard
forge nats tap 'tools.request' --headers # show traceparent / request_id headers
forge nats tap '>' --request-id 7f3a9c   # only frames carrying this request id
```

**Example output**

```
subject                        bytes  request_id  traceparent            preview
daemon.terminal.subscribe        128   7f3a9c      00-4bf9…-01            {"terminal_id":"t-3","cols":80}
daemon.terminal.output           64    7f3a9c      00-4bf9…-01            {"data":"$ "}
tools.request                    212   9c1e0a      00-77aa…-01            {"tool":"read_file","path":"/x"}

18 msgs / 5s   subjects: daemon.terminal.* (12)  tools.* (6)
```

**Implementation in forge's model.** New `internal/cli/nats/` cobra group. forge can
discover the NATS URL generically — either from a declared broker/adapter in
forge.yaml or the compose file (the `observability`/`doctor` code already introspects
compose for ports). Subscribe with the NATS Go client, print subject + size +
selected headers + a JSON preview. Surfacing the `traceparent` / `request_id` headers
**ties this back to `forge trace`** (P0-1) — tap shows the id, trace stitches it. NATS
is generic infra, so this is a legitimate forge primitive, not a Reliant special-case.

**Priority: P1.** Rationale: turns an "instrument the code and redeploy" loop into a
live watch; medium lift (one NATS client), broadly reusable for any bus-backed forge
app.

## P2-6 — `forge api stream <service.method>`

**Pain (scenario #6).** `forge api curl` handles unary and even *prints* a note for
streaming RPCs, but streaming terminal RPCs are opaque — curl only gets the first
frame (the code comment in `api.go` says exactly this).

**CLI shape**

```bash
forge api stream terminal.v1.TerminalService.Subscribe --body '{"terminal_id":"t-3"}'
forge api stream TerminalService.Watch --port 9090 --max 20
```

**Example output**

```
→ connecting  http://localhost:8080/terminal.v1.TerminalService/Subscribe  (server-stream)
← frame 1  12:04:31.021  {"data":"$ "}
← frame 2  12:04:31.402  {"data":"ls\r\n"}
← frame 3  12:04:31.410  {"data":"README.md  go.mod\r\n"}
… stream open, 3 frames in 0.4s (Ctrl-C to stop)
```

**Implementation in forge's model.** New `stream` verb on the existing `api` command
group (`newAPICmd` in `internal/cli/api.go` already anticipates more verbs:
"future verbs … hang off the same parent"). Reuse the descriptor-driven
`resolveServiceMethod` + `lookupServicePort` already there; instead of rendering a
curl string, open a real connect-go streaming client and print frames with
timestamps. Detects client/server/bidi from the same `Method.ServerStreaming` /
`ClientStreaming` fields `api.go` reads today.

**Priority: P2.** Rationale: closes a known, explicitly-acknowledged gap in `api
curl`; valuable but narrower than the cross-tier tools, and needs a live server.

## P2-7 — `forge/debug/terminal-flow` skill

**Pain (scenario #7).** Terminal/PTY + subscribe-driven output across the WS/NATS
bridge was a black box. This is less a *new engine* than a *playbook* that chains the
tools above for the specific terminal-bridge failure mode.

**Content sketch** (SKILL.md, `emit: both`, `@forge-only` block like the existing
debug skills):
1. Get the request id (browser `x-request-id` on the failing terminal RPC).
2. `forge trace <id>` — find which hop the terminal frames stop at.
3. If frames stop before the daemon: `forge nats tap 'daemon.terminal.>'
   --request-id <id>` — is the subscribe even published? received?
4. `forge daemon status` — is the target daemon connected / lease alive?
5. `forge api stream …TerminalService.Subscribe` — reproduce the stream by hand.
6. Cross-reference `forge versions` — is the daemon running stale PTY code?

**Implementation in forge's model.** A markdown `SKILL.md` under
`internal/templates/project/skills/forge/debug/terminal-flow/`, emitted like the
other debug skills. Zero code — it composes 1/3/5 into an ordered recipe, the same
way `multi-cluster-e2e` composes today's tools.

**Priority: P2.** Rationale: cheap (docs only) and directly addresses the terminal
black box, but it's *dependent* on P0-1/P1-5/P2-6 existing — write it as they land.

## Sequencing recommendation

1. **Topology block** (keystone) + **P0-2 `forge versions`** — versions needs the
   least new machinery (forge already owns build truth) and kills the biggest time
   sink first.
2. **P0-1 `forge trace`** — highest ongoing leverage; needs the topology block.
3. **P0-3 `forge daemon/status`** — pair with the Reliant-side admin RPC.
4. **P1-4 cluster daemons** + **P1-5 nats tap** — independent, parallelizable.
5. **P2-6 api stream** + **P2-7 terminal-flow skill** — finish the terminal story.

Everything above fits forge's existing extension seams: dir-nested cobra groups
(`internal/cli/<group>/` + `factory.Register` + `groups.go`), doctor-check composition
(`internal/cli/doctor.go`), descriptor-driven RPC resolution (`internal/cli/api.go`),
the build/version machinery (`image_tag.go` + `build_state.go` + `buildinfo`), and
emitted `SKILL.md` templates. No new subsystem is required — only a topology model and
commands that read across tiers instead of stopping at the first one.
