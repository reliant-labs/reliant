# Examples

Small, real apps that deploy with Reliant Forge. Each directory is a separate
project with its own README: what it shows, how to run it locally, the deploy
command, and how to check that the deploy works.

| Example                                         | Stack                          | What it shows                                                                                                 |
| ----------------------------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| [`vite-spa`](vite-spa/)                         | Vite, no backend               | a static site with client-side routes, adopted with `--kind site`                                             |
| [`fastapi-postgres`](fastapi-postgres/)         | Python, FastAPI, Postgres      | an existing Dockerfile + compose app, adopted with `--kind app`: managed Postgres and a migration job         |
| [`express-postgres`](express-postgres/)         | Node, Express, Postgres        | the same, with no compose file: Postgres found from the `pg` dependency, migrations from the `migrate` script |
| [`llm-app`](llm-app/)                           | Node, OpenAI SDK               | calling an LLM through `forge.LLM` and `forge.llm_env()`, with no provider key in the app                     |
| [`go-forge-crud`](go-forge-crud/)               | Go, Connect RPC, Postgres      | forge's own stack: one entity, its CRUD API generated by `forge scaffold`                                     |
| [`nextjs-static-go-api`](nextjs-static-go-api/) | Go API + Next.js static export | a full-stack forge app: the API, its table, and a frontend over generated hooks                               |

Not here yet: **Rails**, Django and Spring. They adopt the same way as
`fastapi-postgres` (`reliant forge project new --in-place --kind app`), but an
example is added only once it has been built and deployed for real.

## Two kinds of example

- **Committed and deployable.** `vite-spa`, `fastapi-postgres`,
  `express-postgres` and `llm-app` hold the whole app plus the `forge.yaml` and
  `deploy/kcl/` that `reliant forge project new --in-place` wrote for it. From a
  checkout of the directory, one command deploys it.
- **Reproduced by a script.** `go-forge-crud` and `nextjs-static-go-api` are
  forge-generated Go projects (about 170 and 440 files, 2-4.5 MB, most of it generated). Rather
  than commit that tree into forge's repository, each holds a `scaffold.sh`
  that runs the real `forge project new` and `forge scaffold` and writes the
  one hand-written input (the entity). Run it, then deploy the directory it made.

## Deploy one, with no account

From the example's directory (for the scripted two, from the directory
`scaffold.sh` made):

```bash
npx -y @reliantlabs/forge@latest env deploy prod --claimable --plan-only   # check it fits; creates nothing
npx -y @reliantlabs/forge@latest env deploy prod --claimable               # deploy it
```

`--claimable` publishes with no account and prints a live URL and a claim link.
The claim link is one-time: whoever opens it first owns the deploy, so it is for
you alone, never for commits, issues or public places.

|                          | Unclaimed (`--claimable`, no account)                                   | Claimed, or deployed signed in                                               |
| ------------------------ | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| lifetime                 | offline after 72 hours, deleted 7 days later                            | yours until you delete it                                                    |
| shape                    | one static site, or one service with its migration job and one Postgres | what your plan allows                                                        |
| size                     | 125m CPU / 128 MiB per workload; Postgres 256 MiB of data               | billed sizes                                                                 |
| outbound internet        | none: DNS and its own Postgres only (no LLM, payment or webhook calls)  | normal                                                                       |
| secrets                  | none can be set                                                         | `reliant forge secret set`                                                   |
| logs, traces, dashboards | none until claimed                                                      | https://forge.reliantlabs.io (signed in)                                     |
| cost                     | free                                                                    | static sites free in one org per person; a backend or database needs billing |

Signed in already (`reliant forge login`, or inside Reliant)? `--claimable` is
refused; deploy to your own organization with
`reliant forge env deploy prod --yes` instead.

## The badge

Every example README carries the
[Deploy with Reliant Forge](../docs/deploy-badge.md) badge. Paste it into your
own repository's README the same way.

## Regression checks (no deploy)

From the forge repository root:

```bash
node --test examples/deployment.test.cjs examples/nextjs-static-go-api/scaffold.test.cjs
```

The deployment tests evaluate the actual prod/staging KCL with each example's
pinned `reliant forge`: hosted database references, migration ordering and Vite
static hosting. They need Node and `reliant`, but no database or credentials.
The scaffold test runs the real notes script against fixture scaffold/build
tools and checks that every CRUD RPC is public **before** regeneration; it does
not build or start the generated app.

## Adding an example

- One directory per example, with a `README.md` in the shape of the others and
  the badge.
- It must have been run locally and deployed (`--claimable`, or to an
  organization) before it lands. Say in its README what was not verified.
- Keep it small. No `node_modules`, build output or `.forge/` state (each
  example's `.gitignore` excludes them). A lockfile is committed only where the
  Dockerfile needs it (`npm ci`).
- No Go module (`go.mod`) inside `examples/`: a nested module is outside
  `go build ./...` but is still walked by forge's repository guards and
  linters. Forge-generated Go projects are reproduced by a `scaffold.sh`.
- Pin `forge_version` in `forge.yaml` to a published release, so
  `npx -y @reliantlabs/forge@latest` can run it on any machine.
- Format with `task fmt:web`.
