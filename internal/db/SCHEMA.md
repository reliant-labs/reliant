# Database Schema Management

## Overview

Reliant runs exclusively on **Postgres**. The schema is **forge migrations**:
forward-only SQL files under `db/migrations/` (repo root), embedded into the
binary by `forge generate` (`db/embed_gen.go`) and applied by forge's migrator
(`forge/pkg/migratekit`, golang-migrate underneath). `sqlc` reads the same
files to generate type-safe Go code, until the forge ORM replaces it (P5b in
`research/forge-migration/PLAN.md`).

## Files

- **`db/migrations/`** - Forge migrations, `<YYYYMMDDHHMMSS>_<name>.up.sql` (source of truth for the schema). The first is the baseline that replaced goose's history.
- **`postgres/queries/`** - Hand-written SQL queries compiled by `sqlc`
- **`sqlc.yaml`** (repo root) - Points `sqlc` at `db/migrations/` and `postgres/queries/`
- **`migrate.go`** - `Migrate` (apply), `WaitForSchema` (wait for the api-server to apply), and the read-only state behind `reliant db migrate status`
- **`internal/store/`** - The forge ORM's projection of the applied schema (`forge.yaml` `database.orm.package`): `<entity>_orm_gen.go` and `store_gen.go` are regenerated by every `forge generate`; the `<entity>_repo_ext.go` seams are scaffolded once and hand-owned. Aggregates port onto it one lane at a time — see [Porting onto the forge ORM](#porting-onto-the-forge-orm-p5b)
- **`internal/store/storetest/`** - The shared Postgres harness for `internal/store` tests

## Workflow

### Adding a New Migration

1. **Create and edit the migration**:

   ```bash
   make migration NAME=my_changes
   # Edit db/migrations/<version>_my_changes.up.sql
   ```

   `make migration` runs `forge db migration new` from the forge go.mod pins,
   which opens the file with the two compatibility declarations (below) as a
   comment to replace. Always let forge pick the version: it allocates a UTC
   timestamp that sorts after every existing one. There is no down migration —
   a bad migration is repaired by a new one written against the state the
   database is actually in.

   A migration file runs as ONE transaction (golang-migrate sends it as a
   single multi-statement query). A statement that cannot run in a transaction
   block, such as `CREATE INDEX CONCURRENTLY`, must be the only statement in
   its file; `forge lint --migration-safety` enforces it. Such a migration is
   safe beside a replica booting at the same time: forge's migrator waits for
   its run lock by polling `pg_try_advisory_lock`, holding no statement or
   snapshot between attempts, so the index build never waits on a waiter
   (forge #776; before it, every waiting replica failed its boot with
   `deadlock detected`. The goose bridge polls for its own lock the same way).

   **Say whether the previous release survives it.** Rolling back is
   redeploying the previous release onto the schema this one left — until a
   release after the cutover ships, that is the last goose release. Every
   migration after the baseline carries one of:

   ```sql
   -- forge:backward-compatible — additive column; the previous release never reads it
   -- forge:breaks-rollback drops chats.title, which the previous release selects
   ```

   The first is the default and the expand half of expand/contract (add in one
   release, stop reading the old shape, drop it in a later one). forge's
   migrator records it, so an older forge release can prove it may start on
   the newer schema. The second gives the rollback up on purpose; the runbook
   changes with it. forge.yaml sets
   `database.migration_safety.require_compat_declaration`, so
   `forge lint --migration-safety` (a blocking CI step) fails a migration that
   says neither — `make migration`'s unedited template included — gives no
   reason (a `<why …>` placeholder is none), or says both.

2. **Regenerate Go code**:

   ```bash
   make sqlc
   ```

   `forge generate` (at `forge.yaml`'s `forge_version`) does this too, as a
   generate hook, and re-projects `internal/store` from the applied schema;
   commit what it writes there as well.

3. **Write your Go code** using the newly generated types.

4. **Run and test** — the api-server applies pending migrations on startup
   (`reliant db migrate up` does the same as a one-shot), and DB-backed tests
   build their template database the same way.

5. **Commit everything** (migration + generated code + your Go code).

### When a migration lands out of order

golang-migrate applies only versions above the one the database records, so a
migration whose version sorts below one already deployed would never run; the
migrator refuses that state rather than skip it. If your branch's migration is
older than one that merged first, re-version it before merging:

```bash
forge db migration rebase db/migrations/<version>_my_changes.up.sql
```

## Applying and inspecting

| Command | Description |
| ------- | ----------- |
| `reliant db migrate up` | Apply every pending migration (DATABASE_URL, or DATABASE_DIRECT_URL when set) |
| `reliant db migrate status` | Read-only (one READ ONLY transaction): what `up` would do — up to date, apply N, build fresh, adopt, goose catch-up then adopt, or refuse and why. Exits non-zero on a refusal |
| `reliant db migrate force <version>` | Clear a dirty schema after a hand repair (records the version, runs no SQL) |
| `make sqlc` / `make db-regenerate` | Generate Go code from `db/migrations/` + `postgres/queries/` |

## goose history (frozen) and the goose bridge

Until 2026-10 the schema was goose migrations in `migrations/postgres/`. They
are frozen, byte for byte (`TestGooseHistoryIsFrozen`): a file added or edited
there fails the build. The baseline in `db/migrations/` is their squashed
result and lists every goose version in its `-- forge:adopts goose` lines
(`TestBaselineAdoptsExactlyTheGooseHistory` keeps the list and the directory
equal). Three kinds of database meet it, through the same `Migrate`:

- **fresh** (no `goose_db_version`): the baseline's SQL runs;
- **at goose's frozen head**: **adopted** — the baseline is recorded as
  applied in forge's bookkeeping (`schema_migrations*`), none of its SQL runs,
  and `goose_db_version` is left exactly as it was;
- **behind goose's head** (an older goose release migrated it): the **goose
  bridge** (`goose_bridge.go`) first runs goose itself — the same `goose.Up`
  every goose release ran at boot, over these frozen files — to goose's head,
  then the migrator adopts it, in the same run.

A goose version the frozen history does not hold, a frozen version recorded as
rolled back, or reliant's tables with no history at all are refused before
anything runs. `reliant db migrate status` says which of these a database is.
The goose files and library stay compiled in for the bridge; when they can go
is in the cutover runbook, `research/forge-migration/04-p5a-cutover-runbook.md`.

## Porting onto the forge ORM (P5b)

`forge.yaml` sets `database.orm.package: internal/store`, so `forge generate`
projects every applied table — and the `chats_with_activity` view, which its
`COMMENT ON VIEW … IS 'forge:entity'` opts in — into `internal/store`:
`<entity>_orm_gen.go` (the row struct, its `<Entity>Field*`/`Columns`/
`Constraint*` names, and the package-level delegates `Create<E>`,
`Get<E>ByID`, `List<E>`, `Count<E>`, `Update<E>`, `Update<E>Masked`,
`Delete<E>`), `store_gen.go` (one `<Entity>Store` interface per entity plus the
aggregate `Store`, from `store.NewStore(ormClient)`), and one hand-owned
`<entity>_repo_ext.go` seam per entity that forge scaffolds once and never
rewrites. This package (the Repository, its stores and the sqlc queries)
stays as it is and shrinks one aggregate lane at a time; the lanes are in
`research/forge-migration/08-p5b-spike.md`. The rules every lane follows:

1. **Generated delegate, builder, or hand SQL — in that order.** A by-key get,
   a filtered list or count, or a stamp is a generated delegate (compose
   `orm.WhereEq`/`WhereIn`/`WithOrderBy`/`WithLimit` onto `List<E>`/`Count<E>`).
   Predicates composed at runtime are the bun builder (`db.Bun().NewSelect()…`)
   in the entity's `_repo_ext.go`. A statement whose value is that it is one
   hand-tuned statement — a multi-CTE write, the advisory locks, an `unnest()`
   batch insert — moves byte for byte into `db.Bun().NewRaw(…)`, so a reviewer
   still reads SQL. Every ext query is a package-level function taking
   `(ctx context.Context, db orm.Context, …)`, like the generated delegates.

2. **Placeholders: `$N` → `?N`, zero-based.** bun formats the SQL itself:
   `NewRaw`, `Where`, `Set` and every builder fragment take `?` (the next
   argument) or `?N` (argument N, counting from **0**), so sqlc's `$1, $2` is
   `?0, ?1`. Every `?` in the text is a placeholder — in a comment, a string
   literal, or jsonb's `?`/`?|`/`?&` operators too — so write a literal one as
   `\?` (`\?|`, `\?&` for the jsonb operators). Only the raw passthroughs
   that bypass bun (`orm.Context`'s `Exec`/`Query`/`QueryRow`) take `$N`.
   `forge lint` fails a `$1` left in bun-formatted SQL
   (`forgeconv-bun-dollar-placeholder`) and a literal `?` bun would consume
   (`forgeconv-bun-literal-question-mark`), for string literals it can read.
   Arrays bind as `pgdialect.Array(v)`.

3. **Map entities to `core` at the boundary.** Generated rows are storage
   shapes (`store.Chat`), not domain types (`core.Chat`): `*string` for a
   nullable column, `int32` for `chats.unread`, a JSON document as `string`,
   CHECK-constrained text as `string`. An ext function returns `core` types
   (or the caller's own), converting in a small unexported mapper in the same
   `_repo_ext.go`; no `store.<Entity>` crosses into a handler, service or
   workflow. Behavior stays on the `core` types (`ThreadStatusForStopReason`,
   chat activity, `ComputeStreamingState`). `internal/store` may import
   `internal/db/core` and `gen/`, and must **never** import `internal/db`:
   the Repository delegates to the store while both exist, so the reverse
   edge is a cycle. Integer columns that hold a `reliantv1` enum already
   project to it (`COMMENT ON COLUMN … IS 'forge:go-type=…'`; see
   `db/migrations/20261020232630_chats_with_activity_view_entity.up.sql`).
   Mark a new one the same way. A view's comments, its columns' included,
   are dropped with the view, so a migration that DROPs and re-CREATEs
   `chats_with_activity` repeats that migration's view statements.

4. **Defaults apply when a field is unset.** forge projects a defaulted
   column so that leaving its field at the unset value sends `DEFAULT`
   (forge F12.5); do **not** copy the DEFAULT into Go to be safe. A NOT NULL
   scalar whose DEFAULT is not its Go zero is a pointer (`threads.status` is
   `*int32`, `workflows.state` `*reliantv1.WorkflowState`): `nil` is the
   DEFAULT, and a pointer to any value — the zero included — is written as
   is. A column whose zero is never a stored value (a JSON document, an
   array with a non-empty DEFAULT, CHECK-constrained text that refuses `''`)
   is `,nullzero`: the zero is the DEFAULT. A nullable or timestamp column
   keeps bun's `default:` tag: unset is the DEFAULT, so `Create<E>` cannot
   write an explicit NULL into a nullable column that has a DEFAULT (use a
   masked update or the builder). Read the tag on the generated field when
   in doubt.

5. **Composite keys: `Get<E>ByPK`.** A table whose primary key spans
   columns gets `Get<E>ByPK`, `Delete<E>ByPK` and `Upsert<E>` (`INSERT … ON
   CONFLICT` on the whole key) taking every key column in key order, plus
   `Update<E>`/`Update<E>Masked` addressed by the key fields set on the row;
   there is no `Get<E>ByID`. A missing row is `svcerr.NotFound`, as for
   `Get<E>ByID`. The eight: `connection_secrets` (connection_id, field),
   `inbox_dismissals` (user_id, item_id), `integration_access_refresh`
   (user_id, integration_id), `integration_event_access` (user_id,
   integration_id, account_key, resource_key), `message_order_counters`
   (counter_kind, scope_id), `project_daemons` (project_id, daemon_id),
   `thread_provider_accounts` (thread_id, provider), `update_stream_counters`
   (stream_kind, stream_id). Look a row up by a key prefix (every daemon of a
   project) with `List<E>` and `orm.WhereEq`.

6. **One Postgres test per ext query, interleaved with its sqlc twin.** Each
   `_repo_ext.go` query gets a test on `storetest.New(t)`, which hands the
   test its own migrated database reachable through both layers on one pgx
   pool (`env.ORM` and `env.Repo`). Until the sqlc twin is deleted the test
   proves the two agree: write through one, read through the other, both
   ways where it matters (`internal/store/storetest/storetest_test.go` is the
   shape). Delete the twin, its query in `postgres/queries/` and its
   Repository method in the same change that moves the last caller; the test
   then stays as the port's own. Run them with
   `FORGE_TEST_POSTGRES_URL=postgres://…/postgres go test ./internal/store/...`
   (or a `DATABASE_URL`, whose server is used); like this package's tests
   they skip under `-short`.

7. **One transaction, either layer.** The Repository and `internal/store`
   share one pool (`repo.ORM()` is the ORM client over it) and one
   transaction: forge's, carried in `ctx`. `Repo.RunTx` opens it through the
   ORM client, and every Repository/sqlc statement resolves to the
   transaction `ctx` carries (`tx_bridge.go`). So a transaction opened by
   either side is joined by both, and a transaction can port one statement
   at a time — `SaveMessageAtomic` or chat+thread creation may hold sqlc
   and store calls side by side across lanes:

   ```go
   err := repo.RunTx(ctx, func(ctx context.Context) error { // or repo.ORM().RunTx
       if err := repo.UpsertProjectDaemon(ctx, projectID, daemonID, path, nil); err != nil { // sqlc
           return err
       }
       return store.UpdateChatMasked(ctx, repo.ORM(), chat, []string{store.ChatFieldActiveDaemonID}) // store
   })
   ```

   Pass the ctx the closure receives to every call; the handle stays the
   plain client (`repo.ORM()`, never a `*orm.Tx`). A nested `RunTx` of
   either kind joins. The layer that OPENS the transaction owns its retry:
   `Repo.RunTx` keeps its ladder (40001/40P01, plus 23505 and 25P02);
   `orm.Client.RunTx` retries 40001/40P01 only, so keep `Repo.RunTx` around
   a transaction that relied on the other two until its port decides.
   `runAfterCommit` is `orm.AfterCommit`, so post-commit effects registered
   by either layer run once, after the commit that keeps them. A lock that
   needs its own transaction uses `BeginDetached` (or the Repository's
   `BeginTxWithOptions`), refusing when `orm.InTx(ctx)`. Tests that hold
   this: `internal/store/storetest/txbridge_test.go`.
   (A one-column stamp through `Update<E>` reads every other column back;
   pass `crud.NoReadBack()` when the caller does not need the row.)

8. **Consumers depend on the least they use (P6).** A port never widens a
   dependency. A handler, service or workflow that needs persistence
   declares, in its own package, an interface listing only the methods it
   calls, and takes that — never `db.Repository` or the aggregate
   `store.Store`, and one `<Entity>Store` only when the generated CRUD is all
   it needs. While a query is mid-port the Repository still satisfies that
   interface; when the Repository method goes, a small adapter over
   `orm.Context` and the ext functions does. A lane narrows the consumers of
   the methods it ports, and only those.
