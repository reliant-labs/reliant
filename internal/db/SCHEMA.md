# Database Schema Management

## Overview

Reliant runs exclusively on **Postgres**. The schema is **forge migrations**:
forward-only SQL files under `db/migrations/` (repo root), embedded into the
binary by `forge generate` (`db/embed_gen.go`) and applied by forge's migrator
(`forge/pkg/migratekit`, golang-migrate underneath). `forge generate` projects
the applied schema into `internal/store`, the forge ORM package, where every
query the Repo runs lives (P5b in `research/forge-migration/PLAN.md`).

## Files

- **`db/migrations/`** - Forge migrations, `<YYYYMMDDHHMMSS>_<name>.up.sql` (source of truth for the schema). The first is the baseline that replaced goose's history.
- **`migrate.go`** - `Migrate` (apply), `WaitForSchema` (wait for the api-server to apply), and the read-only state behind `reliant db migrate status`
- **`internal/store/`** - The forge ORM's projection of the applied schema (`forge.yaml` `database.orm.package`): `<entity>_orm_gen.go` and `store_gen.go` are regenerated by every `forge generate`; the `<entity>_repo_ext.go` seams are scaffolded once and hand-owned. The rules for writing a query there: [Queries on the forge ORM](#queries-on-the-forge-orm-p5b)
- **`internal/store/storetest/`** - The shared Postgres harness for `internal/store` tests

## Workflow

### Adding a New Migration

1. **Create and edit the migration**:

   ```bash
   make migration NAME=my_changes
   # Edit db/migrations/<version>_my_changes.up.sql
   ```

   `make migration` runs `forge db migration new` from the forge go.mod pins,
   which opens the file with the two compatibility declarations (below) as a
   comment to replace. Always let forge pick the version: it allocates a UTC
   timestamp that sorts after every existing one, including the newest on
   `origin/main` (it fetches main first and checks the result). There is no down migration —
   a bad migration is repaired by a new one written against the state the
   database is actually in.

   A migration file runs as ONE transaction (golang-migrate sends it as a
   single multi-statement query). A statement that cannot run in a transaction
   block, such as `CREATE INDEX CONCURRENTLY`, must be the only statement in
   its file; `forge lint --migration-safety` enforces it. Such a migration is
   safe beside a replica booting at the same time: forge's migrator waits for
   its run lock by polling `pg_try_advisory_lock`, holding no statement or
   snapshot between attempts, so the index build never waits on a waiter
   (forge #776; before it, every waiting replica failed its boot with
   `deadlock detected`).

   **Say whether the previous release survives it.** Rolling back is
   redeploying the previous release onto the schema this one left. Every
   migration after the baseline carries one of:

   ```sql
   -- forge:backward-compatible — additive column; the previous release never reads it
   -- forge:breaks-rollback drops chats.title, which the previous release selects
   ```

   The first is the default and the expand half of expand/contract (add in one
   release, stop reading the old shape, drop it in a later one). forge's
   migrator records it, so an older forge release can prove it may start on
   the newer schema. The second gives the rollback up on purpose; the runbook
   changes with it. forge.yaml sets
   `database.migration_safety.require_compat_declaration`, so
   `forge lint --migration-safety` (a blocking CI step) fails a migration that
   says neither — `make migration`'s unedited template included — gives no
   reason (a `<why …>` placeholder is none), or says both.

2. **Regenerate Go code**: `forge generate` (at `forge.yaml`'s
   `forge_version`; `make forge-generate-check` runs exactly that one)
   re-projects `internal/store` from the applied schema. Commit what it writes.

3. **Write your Go code** using the newly generated types, and your queries in
   the entity's `internal/store/<entity>_repo_ext.go` (rules below).

4. **Run and test** — the api-server applies pending migrations on startup
   (`reliant db migrate up` does the same as a one-shot), and DB-backed tests
   build their template database the same way.

5. **Commit everything** (migration + generated code + your Go code).

### When a migration lands out of order

golang-migrate applies only versions above the one the database records, so a
migration whose version sorts below one already deployed would never run; the
migrator refuses that state rather than skip it. If your branch's migration is
older than one that merged first, re-version it before merging:

```bash
forge db migration rebase db/migrations/<version>_my_changes.up.sql
```

This is enforced, not advisory: `go run ./tools/test-affected migration-order`
fetches `origin/main` and fails any migration on your branch that main does not
carry and whose version is at or below main's newest, naming both versions and
the remedy. It runs in `make test-affected` and `task ci:merge`
(`scripts/merge-gate.sh`) whenever the diff touches `db/migrations/`, in the
`check-migrations` workflow, and after `make migration`. It fails closed: if
`origin/main` cannot be refreshed it reports that instead of passing
(`MIGRATION_ORDER_OFFLINE=1` judges the local ref, for an offline desk only).
`forge lint --migration-safety` has the same rule but reads the local
`origin/main` as it was last fetched, which is how reliant#1399 passed it.

## Applying and inspecting

| Command | Description |
| ------- | ----------- |
| `reliant db migrate up` | Apply every pending migration (DATABASE_URL, or DATABASE_DIRECT_URL when set) |
| `reliant db migrate status` | Read-only (one READ ONLY transaction): what `up` would do — up to date, apply N, build fresh, or refuse and why. Exits non-zero on a refusal |
| `reliant db migrate force <version>` | Clear a dirty schema after a hand repair (records the version, runs no SQL) |

## Before forge migrations

Until 2026-10 the schema was goose migrations. The baseline in
`db/migrations/` is their squashed result (`forge db squash --from-dsn`).
Every database we keep was adopted from goose by a release carrying the goose
bridge (v1.8.2 onwards; the cutover runbook,
`research/forge-migration/04-p5a-cutover-runbook.md`, has the history), and
goose itself was removed afterwards. `goose_db_version` may still sit in such a
database; nothing reads it.

So `Migrate` meets a fresh database (the baseline builds it) or one forge's
migrator has a record in. reliant's tables with no record are refused before
anything runs: a goose-era database nobody adopted upgrades by running v1.8.2
first.

## Queries on the forge ORM (P5b)

`forge.yaml` sets `database.orm.package: internal/store`, so `forge generate`
projects every applied table — and the `chats_with_activity` view, which its
`COMMENT ON VIEW … IS 'forge:entity'` opts in — into `internal/store`:
`<entity>_orm_gen.go` (the row struct, its `<Entity>Field*`/`Columns`/
`Constraint*` names, and the package-level delegates `Create<E>`,
`Get<E>ByID`, `List<E>`, `Count<E>`, `Update<E>`, `Update<E>Masked`,
`Delete<E>`), `store_gen.go` (one `<Entity>Store` interface per entity plus the
aggregate `Store`, from `store.NewStore(ormClient)`), and one hand-owned
`<entity>_repo_ext.go` seam per entity that forge scaffolds once and never
rewrites. P5b ported every query the Repo ran (sqlc's and its hand
SQL) onto these seams, lane by lane (`research/forge-migration/08-p5b-spike.md`);
sqlc is gone. This package keeps the concrete `*db.Repo` over them: the
behaviour (guards, multi-statement transactions, hub emission, sealing) that
is not one statement. The Repo is concrete; declare the role you need where
you need it (rule 8). The rules every query follows:

1. **Generated delegate, builder, or hand SQL — in that order.** A by-key get,
   a filtered list or count, or a stamp is a generated delegate (compose
   `orm.WhereEq`/`WhereIn`/`WithOrderBy`/`WithLimit` onto `List<E>`/`Count<E>`).
   Predicates composed at runtime are the bun builder (`db.Bun().NewSelect()…`)
   in the entity's `_repo_ext.go`. A statement whose value is that it is one
   hand-tuned statement — a multi-CTE write, the advisory locks, an `unnest()`
   batch insert — moves byte for byte into `db.Bun().NewRaw(…)`, so a reviewer
   still reads SQL. Every ext query is a package-level function taking
   `(ctx context.Context, db orm.Context, …)`, like the generated delegates.

2. **Placeholders: `$N` → `?N`, zero-based.** bun formats the SQL itself:
   `NewRaw`, `Where`, `Set` and every builder fragment take `?` (the next
   argument) or `?N` (argument N, counting from **0**), so Postgres's `$1, $2`
   is `?0, ?1`. Every `?` in the text is a placeholder — in a comment, a string
   literal, or jsonb's `?`/`?|`/`?&` operators too — so write a literal one as
   `\?` (`\?|`, `\?&` for the jsonb operators). Only the raw passthroughs
   that bypass bun (`orm.Context`'s `Exec`/`Query`/`QueryRow`) take `$N`.
   `forge lint` fails a `$1` left in bun-formatted SQL
   (`forgeconv-bun-dollar-placeholder`) and a literal `?` bun would consume
   (`forgeconv-bun-literal-question-mark`), for string literals it can read.
   A slice binds as a postgres array through `orm.Arg(v)` (or
   `pgdialect.Array(v)`); a bare slice argument is JSON, so always wrap it
   (`orm.JSON(v)` for a document).

   **A hot hand-tuned statement binds its values.** bun formats every
   argument into the text, so under pgx's statement cache a statement whose
   values vary is a new prepared statement on every call: an extra
   Parse/Describe round trip, and a re-plan. For most queries that is noise;
   for a large statement on a hot path it is not — `SaveMessageAtomic` as
   `NewRaw` measured +35–80% per save against its sqlc predecessor, and at parity
   through the raw passthrough. Such a statement runs through `orm.Context`'s
   `QueryRow`/`Exec` with `$N` and plain Go slices for arrays (pgx encodes
   them), and its comment says why it is not `NewRaw`
   (`internal/store/save_message_atomic.go`). The generated by-key delegates
   (Get, Update, UpdateMasked, Delete) already bind.

   **Never select a relation with a star** — no `SELECT *`, `t.*`,
   `RETURNING *`, `ColumnExpr("t.*")` or `Returning("*")`. A star is
   expanded when the statement is prepared, and prepared statements outlive
   migrations (pgx's per-connection cache, and pgbouncer's server-side one,
   shared across clients): once a migration adds a column, every statement
   prepared before it fails with "cached plan must not change result type".
   That broke `ListArchivedChats` in prod on 2026-10-22, after
   `chats_with_activity` gained `working_threads`. Name the model's columns
   instead: `ColumnExpr("?TableColumns")` / `Returning("?TableColumns")` on a
   builder query (bun expands them from the query's model), `columnsOf[T](alias)`
   in raw SQL (`internal/store/columns.go`). A bare star over a derived table
   or a function (`SELECT * FROM (…)`, `FROM unnest(…)`) is fine: the
   statement fixes that shape. `internal/architecture`'s `TestNoStarSelects`
   enforces this; `internal/store`'s `TestPreparedQueriesSurviveAnAddedColumn`
   proves each converted query survives an added column on one connection.

3. **Map entities to `core` at the boundary.** Generated rows are storage
   shapes (`store.Chat`), not domain types (`core.Chat`): `*string` for a
   nullable column, `int32` for `chats.unread`, a JSON document as `string`,
   CHECK-constrained text as `string`. An ext function returns `core` types
   (or the caller's own), converting in a small unexported mapper in the same
   `_repo_ext.go`; no `store.<Entity>` crosses into a handler, service or
   workflow. Behavior stays on the `core` types (`ThreadStatusForStopReason`,
   chat activity, `ComputeStreamingState`). `internal/store` may import
   `internal/db/core` and `gen/`, and must **never** import `internal/db`:
   the Repo delegates to the store, so the reverse edge is a cycle. Integer columns that hold a `reliantv1` enum already
   project to it (`COMMENT ON COLUMN … IS 'forge:go-type=…'`; see
   `db/migrations/20261020232630_chats_with_activity_view_entity.up.sql`).
   Mark a new one the same way. A view's comments, its columns' included,
   are dropped with the view, so a migration that DROPs and re-CREATEs
   `chats_with_activity` repeats that migration's view statements.

4. **Defaults apply when a field is unset.** forge projects a defaulted
   column so that leaving its field at the unset value sends `DEFAULT`
   (forge F12.5); do **not** copy the DEFAULT into Go to be safe. A NOT NULL
   scalar whose DEFAULT is not its Go zero is a pointer (`threads.status` is
   `*int32`, `workflows.state` `*reliantv1.WorkflowState`): `nil` is the
   DEFAULT, and a pointer to any value — the zero included — is written as
   is. A column whose zero is never a stored value (a JSON document, an
   array with a non-empty DEFAULT, CHECK-constrained text that refuses `''`)
   is `,nullzero`: the zero is the DEFAULT. A nullable or timestamp column
   keeps bun's `default:` tag: unset is the DEFAULT, so `Create<E>` cannot
   write an explicit NULL into a nullable column that has a DEFAULT (use a
   masked update or the builder). Read the tag on the generated field when
   in doubt.

5. **Composite keys: `Get<E>ByPK`.** A table whose primary key spans
   columns gets `Get<E>ByPK`, `Delete<E>ByPK` and `Upsert<E>` (`INSERT … ON
   CONFLICT` on the whole key) taking every key column in key order, plus
   `Update<E>`/`Update<E>Masked` addressed by the key fields set on the row;
   there is no `Get<E>ByID`. A missing row is `svcerr.NotFound`, as for
   `Get<E>ByID`. The eight: `connection_secrets` (connection_id, field),
   `inbox_dismissals` (user_id, item_id), `integration_access_refresh`
   (user_id, integration_id), `integration_event_access` (user_id,
   integration_id, account_key, resource_key), `message_order_counters`
   (counter_kind, scope_id), `project_daemons` (project_id, daemon_id),
   `thread_provider_accounts` (thread_id, provider), `update_stream_counters`
   (stream_kind, stream_id). Look a row up by a key prefix (every daemon of a
   project) with `List<E>` and `orm.WhereEq`.

6. **One Postgres test per ext query.** Each `_repo_ext.go` query gets a
   test on `storetest.New(t)`, which hands the test its own migrated database
   reachable through both layers on one pgx pool (`env.ORM` and `env.Repo`).
   The tests the lanes wrote against a sqlc twin (`…AgreeWithSQLC`) now
   compare the query with the Repo method over it. A new test asserts
   the rows it expects. Run them with
   `FORGE_TEST_POSTGRES_URL=postgres://…/postgres go test ./internal/store/...`
   (or a `DATABASE_URL`, whose server is used); like this package's tests
   they skip under `-short`.

7. **One transaction, either layer.** The Repo and `internal/store`
   share one pool (`repo.ORM()` is the ORM client over it) and one
   transaction: forge's, carried in `ctx`. `Repo.RunTx` opens it through the
   ORM client, and every hand Repo statement resolves to the
   transaction `ctx` carries (`tx_bridge.go`). So a transaction opened by
   either side is joined by both, and Repo and store calls mix in one:

   ```go
   err := repo.RunTx(ctx, orm.Serializable, func(ctx context.Context) error { // or repo.ORM().RunTx
       if err := repo.UpsertProjectDaemon(ctx, projectID, daemonID, path, nil); err != nil { // Repo
           return err
       }
       return store.UpdateChatMasked(ctx, repo.ORM(), chat, []string{store.ChatFieldActiveDaemonID}) // store
   })
   ```

   Pass the ctx the closure receives to every call; the handle stays the
   plain client (`repo.ORM()`, never a `*orm.Tx`). A nested `RunTx` of
   either kind joins. The layer that OPENS the transaction owns its retry:
   `Repo.RunTx` keeps its ladder (40001/40P01, plus 23505, 25P02 and 40002);
   `orm.Client.RunTx` retries 40001/40P01 only, so keep `Repo.RunTx` around
   a transaction that relied on the others until its port decides.

   **`Repo.RunTx` takes the ORM's policy, and the policy's budget drives the
   ladder.** `Repo.RunTx(ctx, policy, fn)` takes the same `orm.TxPolicy` as
   `orm.Client.RunTx` — `orm.Serializable`, `orm.ReadCommitted`, or a
   refinement (`.WithMaxAttempts(n)`, `.WithReadOnly()`) — with no default:
   a blank level is refused (`orm.ErrInvalidTxOptions`) naming the call site.
   It is the Repo's one transaction primitive; `RunTxReadOnly` is sugar
   for `orm.Serializable.WithReadOnly()`, as on the ORM client. The two
   compose like this: the policy's `MaxAttempts` is the TOTAL number of
   times `fn` runs (begin failures included), and the Repo's ladder
   (`isRetryableError`) decides which failures spend an attempt, with
   `calculateBackoff` between them. So:

   | policy | runs `fn` | retried on |
   |---|---|---|
   | `orm.Serializable` | up to 7 (`orm.DefaultTxMaxAttempts`, = `maxRetries`+1) | the whole ladder |
   | `orm.Serializable.WithMaxAttempts(1)` | once; the raw error comes back verbatim (a contention measurement) | nothing |
   | `orm.ReadCommitted` | once | nothing |
   | `orm.ReadCommitted.WithMaxAttempts(orm.DefaultTxMaxAttempts)` | up to 7 | the whole ladder — 23505/40P01 are what READ COMMITTED can still raise |

   The ladder is the same at every level: the level decides how much budget a
   caller asks for, not which SQLSTATEs count. A failure the ladder does not
   accept, or the last attempt's, is returned verbatim. The last row is what
   the Repo's READ COMMITTED writers (`CreateUserUpdate`,
   `SaveMessageAtomic`, `MutateChatSelection`, the daemon registry, the
   workflow drafts) name, keeping the budget they had before the level
   became explicit. `Repo.RunTx` is declared `//forge:tx-opener level-arg=1`
   (and the detached `WrappedDBTX.BeginTxWithOptions` likewise), so `forge
   lint`'s `forgeconv-tx-lock-under-serializable` judges its calls as it
   judges `orm.Client.RunTx`'s.
   `runAfterCommit` is `orm.AfterCommit`, so post-commit effects registered
   by either layer run once, after the commit that keeps them. A lock that
   needs its own transaction uses `BeginDetached` (or the Repo's
   `BeginTxWithOptions`), refusing when `orm.InTx(ctx)`. A statement that
   must commit whatever the caller's transaction does (the write ledger)
   runs with `orm.Detached(ctx)`: on the pool, its own autocommit
   transaction. Tests that hold this: `internal/store/storetest/txbridge_test.go`.
   (A one-column stamp through `Update<E>` reads every other column back;
   pass `crud.NoReadBack()` when the caller does not need the row.)

   **Porting a hand-SQL transaction keeps its isolation.** Neither layer has
   a default level: every opener names one (`RunTx(ctx, orm.Serializable,
   fn)`, `BeginDetached(ctx, orm.ReadCommitted)`, `repo.RunTx(ctx,
   orm.Serializable, fn)`). A hand store's `db.BeginTx(ctx, nil)` was READ
   COMMITTED. A transaction whose correctness
   comes from row locks (`SELECT … FOR UPDATE`, advisory locks) rather than
   snapshot isolation names `orm.ReadCommitted` (one attempt) — under
   SERIALIZABLE the loser of a lock race fails with 40001 instead of reading
   the winner's write; `forge lint --conventions` reports a SERIALIZABLE
   transaction — `orm` or `Repo.RunTx` — that takes a lock
   (`forgeconv-tx-lock-under-serializable`). One that may survive a deadlock
   says so with `orm.ReadCommitted.WithMaxAttempts(n)`; one that runs a side
   effect it must not repeat (a token refresh over the network) keeps one
   attempt. `internal/store/connection_repo_ext.go`'s `connectionTx` is
   both READ COMMITTED and one attempt.

   Every opener's level is pinned on the wire by
   `storetest.TestTransactionOpenersBeginAtTheirLevel`: a port that moves a
   transaction adds or keeps its row there. Prove a lock-based one with a race
   test through `storetest.Env.Probe` (records each BEGIN's level and every
   SQLSTATE, so a 40001 that `RunTx` retried past still fails the test) and
   `Env.HoldLocks` (the winner, committed once the transaction under test is
   queued behind it) — `TestMergeWorktreeCleanupMetadataLoserReadsTheWinnersWrite`
   is the pattern. A nested opener joins the outer transaction at the
   OUTER's level, whatever policy it passes (the policy is still validated).

8. **The Repo is concrete; declare the role you need where you need it
   (P6).** `internal/db` declares no interface over `*db.Repo`. A handler,
   service or workflow that needs persistence declares, in its own package,
   an interface listing only the methods it calls, and takes that: a
   handler's or component's `Repository` in `deps.go` (forge mocks it into
   `mock_gen.go`), a contract package's in `contract.go`, an unexported
   `<thing>Store` beside the helper that takes it. A consumer that forwards
   the repo to a callee embeds the callee's exported role. Never the
   aggregate `store.Store`, and one `<Entity>Store` only when the generated
   CRUD is all it needs. Composition code (`internal/app`, the activity and
   tool registries, `workersetup`) takes `*db.Repo` itself. The sub-stores
   the Repo hands out (`Connections()`, `IntegrationWrites()`) are concrete
   too (`db.ConnectionStore`, `db.IntegrationWriteLedger`); their consumers
   declare their own slice of them as well.
