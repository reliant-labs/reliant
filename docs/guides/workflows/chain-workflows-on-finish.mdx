A nightly job that fails at 3am helps nobody until someone notices. In this guide a second workflow starts by itself every time the first one's run fails, and receives which run failed and why. Neither workflow names the other in its graph: the follow-up declares a `workflow_event` trigger, and you turn it on. [Workflow events](/automations/workflow-events) lists every field and payload key.

## Before you begin

- The `reliant` CLI, v1.21 or later, signed in ([Sign in and tokens](/cli/sign-in)).
- A Reliant project for the repository and a connected machine that holds it ([Run a machine from the terminal](/cli/run-a-machine)).
- The workflow you want to follow up on, in `.reliant/workflows/`. This guide uses a stand-in called `nightly-check`.

<Steps>
  <Step title="Know when a run counts as failed">
    A run reports `failed` when it errors, or when it ends at a node that declares `outcome: failure`. This stand-in runs a check and routes a non-zero exit to such a node:

    ```yaml .reliant/workflows/nightly-check.yaml
    name: nightly-check
    description: Runs the project's checks and ends failed when they fail.

    entry: [check]

    nodes:
      - id: check
        type: run
        args:
          command: "echo 'FAIL: 2 tests failed'; exit 1"
        timeout: 5m

      - id: passed
        type: save_message
        outcome: success
        args:
          role: assistant
          content: "Checks pass."

      - id: failed
        type: save_message
        outcome: failure
        args:
          role: assistant
          display_style: warning
          content: "Checks failed: {{nodes.check.stdout}}"

    edges:
      - from: check
        cases:
          - to: passed
            condition: nodes.check.exit_code == 0
        default: failed
    ```

    A run whose `run` node exits non-zero but reaches no failure node counts as `finished`: the exit code is an output to route on.
  </Step>
  <Step title="Declare the follow-up">
    The trigger watches `nightly-check` for `failed` and maps fields of the event into the follow-up's inputs:

    ```yaml .reliant/workflows/failure-follow-up.yaml
    name: failure-follow-up
    description: Opens a follow-up run for every failed nightly-check run.

    # lint:allow no-failure-path — its only step writes a message into this run
    triggers:
      - name: nightly-check-failed
        workflow_event:
          workflows: [nightly-check]
          outcomes: [failed]
        inputs:
          failed_run: "{{ trigger.payload.run_id }}"
          reason: "{{ trigger.payload.error }}"

    inputs:
      failed_run:
        type: string
        default: ""
      reason:
        type: string
        default: ""

    entry: [note]

    nodes:
      - id: note
        type: save_message
        outcome: success
        args:
          role: assistant
          display_style: warning
          content: |
            nightly-check run {{ inputs.failed_run }} failed.
            {{ inputs.reason }}
    ```

    Add `finished` or `blocked` to `outcomes` to react to those too. To have an agent investigate instead, replace `note` with an agent node:

    ```yaml .reliant/workflows/failure-follow-up.yaml
      - id: investigate
        type: workflow
        ref: builtin://agent
        args:
          mode: plan
        thread:
          mode: inherit
          inject:
            role: user
            content: |
              nightly-check run {{ inputs.failed_run }} failed. Run the checks,
              find the cause and report it. Do not change any files.
    ```
  </Step>
  <Step title="Test the trigger with a scenario">
    A scenario starts the run through the trigger with a sample payload, so the input mapping is tested without a real failure:

    ```yaml .reliant/workflows/failure-follow-up/scenarios/failed_run_gets_a_note.yaml
    name: failed_run_gets_a_note
    trigger:
      name: nightly-check-failed
      payload: {run_id: run-123, outcome: failed, error: "Checks failed: FAIL: 2 tests failed"}
    events: []
    expect:
      outcome: completed
      completed: [note]
      messages:
        note:
          content_contains: ["nightly-check run run-123 failed."]
    ```

    ```bash terminal
    reliant workflow lint .reliant/workflows/failure-follow-up.yaml
    reliant workflow scenario run
    ```

    ```text
    1 workflow(s): 0 lint error(s), 0 warning(s)
    ✅ All scenarios passed
    ```

    Commit both files, so the machine syncs them. [Test workflows with scenarios](/guides/workflows/test-workflows-with-scenarios) covers the format.
  </Step>
  <Step title="Turn the trigger on">
    Declaring a trigger fires nothing. Activate it for this project and machine, with the message each follow-up run starts with:

    ```bash terminal
    reliant trigger activate --workflow failure-follow-up --machine build-box \
      --name-prefix guides-sandbox-chain --message "Follow up on the failed nightly-check run."
    ```

    ```text
    TRIGGER               OUTCOME  ACTIVATION                                                                          NOTE
    nightly-check-failed  enabled  guides-sandbox-chain · nightly-check-failed (35bcfc5f-7410-4dd6-800a-cda23d43821b)  -
    ```
  </Step>
  <Step title="Verify a failure starts the follow-up">
    Run the watched workflow, then list the trigger's firings:

    ```bash terminal
    reliant workflow run nightly-check --project-path .
    reliant trigger events "guides-sandbox-chain · nightly-check-failed"
    ```

    ```text
    OCCURRED AT           OUTCOME   CHAT                                  DEFINITION
    2026-11-20T16:06:36Z  launched  a24ea239-1817-5cb6-b403-71a262e33b85  machine build-box at .reliant/workflows/failure-follow-up.yaml @ master f687abe, clean …
    ```

    `launched` with a chat ID is the follow-up run. `reliant workflow status a24ea239-1817-5cb6-b403-71a262e33b85` shows `Outcome: ✓ SUCCESS`, and the run's message in the app reads `nightly-check run bab4c621-d14c-4244-ba39-072766995a66 failed.`, naming the run that failed.
  </Step>
  <Step title="Turn it off">
    ```bash terminal
    reliant trigger disable "guides-sandbox-chain · nightly-check-failed"   # pause; enable resumes it
    reliant trigger delete "guides-sandbox-chain · nightly-check-failed"
    ```
  </Step>
</Steps>

## What this does not do

- **No loops.** A workflow-event trigger never fires on a run it started, or on that run's descendants, and a chain of event-started runs stops after five hops.
- **It watches only your own workflows' runs.** Leave `workflows` empty to watch all of them.
- **Nobody answers the follow-up.** Event-started runs are unattended: an agent in one decides and proceeds, and some tools are withheld from it ([Unattended by design](/automations/overview#unattended-by-design)). In an organization, an agent follow-up spends only the organization's AI accounts.
- **`error` is not always filled.** It holds the error of a run that errored. For a run that ended at an `outcome: failure` node it is empty, so put what the follow-up needs in that node's message, or have the follow-up open the failed run.

## Troubleshooting

<AccordionGroup>
  <Accordion title="message is required: the declared trigger has no prompt, so the activation must write one">
    `trigger activate` needs the first message for each run. Pass it with `--message`.
  </Accordion>
  <Accordion title="at least one user message or attachment is required">
    Shown by `reliant trigger events` and `reliant trigger get` when the activation has no message. Check `Message:` in `reliant trigger get <name>`. If it is empty, delete the activation, remove `prompt:` from the declared trigger, and activate again with `--message`.
  </Accordion>
</AccordionGroup>
