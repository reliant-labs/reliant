By the end of this guide, labelling a GitHub issue `agent:ready` starts an agent that writes a failing test, fixes the bug, runs your fast checks and opens a pull request that closes the issue. The Reliant bot opens it, so you can approve and merge it yourself.

This is `autopilot-issue-worker`, one of the [Autopilot](/guides/autopilot) built-ins. Its own description says: "Never merges, never approves."

## Before you begin

- The `reliant` CLI, v1.21 or later, signed in ([Sign in and tokens](/cli/sign-in)), and `gh`.
- The Reliant GitHub App installed on the repository, and push access to it on your own account ([GitHub integration](/integrations/github#access)).
- A connected machine with a clone of the repository ([Run a machine from the terminal](/cli/run-a-machine)). The agent works in a worktree of that clone.
- In an organization: an organization AI account that can run the authoring model (the `flagship` tag by default). See [What this does not do](#what-this-does-not-do).

<Steps>
  <Step title="Create a project for the clone">
    Run this in the clone on the machine. The project's path must be the clone itself, or a folder holding it as a subdirectory named after the repository.

    ```bash terminal
    reliant project create --name guides-sandbox-autopilot
    ```

    ```text
    9859294a-8b3c-419f-a5c4-eb85a022fd65
    ```
  </Step>
  <Step title="Turn on the issue worker">
    `--machine` takes the machine's hostname or daemon ID. `gate_command` is the check that must pass before anything is pushed. The default runs `gofmt` and `task test:short` or `make test-short`, so set it for your repository.

    ```bash terminal
    reliant trigger activate --workflow builtin://autopilot-issue-worker \
      --machine build-box --project-id 9859294a-8b3c-419f-a5c4-eb85a022fd65 \
      --param 'repos=["reliant-labs/guides-sandbox"]' \
      --param 'gate_command=go test ./...' \
      --name-prefix "guides-sandbox-autopilot · issue-worker"
    ```

    ```text
    TRIGGER      OUTCOME  ACTIVATION
    ready-label  enabled  guides-sandbox-autopilot · issue-worker · ready-label (30f7ac0c-...)
    mention      enabled  guides-sandbox-autopilot · issue-worker · mention (c175e840-...)
    ```

    Only you and the accounts in `trusted_ids` can start work; anyone else's label or mention is skipped. Other settings, such as `max_turns` and `lease_minutes`, are in [Autopilot settings](/guides/autopilot#issue-worker).
  </Step>
  <Step title="Create the label">
    The workflow creates its other labels on its first run, but that run starts from this one, so create `agent:ready` yourself:

    ```bash terminal
    gh label create "agent:ready" --color 0e8a16 --description "An agent may work this issue"
    ```
  </Step>
  <Step title="Label an issue">
    Write the issue the way you would for a teammate: what is wrong and what done looks like.

    ```bash terminal
    gh issue create --title "textutil.Truncate panics when the string is shorter than n" \
      --body 'Calling textutil.Truncate("hi", 5) panics. Return the string unchanged when it is short enough.'
    gh issue edit 2 --add-label "agent:ready"
    reliant trigger events 30f7ac0c-17e7-490c-a0b7-5881326e6d21   # the ready-label activation
    ```

    A `launched` row with a chat ID means the agent started. Commenting `@reliant` on an open issue starts it the same way.
  </Step>
  <Step title="Watch it work">
    The run takes a **lease** on the issue: a comment from the bot and the `agent:working` label, so a second label cannot start a second run. Then it:

    1. creates a worktree from the default branch;
    2. runs an agent whose shell has no credentials to write a failing test and the smallest fix;
    3. runs `gate_command`, and retries the agent once with half the turns if it fails;
    4. pushes an `autopilot/issue-<number>` branch, never the default branch and never with `--force`.

    Follow it with `reliant workflow follow <chat>` or under **Workflows → Runs**.
  </Step>
  <Step title="Review the pull request">
    ```bash terminal
    gh pr list --label agent:authored
    gh issue view 2 --comments
    ```

    The pull request comes from `reliant-labs[bot]`, says `Closes #2`, and carries `agent:authored`, `agent:in-review` and a size label (`size:S` under 60 changed lines). Its footer reads "Never merged by Autopilot; a human reviews and merges." The issue swaps `agent:ready` for `agent:in-review` and gets a comment linking the pull request.

    If the agent could not finish, the issue gets `agent:punted` (it needs your decision) or `agent:blocked` (it tried and failed) and a comment saying what is missing. Add `agent:ready` again once you have answered it.

    Review the change, then approve and merge it yourself. Because the bot is the author, a branch rule that requires another person's approval works as it does for a teammate.
  </Step>
  <Step title="Turn it off">
    Pass `--project-id`. Without it, `deactivate` pauses the issue worker in every project you own.

    ```bash terminal
    reliant trigger deactivate --workflow builtin://autopilot-issue-worker \
      --project-id 9859294a-8b3c-419f-a5c4-eb85a022fd65
    ```
  </Step>
</Steps>

## What this does not do

- **It never merges or approves.** If you want a pipeline that merges, you compose it yourself: a workflow you write can call `github/pr.merge@1` in an action node, pinned to the reviewed head commit ([Merging is a workflow step](/integrations/github#merging-is-a-workflow-step-never-an-agent-tool)).
- **It does not pick issues.** Only issues you or a trusted account opted in are worked. On-call files issues as `agent:triage`, and a person promotes them.
- **It does not touch CI, secrets or deploy configuration.** It punts those issues, and changes over about 400 lines, back to you.
- **It has no budget of its own.** One attempt runs up to 120 agent turns, plus a retry of up to 60 ([What it costs](/guides/autopilot#what-it-costs)).
- **In an organization with two or more members, runs spend only the organization's AI accounts** by default (`Unattended funding: org_only` in `reliant trigger get`). The CLI cannot widen that. A person allows your own accounts on the automation in the app, or an admin adds an organization account.

## Troubleshooting

<AccordionGroup>
  <Accordion title="This automation runs only on its organization's AI accounts, and none of them can run the flagship model">
    `reliant trigger events` shows the firing as `failed` with no chat, and `reliant trigger get` shows `Health: degraded`. Nothing was written to the issue, and a second failure in a row pauses the activation. An admin can add an organization API key or turn on Reliant credits, or you can set `model` to one an organization account can run. Then label the issue again.
  </Accordion>
  <Accordion title="'agent:ready' not found">
    The repository has no such label yet. Create it first, as in step 3.
  </Accordion>
  <Accordion title="No checkout of owner/name was found in the worktree">
    The project's path does not hold a clone whose `origin` is this repository. Point the project at the clone, or at a folder holding it in a subdirectory named after the repository.
  </Accordion>
  <Accordion title="The repo's fast gate failed, so nothing was pushed or opened">
    `gate_command` failed after both attempts; the issue comment shows the end of its output. Check that it passes in a clean clone on the machine.
  </Accordion>
</AccordionGroup>
