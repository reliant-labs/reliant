You will move the `shop` project to a newer Forge release in one command and review the result. `forge project upgrade` does every mechanical step for the range: Go modules, the codemods and playbook steps of each release you cross, the scaffolded files you have not edited, then generate and lint. What it cannot decide, it lists.

A project pins one Forge in `forge.yaml` (`forge_version`), and `reliant forge` hands each command to that version, so the pin moves only when you move it ([Forge CLI](/cli/forge)).

## Before you begin

- A Forge project in git with a clean working tree, such as `shop` from [Add a database table with a CRUD API and pages](/guides/forge/add-table-crud-api-pages).
- Go on your `PATH`. No account.

<Steps>
  <Step title="Pick the target">
    Check the current pin:
    ```bash terminal
    grep forge_version forge.yaml
    ```
    ```text
    forge_version: v1.6.1-0.20261115024114-0ab7c562e817
    ```
    To move to the Forge inside `reliant` (`reliant forge --version`), use `reliant forge` in the steps below. To go past it, install the target release once and use that binary, written `forge` below:
    ```bash terminal
    (cd "$(mktemp -d)" && GOBIN="$HOME/.local/forge-v1.8.0" go install github.com/reliant-labs/forge/cmd/forge@v1.8.0)
    export PATH="$HOME/.local/forge-v1.8.0:$PATH"
    forge --version
    ```
    ```text
    forge version v1.8.0
    ```
    `project upgrade` runs as the binary you call, not the pinned one. One run jumps at most two minor releases; a larger jump is refused with the version to stage through.
  </Step>
  <Step title="List the migration playbooks">
    A release whose change a diff cannot explain ships a migration playbook: steps for you or an agent. List the ones that match this project:
    ```bash terminal
    forge project upgrade list
    ```
    ```text
    Project is up to date.
    ```
    No playbook applies between this pin and v1.8.0. When one does, it is listed by release ID; read it with `forge agent skill load migrations/<id>`.
  </Step>
  <Step title="Preview the upgrade">
    `--check` writes nothing. It names each file that differs, grouped by what adopting it costs:
    ```bash terminal
    forge project upgrade --check --to v1.8.0
    ```
    ```text Output (trimmed)
    forge project upgrade --check (dry run): v1.6.1-0.20261115024114-0ab7c562e817 (dev build) → v1.8.0

      go.mod: v1.6.1-0.20261115024114-0ab7c562e817 → v1.8.0
      gen/go.mod: v1.6.1-0.20261115024114-0ab7c562e817 → v1.8.0
      forge.yaml: v1.6.1-0.20261115024114-0ab7c562e817 (dev build) → v1.8.0
      3 with local edits (skipped), 15 up to date

      Your lines and the template's (merge by hand):
        internal/metrics/metrics.go       4 behind, 37 yours
        pkg/middleware/middleware.go      5 behind, 38 yours
        cmd/shop/cmd/commands.go          4 behind, 59 yours

    Files you own, whose forge templates have moved on:
      2 cheap adopt(s), 15 merge(s), 2 absent here
    ```
    Files you have not edited update on their own; a file you edited is reported and kept. `--check <path>` prints one file's diff.
  </Step>
  <Step title="Run the upgrade">
    ```bash terminal
    forge project upgrade --to v1.8.0
    ```
    ```text Output (trimmed)
    Forge module requirements synchronized to v1.8.0.
    forge_version → v1.8.0 (forge.yaml updated)
    🔁 regenerating
    ✅ Code generation complete — 64 file(s) written, 12 changed (1 new, 11 updated).
       1 of them changed outside forge's writers: frontends/web/pnpm-lock.yaml
    Converged: every mechanical fix applied and nothing is left for a person.
    ```
    With `--json` it prints one document a pin bot can branch on: exit `0` converged, `9` needs a person (`needs_human` names each item and its fix), `1` failed, `2` retryable.
  </Step>
  <Step title="Review the diff">
    ```bash terminal
    git status --short
    ```
    ```text
     M forge.yaml
     M go.mod
     M go.sum
     M gen/go.mod
     M gen/go.sum
     M frontends/web/package.json
     M frontends/web/pnpm-lock.yaml
     M frontends/web/src/components/nav.tsx
     M internal/handlers/catalog/helpers_gen_test.go
    ?? frontends/web/src/lib/auth/route-access_gen.ts
     ...
    ```
    Merge the files `--check` listed as yours by hand, or adopt one wholesale with `forge project upgrade --force <path>`. `forge project disown <path> --reason "..."` claims a file for good, and upgrade never touches it again.
  </Step>
  <Step title="Verify and record">
    `reliant forge` now hands every command to v1.8.0, building it once:
    ```bash terminal
    go build ./... && reliant forge lint --quiet
    ```
    ```text
    forge: building forge v1.8.0 (one time; cached in ...)
    ✅ All 29 gating linters passed.
    ```
    Run `task test`, then commit the upgrade as one change. If a playbook was listed, finish its steps and record it with `forge project upgrade apply <id>` so `upgrade list` stops showing it.
  </Step>
</Steps>

## What this does not do

- **No silent overwrites.** A file you edited is replaced only when you name it after `--force`.
- **No downgrade.** To return to the old Forge, revert the upgrade commit.

## Troubleshooting

<AccordionGroup>
  <Accordion title="this forge is v1.8.0, but forge.yaml pins forge_version ... — a different forge than the project's">
    Printed before the pin moves. Ignore its advice to run the pinned Forge: the upgrade must run as the newer binary.
  </Accordion>
  <Accordion title="Exit 9: Still needs a person">
    Everything mechanical is applied. Fix each listed item, then run `forge project upgrade` again to confirm it converges.
  </Accordion>
</AccordionGroup>
