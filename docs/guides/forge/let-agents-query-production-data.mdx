By the end of this guide an AI agent can answer questions from your production database with one command, and Postgres, not a prompt, stops it from writing anything or reading a credential. The agent runs [`reliant forge db query`](/reference/cli#reliant-forge-db-query), which reads as a role forge generates from your migrations, inside a `READ ONLY` transaction, and records every call.

The seam is that your migrations are the schema. `forge generate` decides, column by column, what the read-only role `forge_ro` may select, and the migrator applies those grants after every migration run. [Safe migrations](/deep-dives/safe-migrations#the-read-only-role-and-secret-columns) explains how the grants converge.

## Before you begin

- A Forge project with a database, deployed to a hosted environment: [Deploy a Go API with managed Postgres](/guides/hosting/deploy-go-api-managed-postgres).
- Forge v1.6.1 or later in the project (`reliant forge --version`).
- The organization's `db:query` grant. Owners and admins hold it.
- An agent that runs commands as you. In a Reliant chat, the agent's shell is signed in as you, so its queries are recorded under your name.

<Steps>
  <Step title="Decide every credential-like column">
    Lint refuses a column whose name looks like a credential until someone decides it. This table has an `api_key`:

    ```bash terminal
    reliant forge lint --db-grants
    ```

    ```text Output
    ❌ db-grants — 1 error
       ✗ db/migrations/20261120090758_create_tasks.up.sql:14 [forge-db-grants-undecided] tasks.api_key looks like a credential and nobody decided it: forge_ro cannot read it
    ```

    Mark it secret in the migration. If the column has already shipped, write a new migration instead:

    ```sql db/migrations/20261120090758_create_tasks.up.sql
    COMMENT ON COLUMN tasks.api_key IS 'forge:secret';
    ```

    `forge:readable <why>` grants a column that only looks like a credential. A credential in a column with a neutral name, such as `config`, needs `forge:secret` even though lint can't spot it. Re-run lint; it ends `✅ All 1 gating linters passed.`
  </Step>

  <Step title="Generate the grants and ship them">
    ```bash terminal
    reliant forge generate
    ```

    The table's row in the read-only grants leaves the secret out:

    ```sql db/grants/readonly/public.tasks_gen.sql
    ('public', 'tasks', ARRAY['created_at', 'done', 'id', 'owner', 'title', 'updated_at']::text[])
    --   public.tasks: api_key  (forge:secret, withheld)
    ```

    Commit, then cut and deploy a release as in [Deploy a Go API](/guides/hosting/deploy-go-api-managed-postgres). The migration job applies the grants before the new release serves.
  </Step>

  <Step title="Tell your agent how to read production">
    Add the rule to the instructions your agent loads: the project's [`reliant.md` memory file](/settings/memories) in Reliant, or `AGENTS.md` in another harness:

    ```markdown reliant.md
    Read production data only with:
      reliant forge db query prod "<one SELECT>" --confirm-env prod --reason "<why>" --json
    Prefer aggregates and LIMIT. Exit 1 means the query was refused; exit 2 means it was not answered.
    ```

    `--json` gives the agent `ok`, `exit_code`, `columns` and `rows` to parse. `reliant forge agent skill load db/query` is the full reference, and agents in a Forge project can load it themselves.
  </Step>

  <Step title="Run a query against production">
    ```bash terminal
    reliant forge db query prod "select current_user" \
      --confirm-env prod --reason "docs guide verification"
    ```

    ```text Output
    current_user
    forge_ro
    (1 row, 4 ms; release v6.5.0; audit e2cd93ae-bef7-4b70-b971-dae365824e5b)
    ```

    The platform runs the query inside the environment as `forge_ro`; you hold no database password. The footer names the live release and the audit record.
  </Step>

  <Step title="Verify the boundary holds">
    Ask for what the agent must not get. Each of these exits 1:

    | Query | Refused with |
    |---|---|
    | `select api_key from tasks` | `permission denied for table tasks` |
    | `select * from tasks` | `permission denied for table tasks` |
    | `select row_to_json(t) from tasks t` | `permission denied for table tasks` |
    | `update tasks set done = true` | `only SELECT, WITH, TABLE, VALUES, SHOW and EXPLAIN statements are allowed; got UPDATE` |
    | `with x as (update tasks set done = true returning id) select count(*) from x` | `this connection is read-only: cannot execute SELECT in a read-only transaction` |
    | any query without `--confirm-env prod --reason` | `this environment is audited: confirm_env_id must equal the environment id` |

    The last write got past forge's text check and Postgres refused it. Naming the readable columns works: `select id, title, owner from tasks limit 5` returns rows.
  </Step>

  <Step title="Check the record">
    ```bash terminal
    reliant forge obs changes prod
    ```

    ```text Output (trimmed)
    TIME            KIND       WHAT                                              BY
    11-20 09:14:45  activity   query database database guides-sandbox-dbquery    you@example.com
    11-20 09:14:22  activity   query database database guides-sandbox-dbquery    you@example.com
    11-20 09:09:43  promotion  promoted v6.5.0                                   you@example.com
    ```

    `BY` is the account that ran the query: here, the person whose chat the agent ran in. The control plane's audit log keeps each statement in full, with its reason.
  </Step>
</Steps>

## What this does not do

- It never writes. Data fixes belong in a migration or application code, reviewed like any change.
- On dev it reads as your app's own role. `db query dev` connects with the dev `DATABASE_URL` (`current_user` is `postgres`), so secret columns are readable there. To check the role before you ship, ask Postgres: `select has_column_privilege('forge_ro', 'tasks', 'api_key', 'SELECT')` returned `false` on the local stack.
- It doesn't let an unattended run into an audited environment. Production is `audited` by default, which admits people only. An organization automation token is refused. A machine token works only on an environment whose `data_access` is `open`, and only with the `db:query` scope. See [Managed Postgres](/hosting/managed-postgres#read-the-data-safely).
- The [forge MCP server](/hosting/observability/agents#it-speaks-mcp) has no query tool. An agent in another harness needs a shell with `reliant forge` signed in.
- It caps each query: one at a time per person per environment, 30 a minute, 200 rows by default (10,000 at most) and a 5-second timeout (30 at most).

## Troubleshooting

<AccordionGroup>
  <Accordion title="this environment is audited: confirm_env_id must equal the environment id">
    Pass `--confirm-env <env>`, the environment name again, and `--reason "<why>"`. Both are required on any environment that isn't local or ephemeral.
  </Accordion>
  <Accordion title="permission denied for table tasks">
    The query touched a column `forge_ro` can't read: a `forge:secret` column, an undecided credential-like one, or any column through `select *`. Name the readable columns. To make a column readable, mark it `forge:readable <why>` in a migration and deploy.
  </Accordion>
  <Accordion title="exit 2">
    Forge could not look, so treat the result as not answered, never as no rows. `env prod does not exist on its control plane yet` means nothing is deployed there; `credential_missing` in `--json` means the environment's read-only role isn't provisioned yet.
  </Accordion>
</AccordionGroup>
