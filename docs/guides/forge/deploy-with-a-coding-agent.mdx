By the end of this guide, your coding agent will have put your app online with no account, no token and no card, and handed you a live URL and a claim link. Use it when you already have a Vite or Next.js app, or an app with its own Dockerfile, and you want a URL to share before you decide where it lives.

The agent does it with [Forge](/forge/overview), through its MCP server or its CLI. Forge reads the app where it stands, adds a `forge.yaml` and a `deploy/kcl/` directory, builds a release, and publishes it to [Reliant Cloud](/hosting/overview) under a temporary anonymous identity. The deploy stays online for 72 hours. If you open the claim link and sign up (free) before then, the deploy becomes yours.

## Before you begin

- Claude Code, Codex or Cursor, open on the app's repository.
- Node 18 or later. `npx -y @reliantlabs/forge mcp` downloads the matching Forge binary the first time it runs.
- An app Forge can adopt: a Vite or Next.js app at the repository root, or an app in any language with its own Dockerfile. [The limits](#what-it-fits) say what fits.

<Steps>
  <Step title="Install the Forge MCP server in your agent">
    Pick the one you use.

    ```bash terminal
    claude mcp add forge -- npx -y @reliantlabs/forge mcp    # Claude Code
    codex mcp add forge -- npx -y @reliantlabs/forge mcp     # Codex
    ```

    For Cursor, put this in `.cursor/mcp.json` for one project, or `~/.cursor/mcp.json` for all of them:

    ```json .cursor/mcp.json
    {
      "mcpServers": {
        "forge": {"command": "npx", "args": ["-y", "@reliantlabs/forge", "mcp"]}
      }
    }
    ```

    The server gives the agent a `deploy_claimable` tool beside Forge's lint, generate and skill tools. [Connect Claude Code or Cursor to Forge over MCP](/guides/forge/connect-claude-code-cursor-mcp) lists every tool and shows how to check the server answers. You can skip this step: the agent can run the same deploy as a shell command (step 3).
  </Step>
  <Step title="Paste the prompt">
    Give the agent this:

    ```text prompt
    Deploy this app with Reliant Forge. Run `npx -y @reliantlabs/forge@latest env deploy prod --claimable`
    (or call the forge MCP server's `deploy_claimable` tool), then give me the live URL and the
    claim link. The claim link expires in 72 hours; treat it like a password.
    ```

    Your agent asks before it calls a tool that changes something, so expect an approval prompt for `deploy_claimable`.
  </Step>
  <Step title="Let it deploy">
    The deploy takes minutes. In a directory with no `forge.yaml`, Forge first adopts the app, and prints one line saying what it added: `forge.yaml`, `deploy/kcl/`, an `AGENTS.md` and Forge's `.gitignore` entries. The app's own files are not changed. It then builds, publishes and waits for the rollout.

    The command the agent runs is:

    ```bash terminal
    npx -y @reliantlabs/forge@latest env deploy prod --claimable
    ```

    Use `@latest`: an older cached Forge refuses with "add forge first" instead of adopting the app. `--claimable` implies `--yes`, so nothing prompts. Add `--plan-only` first if you want to see what it would do, and what it would refuse.
  </Step>
  <Step title="Receive the URL and the claim link">
    The result has a public URL, a claim link, when the deploy goes offline, and the plan's limits. With `--json`, or through the MCP tool, it is one structured document the agent relays to you, and it only calls the app live once the rollout came up healthy. The agent should say something like this:

    ```text Output
    It's live at <url>. This deploy isn't tied to any account yet: it goes offline
    at <expires_at> and is deleted 7 days later. To keep it, open this link and
    sign up (free): <claim_url>. Treat the link like a password: whoever opens it
    first owns the deploy.
    ```

    To deploy again after a change, run the same command. You keep the same URL and claim link, and the expiry does not move. `forge env status prod --claimable` prints them again.
  </Step>
</Steps>

## What it fits

The claimable plan is small on purpose. It fits one static site (Vite or Next.js), or one service built from your app's own Dockerfile with one managed Postgres database. A Next.js app has to build as a static export (`output: "export"`).

**An unclaimed service has no outbound internet.** It answers requests and uses its own database, but every call out of it fails: payments, webhooks, email, model APIs and DNS for names outside the cluster. A static site is not affected, because its requests come from the browser. This is the platform, not a bug in your app, so neither you nor the agent should try to work around it. It ends when you claim the deploy.

Workers, cron jobs, a second service or database, custom domains and remote builds are refused, and the refusal names what to change. The exact limits, the `--json` fields, and every refusal with its exit code are in [Deploy a Vite or Next.js app without an account](/forge/deploy-without-an-account#limits) and in [Forge's MCP reference](https://github.com/reliant-labs/forge/blob/main/docs/mcp.md): this guide does not repeat them.

## Keep the claim link private

The claim link is a credential: whoever opens it first owns the deploy. Tell the agent not to put it in an issue, a pull request, a commit, a log or a README, and keep it out of screenshots you share.

## Claim it

Open the claim link and sign up, or sign in. The deploy moves into your account and stops expiring. A static site stays free in your free hosting organization (one per person, any number of sites). A service and its managed Postgres get their outbound internet back, and need [paid hosting](/hosting/overview#billing) to keep running long term. [What claiming gives you](/forge/deploy-without-an-account#what-claiming-gives-you) has the detail.

## Troubleshooting

<AccordionGroup>
  <Accordion title="The agent says the deploy was refused with exit code 1, claimable_signed_in">
    A Forge credential resolves on this machine: you ran `forge cloud login`, or you are inside a Reliant chat. `--claimable` is only for no account. Drop it and deploy to your account with `forge env deploy prod`.
  </Accordion>
  <Accordion title="Exit code 4, claimable_ineligible">
    The project does not fit the plan above. Run `forge env deploy prod --claimable --plan-only`: each refusal names the change that fixes it.
  </Accordion>
  <Accordion title="Exit code 4, claimable_throttled">
    A rate limit. Wait until the `retry_at` it prints, and do not retry in a loop: Forge never retries on its own.
  </Accordion>
  <Accordion title="The app deploys but its service never comes up">
    If it calls an outside API at startup, it cannot, because an unclaimed service has no outbound internet. Claim the deploy first.
  </Accordion>
</AccordionGroup>

## What to do next

Once you have claimed the deploy, sign in with `forge cloud login` (inside Reliant it is already done) and deploy to your account with `forge env deploy prod`, with no `--claimable`. After every deploy, prove it with `forge obs check prod --wait --json`: its exit code says whether the release is healthy, regressed, or could not be judged. [Querying with forge obs](/hosting/observability/forge-obs) covers the exit codes.

## Give your agent these docs

The documentation is also an MCP server, so the agent can search it instead of guessing at a flag, a limit or an exit code. It is public and read-only, and needs no account:

```bash terminal
claude mcp add --transport http reliant-docs https://docs.reliantlabs.io/mcp    # Claude Code
codex mcp add reliant-docs --url https://docs.reliantlabs.io/mcp               # Codex
```

For Cursor, add it beside `forge` in the same `mcpServers` object:

```json .cursor/mcp.json
{
  "mcpServers": {
    "forge": {"command": "npx", "args": ["-y", "@reliantlabs/forge", "mcp"]},
    "reliant-docs": {"url": "https://docs.reliantlabs.io/mcp"}
  }
}
```

The Forge server acts on your repository; the docs server only answers questions. [Search these docs from your agent](/getting-started/search-docs-from-your-agent) lists its tools and the setup for other clients.
