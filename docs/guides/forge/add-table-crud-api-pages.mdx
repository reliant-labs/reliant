You will add a `reviews` table to a Forge project. One marked proto message produces the migration, the five CRUD RPCs and their handlers, the data access code, typed React hooks, and list, detail, create and edit pages. After that you own every file it wrote.

Forge projects everything else from two inputs, the proto and the migrations; [Two sources of truth](/forge/concepts/two-sources-of-truth) explains the split.

## Before you begin

- A Forge project with a service and a web frontend. [Build a Go and React app with Connect RPC](/guides/forge/build-go-react-app-connect-rpc) creates `shop`, with a `catalog` service and a `Product` entity. This page continues from there.
- Forge v1.6 or later. Inside Reliant, run it as `reliant forge`. Check the version with `reliant forge --version` inside the project.
- No account. Every step runs locally.

<Steps>
  <Step title="Mark a message as an entity">
    Add the message to the service's proto with a `// forge:entity` comment directly above it. Leave out `id`, `created_at` and `updated_at`, because Forge adds them. A `deleted_at` field asks for soft delete, and a field named `<entity>_id` becomes a foreign key when an entity with that name exists.

    ```protobuf proto/services/catalog/v1/catalog.proto
    // forge:entity
    message Review {
      string product_id = 2;
      int32 rating = 3;
      string body = 4;
      google.protobuf.Timestamp deleted_at = 5;
    }
    ```
  </Step>
  <Step title="Preview the scaffold">
    ```bash terminal
    reliant forge scaffold --dry-run
    ```
    ```text
    ── Phase 1: entity births (// forge:entity markers) ─────────────
      ⏭️  Product: table "products" exists — marker inert; evolution is a new migration
      📋 would birth services.catalog.v1.Review → table "reviews" (migration)
            quintet: would inject 5 rpc(s) [CreateReview GetReview UpdateReview DeleteReview ListReviews] + 10 message(s)
    ```
    The marker on `Product` does nothing now, because its table exists. A message is born once. After that, you change its table with a new migration.
  </Step>
  <Step title="Run the scaffold">
    Bare `scaffold` writes the migration, adds the RPCs to the proto, and runs `generate` itself. It took about 7 seconds here.
    ```bash terminal
    reliant forge scaffold
    ```
    ```text
    ── Summary ───────────────────────────────────────────────────────
      entities birthed:    1 (services.catalog.v1.Review → reviews)
      managed fields:      3 declared on entity messages
      quintets completed:  1
    ```
    New files, from `git status` (the proto, `handlers_crud.go`, the hooks and the mocks were updated too):
    ```text
    db/migrations/20261120063312_create_reviews.up.sql
    internal/db/review_orm_gen.go
    internal/db/review_store_gen.go
    internal/db/review_repo_ext.go
    frontends/web/src/app/reviews/                 (page.tsx, new/, view/, edit/)
    frontends/web/src/components/dashboard-tiles/reviews_gen.tsx
    frontends/web/src/lib/nav-routes/reviews_gen.ts
    frontends/web/src/mocks/reviews_gen.ts
    db/grants/readonly/public.reviews_gen.sql
    ```
    The migration is ordinary SQL, and it is yours. Forge never edits it again:
    ```sql db/migrations/20261120063312_create_reviews.up.sql
    CREATE TABLE reviews (
        id TEXT PRIMARY KEY CHECK (id <> ''),
        product_id TEXT NOT NULL,
        rating BIGINT NOT NULL DEFAULT 0,
        body TEXT NOT NULL DEFAULT '',
        created_at TIMESTAMPTZ NOT NULL DEFAULT (now()),
        updated_at TIMESTAMPTZ NOT NULL DEFAULT (now()),
        deleted_at TIMESTAMPTZ
    );
    ALTER TABLE reviews ADD CONSTRAINT reviews_product_id_fkey FOREIGN KEY (product_id) REFERENCES products (id);
    CREATE INDEX reviews_product_id_idx ON reviews (product_id);
    ```
  </Step>
  <Step title="Read what the columns turn on">
    Behaviour comes from the columns in the applied schema, not from proto annotations:
    - `created_at` and `updated_at` are managed timestamps. Create stamps both, and Update stamps `updated_at` again.
    - With a `deleted_at` column, deletes are soft. `DeleteReview` sets `deleted_at`, and Get and List skip the row. The generated `db.ListAllReview` still returns it. To keep the column as a plain archive stamp, run `COMMENT ON COLUMN reviews.deleted_at IS 'forge:no-soft-delete'` in a migration.
    - Text columns get a free-text `search` filter, and `product_id` gets an equality filter. Both appear as fields on `ListReviewsRequest`:

    ```protobuf proto/services/catalog/v1/catalog.proto
    message ListReviewsRequest {
      int32 page_size = 1;
      string page_token = 2;
      optional string search = 3;
      optional string product_id = 4;
      string order_by = 5;
      bool descending = 6;
    }
    ```
    To filter on another column, add an `optional` field with that column's name. Forge wires it through the query, the hook and the list page.
  </Step>
  <Step title="Keep list filters optional">
    A filter field without `optional` cannot tell "no filter" from an empty value, so it never filters. `lint` rejects it. This is the output after removing `optional` from `product_id`:
    ```bash terminal
    reliant forge lint --conventions
    ```
    ```text
    ❌ conventions — 1 error
       ✗ proto/services/catalog/v1/catalog.proto:214 [forgeconv-list-filter-optional] ListReviewsRequest.product_id has no field presence: unset and "" are the same value on the wire, ...
          → a filter: mark it `optional` — `optional string product_id = 4;` — so unset means "no filter" end to end (Go pointer, TS `?:`, generated nil-guard). A required parameter (a parent or org id the handler insists on): declare it with `[(buf.validate.field).required = true]`
    ```
    [The rule's reference](/forge/linting/rules-conventions#forgeconv-list-filter-optional) covers the required-parameter case.
  </Step>
  <Step title="Verify the build, the gate and the shapes">
    ```bash terminal
    go build ./... && reliant forge lint --quiet
    ```
    ```text
    ✅ All 29 gating linters passed.
    ```
    `project shapes` lists each new symbol with its file and line:
    ```bash terminal
    reliant forge project shapes --grep Review
    ```
    ```text

    handler  CatalogService.CreateReview    internal/handlers/catalog/handlers_crud.go:107

    hook     useListReviews                 frontends/web/src/hooks/catalog-service-hooks_gen.ts:250
    ...
    ```
  </Step>
  <Step title="Test the behaviour">
    The first entity in a service gets a lifecycle test, `TestCRUD_Product_Lifecycle` in `internal/handlers/catalog/handlers_crud_test.go`. Later entities get request factories (`catalog.NewCreateReviewRequest`) but no test of their own, so copy that test for `Review`. This version also checks soft delete and the filter. It passed against a real Postgres that the test harness starts for you:
    ```bash terminal
    task test:short -- -v -run 'TestCRUD_Product_Lifecycle|TestReview_' ./internal/handlers/catalog/...
    ```

    To see the pages, run `reliant forge env up dev` and open `/reviews`.
  </Step>
</Steps>

## What this does not do

- **No access control.** Every generated handler requires a signed-in caller but does not check who it is. The comment above each one says `AUTHENTICATED, UNSCOPED`. To scope rows to their owner, read `middleware.GetUser(ctx)` in `handlers_crud.go` and filter on it.
- **No later schema changes.** The marker only works once. To add a column, write a new migration (`reliant forge db migration new`) and add the field to the proto.
- **`hard_delete` and the delete response's `deleted_at` are not wired.** The scaffold puts both fields in the delete messages, but at this forge version the generated handler ignores `hard_delete` and returns `deleted_at` unset.
- **The pages are starter code.** They prove the stack works. They are not a design. See [Generated code vs yours](/forge/concepts/generated-vs-yours).
