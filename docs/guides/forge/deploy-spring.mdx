You will deploy an existing Spring Boot app, with a Dockerfile, to [Reliant hosting](/hosting/overview) with a managed Postgres. Forge reads the Dockerfile and writes its declarations beside it. Spring needs more hand edits than other stacks, because the detector reads the port from the Dockerfile but does not read `pom.xml` or `build.gradle`: you add the database yourself. The detector output here is from Forge `v1.10.1-0.20261123064811-54313eead62f`.

## Before you begin

- Docker, and the app in a git repository with a root `Dockerfile` that builds on its own.
- Forge: `reliant forge` inside Reliant, or `npx -y @reliantlabs/forge@latest` anywhere else.
- A Reliant account with [app hosting billing](/hosting/overview#billing). A JVM doesn't fit the anonymous plan (below).

## What the Dockerfile must do

A deploy runs `docker build` on the Dockerfile alone, so build the jar inside it. A Dockerfile that only does `COPY target/app.jar` fails, because `target/` exists only on your machine:

```dockerfile Dockerfile
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY . .
RUN ./mvnw -q -DskipTests package

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /src/target/*.jar app.jar
RUN useradd -r -u 10001 app
USER 10001
EXPOSE 8080
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75"
CMD ["java", "-jar", "app.jar"]
```

The detector takes the port from `EXPOSE` and sets `PORT=8080` in the container. Spring Boot ignores `PORT` unless you map it: put `server.port=${PORT:8080}` in `application.properties`. Spring binds all interfaces by default. `MaxRAMPercentage` sizes the heap from the container's memory limit instead of the JVM's default quarter, which leaves room for metaspace and threads without being killed.

## Postgres: a JDBC URL

Hosting hands each environment's managed Postgres to the app as a URL in `DATABASE_URL` (`postgres://user:pass@host/db` form). Spring's datasource wants `jdbc:postgresql://host/db` with the user and password separate, and doesn't parse the URL form. The least code is a small `DataSource` bean that reads `DATABASE_URL`:

```java DatabaseConfig.java
@Bean
DataSource dataSource(@Value("${DATABASE_URL}") String url) {
    URI u = URI.create(url);
    String[] cred = u.getUserInfo().split(":", 2);
    HikariDataSource ds = new HikariDataSource();
    ds.setJdbcUrl("jdbc:postgresql://" + u.getHost() + ":" + (u.getPort() == -1 ? 5432 : u.getPort()) + u.getPath()
        + (u.getQuery() == null ? "" : "?" + u.getQuery()));
    ds.setUsername(URLDecoder.decode(cred[0], UTF_8));
    ds.setPassword(URLDecoder.decode(cred[1], UTF_8));
    ds.setMaximumPoolSize(5);
    return ds;
}
```

Then declare the database in each hosted env, as the detector does for other stacks:

```python deploy/kcl/prod/main.k (excerpt)
_db = forge.ManagedDatabase {name = "orders", runtime = forge.OnHosted {}}

_bundle = forge.Bundle {
    project = "orders"
    control_plane = forge.ControlPlane {}
    workloads = [
        _hosted(wl.api) | {env.DATABASE_URL = forge.DatabaseRef {name = _db.name}}
    ]
    databases = [_db]
    secret_provider = forge.HostedSecrets {}
}
```

The database's name may not be a workload's name (`api`).

## Migrations: on startup

Flyway (`spring-boot-starter-flyway` or `flyway-core`) and Liquibase run on application startup, against the same `DataSource`, before Spring starts serving, so you don't need a separate `migrate` job. With one replica that is safe; with more, both tools take a database lock, so the second replica waits. Keep migrations backward-compatible, because the old release serves while the new one migrates. If you'd rather migrate before the rollout, add a `migrate` job running `java -jar app.jar --spring.main.web-application-type=none` with a profile that exits after Flyway.

    ```python deploy/kcl/workloads.k (excerpt)
    resources = fw.Resources {
        cpuRequestMillicores = 500

    }
    ```

## Spring gotchas

- **OOMKilled at startup:** raise `memoryRequestBytes`, or lower `MaxRAMPercentage`. Never set `-Xmx` above the limit.
- **Probe failures during a slow start:** the TCP probe passes only once Tomcat listens. Give a large app more CPU rather than a longer timeout.
- **`Failed to determine a suitable driver class`:** the datasource never got a JDBC URL. See the bean above.
