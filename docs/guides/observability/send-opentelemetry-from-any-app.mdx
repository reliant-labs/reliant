By the end of this guide, an app that Forge did not build and does not deploy sends its traces, logs and metrics to Reliant, and you can read them with `reliant forge obs`. It can be in any language, on any infrastructure: you add an OpenTelemetry SDK and a few environment variables.

The variables are the standard OpenTelemetry ones, so there is no Reliant SDK to install. The token decides which organization and environment the data lands in.

## Before you begin

- A Reliant account in the organization the telemetry should belong to, with the `obs:write` permission to mint tokens. Owners and admins hold it.
- The `reliant` CLI v1.21.3 or later, which includes forge v1.6.1 ([install](/getting-started/installation)). Your repository does not need a `forge.yaml`.
- Your own terminal and browser. Ingest tokens are minted by a person, so this cannot be run by an agent or a CI job.

<Steps>
  <Step title="Sign in as yourself">
    ```bash terminal
    reliant forge cloud login
    ```

    This opens your browser and stores a credential for Reliant's control plane.
  </Step>

  <Step title="Register the environment and mint a token">
    From the root of your app's repository, name the environments and the project to create or reuse:

    ```bash terminal
    reliant forge obs init prod --project shop --service checkout-api
    ```

    In a repository with no Forge files, it asks before writing `deploy/envs/prod.yaml` (`--write-config` skips the question, `--no-write` writes nothing). Commit that file: every `obs` command reads the project from it.

    ```yaml deploy/envs/prod.yaml
    apiVersion: forge.dev/env/v1
    project: "shop"
    env: "prod"
    control_plane: {}  # Reliant's control plane
    observability:
      enabled: true
      destination: {token_from_control_plane: true}
    ```

    It then prints the ingest token's name, id and expiry date, followed by an `export` line for each variable. The token is shown once and expires after 90 days at most.
  </Step>

  <Step title="Set the variables where the app runs">
    Store the header as a secret in your deploy system, never in the repository, and set the rest beside it:

    ```bash terminal
    OTEL_EXPORTER_OTLP_ENDPOINT=https://otlp.reliantapi.com
    OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
    OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer <token>"
    OTEL_SERVICE_NAME=checkout-api
    OTEL_RESOURCE_ATTRIBUTES="deployment.environment.name=prod,service.namespace=shop,service.version=$GIT_SHA"
    ```

    Use the values `obs init` printed. Give each deployable its own `OTEL_SERVICE_NAME`. Set `service.version` to what you deploy, such as the git SHA or release tag: the issue list's "first seen in" and `obs check` both key on it. Keep `deployment.environment.name` equal to the env name you passed to `obs init`.
  </Step>

  <Step title="Add an OpenTelemetry SDK">
    Any SDK that reads the standard variables works. Zero-code instrumentation is the shortest path:

    | Language | Install | Run |
    |---|---|---|
    | Node.js | `npm i @opentelemetry/api @opentelemetry/auto-instrumentations-node` | `node --require @opentelemetry/auto-instrumentations-node/register app.js` |
    | Python | `pip install opentelemetry-distro opentelemetry-exporter-otlp && opentelemetry-bootstrap -a install` | `opentelemetry-instrument python app.py` |
    | Java or Kotlin | download `opentelemetry-javaagent.jar` | `java -javaagent:opentelemetry-javaagent.jar -jar app.jar` |
    | Go | `go.opentelemetry.io/otel` with `otlptracehttp` and `otelhttp` | wrap your handlers |

    For errors to become issues, failed requests must set the span status to error and record the exception. The auto-instrumentation above does this for unhandled errors. Export logs over OTLP (`OTEL_LOGS_EXPORTER=otlp`) only if nothing already ships the app's stdout, or every line arrives twice.
  </Step>

  <Step title="Check that telemetry arrives">
    Deploy the app with the variables set, send it some requests, then:

    ```bash terminal
    reliant forge obs status prod
    ```

    Before anything arrives, the env exists but is empty:

    ```text
    prod (cloud backend), 2026-11-20T08:28:39Z .. 2026-11-20T09:28:39Z
    no promotion on record
    telemetry: nothing received in the last 24h0m0s

    no service traffic in the range
    ```

    Once data arrives, the `telemetry` line shows when the newest log and span came in, and your service appears with its request rate, errors and p95. Then read the data itself:

    ```bash terminal
    reliant forge obs traces prod --errors
    reliant forge obs logs prod --severity error
    reliant forge obs issues prod
    ```
  </Step>

  <Step title="Rotate the token before it expires">
    Nothing renews a token. `list` marks one in its last 14 days with "expires soon: rotate it":

    ```bash terminal
    reliant forge obs tokens list prod
    reliant forge obs tokens rotate <token-id> --grace 24h
    ```

    `rotate` mints a replacement, and the old token keeps working for the grace period while you roll out the new header. `obs tokens create prod --name <label>` mints a separate token per cluster or CI system, and `obs tokens revoke <token-id> --reason leaked` cuts one off within minutes.
  </Step>
</Steps>

## What this does not do

- It does not build or deploy your app. The environment is registered as self-managed, and the platform never deploys there.
- There is no anonymous path. Reading telemetry needs a sign-in, and minting tokens needs a person with `obs:write`. A CI job can read with a token that has `obs:read` ([credentials](/hosting/observability/forge-obs#credentials)).
- With no deploy recorded, `obs check` judges a new `service.version` from the first time telemetry showed it, and marks the result `marker INFERRED`. A canary or slow rollout moves that moment.
- A monitoring-only environment gets the built-in alerts (new and regressed issues, quota) and your organization's alert receivers. Per-environment alert rules come from a Forge-deployed environment's declaration ([dashboards and alerts](/hosting/observability/dashboards-and-alerts#alerts)).
- The ingest token is a server-side secret. Never ship it in a browser bundle or a mobile app.

## Troubleshooting

<AccordionGroup>
  <Accordion title="telemetry ingest tokens are minted, rotated and revoked by a person, not a machine credential">
    `obs init` ran with an agent's or a pipeline's credential. Run it yourself in your own terminal after `reliant forge cloud login`. The refused run may still have registered the env and written `deploy/envs/prod.yaml`; running it again reuses both and only mints the token.
  </Accordion>
  <Accordion title="minting an ingest token needs a person who is a member of the organization holding the obs:write permission">
    Your account lacks `obs:write`. Ask an owner or admin of the organization to grant it, or to run `obs init` for you.
  </Accordion>
  <Accordion title="telemetry: nothing received in the last 24h0m0s">
    Check that the app's process actually has the variables, the protocol is `http/protobuf`, and the header reads `authorization=Bearer <token>` with no extra quotes. Check that the token is not revoked (`obs tokens list prod --all`).
  </Accordion>
  <Accordion title="env prod is declared in deploy/kcl/prod/main.k">
    That env is deployed by Forge, which wires its telemetry for you. For a token for an app outside Forge's deploys, use `reliant forge obs tokens create prod`.
  </Accordion>
</AccordionGroup>
