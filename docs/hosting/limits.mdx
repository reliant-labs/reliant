This page gathers the limits of [Reliant hosting](/hosting/overview) and of a no-account `--claimable` deploy in one place, so you can decide before you build whether your app fits. Each section points at the page that explains the behavior in depth. If a number here disagrees with what a deploy prints, trust the deploy: the numbers come from the platform's own plan definitions, and `forge env deploy <env> --plan-only` and `forge env shape <env>` print the ones that apply to your environment.

Nothing here is a promise of capacity beyond what is stated. Reliant is young, and where a limit has no declared value the page says so instead of guessing.

<Tip>
Live availability of Reliant's services (the API, hosted deploys, static hosting, identity, the LLM gateway and these docs) and the history of past incidents are on the public status page, [status.reliantlabs.io](https://status.reliantlabs.io).
</Tip>

## Deploy with no account: `--claimable`

`forge env deploy prod --claimable` publishes under a temporary anonymous identity and prints a live URL and a claim link ([the walkthrough](/forge/deploy-without-an-account)). The anonymous plan is deliberately small, and a deploy that does not fit is refused before anything is built, with each offence named.

| Limit | Value |
|---|---|
| Lifetime | Serves for **72 hours** from the first deploy attempt, then is suspended (offline, data kept), then deleted **7 days** later: 10 days at most. A redeploy does not extend it. Claiming stops the clock |
| Shape | One static site, **or** one service with its migration job, one managed Postgres, and an optional static site |
| Refused | Workers, cron jobs, a second service or database, custom domains, remote builds, object storage (`forge.Bucket`) |
| Service size | 1 replica, **125m CPU and 128 MiB memory** (request and limit, no burst), 512 MiB scratch disk, no persistent volume |
| Database | One Postgres server at 125m CPU and 128 MiB memory, **256 MiB** of data (on a 1 GiB volume), 10 connections, **no backups** |
| Static site | One site, **100 MiB** stored (the live copy, its archive and the previous release's archive each count), **2 GiB** of traffic per calendar month |
| Image registry | 1 GiB for the pushed image |
| Outbound internet | **None** for an unclaimed service: payments, webhooks, email, model APIs and DNS outside the cluster all fail. A static site is unaffected, because its requests come from the browser. Claiming ends the block |
| Starts | Per network (IPv4 /24, IPv6 /56): 3 an hour and 10 a day. Per device: 3 live deploys at once and 20 redeploys a day. Platform-wide: 30 starts an hour, 200 unclaimed deploys running compute at once. No coarse network may take more than 20% of an hour's starts. A start also carries a small proof of work that gets harder as the hour fills |

A refusal is a non-zero exit with a stable `reason` in the `--json` document, and forge never retries on its own: the table of exit codes is in [Deploy without an account](/forge/deploy-without-an-account#when-its-refused).

<Note>
The 72-hour clock starts with the first attempt, not the first success. `forge env status prod --claimable` prints when it started and when it ends.
</Note>

## The free plan

Each person's free hosting organization (one per person, see below) can publish static sites for free with no hosting billing, with these limits ([billing details](/hosting/overview#billing)):

| Limit | Value |
|---|---|
| Organizations | **One per person**: one organization its founder owns, their personal organization by default, movable once every 30 days. Static sites in their other organizations without app hosting billing are queued |
| Static sites | **No limit** on the number of sites in that organization. Each environment's site is a site of its own, so `staging` and `prod` both deploy free |
| Storage | **1 GiB** per site and **10 GiB** in total across the organization's sites, retained releases included. A release is kept three times (live, its archive, the previous release), so a release of about 340 MiB or less fits a site |
| Traffic | **10 GiB** per calendar month (UTC) for the organization. The owner is told at 80% and 100%, and past the limit the site answers `429` until the month rolls over |
| Static headers | A site can add response headers with a `_headers` file, but not `Cache-Control`, `Set-Cookie`, `Strict-Transport-Security` or `Content-Type`: the platform owns those |
| Static redirects | A `_redirects` file declares at most **1,000** rules, **2,048** characters per line and **64 KiB** per file. Statuses 301, 302, 307 and 308 only, with exact paths or a trailing `/*` and `:splat`. No rewrites (`200`), proxying or conditions. A line the platform cannot follow fails the deploy and is named in the error. An unclaimed site may redirect only within its own hostname |

## What needs billing

Everything that runs a process or a database needs [app hosting billing](/hosting/overview#billing), a pay-as-you-go agreement an organization owner or admin authorizes under **Settings → Billing**. That covers any hosted service, worker, job or managed Postgres, and static sites in any organization other than your free hosting one. Until billing is on, such a deploy is **queued, not refused**: forge builds and records the release, holds it, and exits with code **7**, printing a billing link. Nothing needs re-running once billing is on.

Hosted workloads are held to a fixed shape: 4 GiB of memory per vCPU, in 125m steps (125m with 512 MiB, 250m with 1 GiB, 500m with 2 GiB). One deploy may ask for at most 2,000m of CPU, 8 GiB of memory and 50 GiB of storage in total, summed over every workload and replica. A deploy over that is refused, not queued. [Inside Reliant hosting](/deep-dives/inside-reliant-hosting#capacity-shape-and-the-limits-block) explains why.

Observability has its own allowance: 10 GiB of ingestion per organization per month, then billed per GB. See [Observability billing](/hosting/observability-billing).

## What hosting does not do

| Not available | What to do instead |
|---|---|
| **Hosted cron-kind workloads.** A `kind = "cron"` workload fails the render on hosted, because scheduled pods are not metered yet | A worker that runs its own schedule (`forge scaffold worker <name> --kind cron`) is an ordinary worker and does run hosted |
| **Operators, CRDs and RBAC.** There is no Kubernetes API access on shared machines | Bind that workload to your own cluster and keep the rest hosted |
| **Sidecars, volumes and pod-level overrides.** The platform builds the pod itself | Same |
| **Outbound traffic other than TCP 80 and 443** to public addresses. SMTP, an external Postgres or Redis and any other port are unreachable from a hosted workload | Use a provider's HTTPS API, or run that workload on your own cluster |
| **Connecting to the managed database from your laptop.** It is reachable only from inside its environment | `forge db query` reads it with audit |
| **A separate origin for each service.** Every service and worker runs in the one `api` workload, reached at `/_api` on the site's host | Split a service out only when no browser calls it |

The full list, with the reason for each, is in [What hosting does not run](/hosting/overview#what-hosting-does-not-run) and [Inside Reliant hosting](/deep-dives/inside-reliant-hosting#limits-and-what-it-does-not-do).

## Deploying a Next.js app

A hosted frontend is served as plain files from a CDN, so a Next.js app must build as a **static export** (`output: "export"`, into `out/`). That rules out anything that needs a server at request time: a dynamic `[slug]` route without `generateStaticParams()`, server actions, middleware, `cookies()` and `headers()`, a route handler that answers dynamically, and `next/image` without `unoptimized`. `forge lint --static-export` names each one with its file and line, and `npm run build` is the authority.

A Next.js app that does need a server is not stuck. It deploys as a **workload** instead of a static site: give it a `Dockerfile` that runs `next start` (with `output: "standalone"`), and adopt it with `forge project new --in-place --kind app`. That is a hosted service, so it needs [billing](#what-needs-billing), and an anonymous deploy must fit the 125m / 128 MiB [claimable service](#deploy-with-no-account---claimable), which a Next.js server may well exceed: if it does, sign in and deploy to your own account. [Deploy a Next.js app with Reliant Forge](/guides/forge/deploy-nextjs-static) covers both shapes.

## Telemetry retention

Hosted telemetry is retained for these defaults. They are the platform's, and the billing editor shows them read-only; changing your spend cap does not change them.

| Data | Retention |
|---|---|
| Logs | TRACE/DEBUG: 3 days; INFO and WARN and above: 30 days |
| Traces | 30 days |
| Metrics | 30 days; the one-minute query rollups behind long charts: 395 days |
| Profiles | 24 hours raw; 30 days aggregated |
| Browser errors | 30 days |
| Session replay | 14 days by default; 1 to 30 with `forge.ObservabilityRetention {replay_days = N}` |
| Product events | 90 days by default; up to 400 with `product_events_days`, bounded by the plan (90 without a paid compute subscription) |

Expiry is handled by database TTL processing, so data can outlive its boundary briefly. There is **no telemetry for a claimable deploy**: monitoring requires signing in, so claim the deploy first. [Where the telemetry goes](/hosting/observability/where-it-goes) and [Observability billing](/hosting/observability-billing) have the rest.

## Request and build limits

These are the numbers an app's operator usually asks about, and where a value is not declared we say so.

| Limit | Value |
|---|---|
| Build time | A build run by the platform's build service is stopped after **15 minutes** (900 seconds). `forge env deploy` builds on your machine by default, so this applies only to platform builds, and a claimable deploy refuses remote builds entirely |
| Static release size | One release may be at most **5 GiB** as pushed on a paid plan (raised by support, with a platform ceiling of 20 GiB); the free tier's per-site guard is 1 GiB, with 10 GiB stored across the organization's free sites |
| Image pull | Hosted workloads pull only from Reliant's registry. forge copies a third-party image into it by digest when a release is cut |
| Request timeout and request body size for a hosted service | **Not declared as a published limit.** Do not build on a particular value, and keep long work out of the request path |

<Warning>
The request timeout and maximum request body for a hosted service are not set as a documented platform contract today. Treat any single request as something that must finish in seconds, and move long work to a [worker](/guides/forge/background-worker-cron-job).
</Warning>
