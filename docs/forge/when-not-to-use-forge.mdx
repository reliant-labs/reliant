Forge is opinionated about the common path, and a tool that says where it does not fit is easier to trust. This page lists the cases where we would tell you to use something else, or to use only part of Forge. Forge is [usable piece by piece](/forge/migrate-an-existing-app) in any repo, so several of these have a partial answer: the part of Forge that does fit, without the part that doesn't.

## You don't want generated code in your repo

Forge writes real files into your repository and regenerates some of them: the ORM, the Connect handlers' stubs, the typed frontend hooks, the mocks. Everything generated is marked, never edited by hand, and kept beside files you own, and [the split is explicit](/forge/concepts/generated-vs-yours). But if you would rather hand-author everything, or your review process cannot absorb generated diffs, the ownership model is overhead. You can still use the pieces that generate nothing: `forge lint`, the migration-safety checks, [deploys of an app Forge never compiled](/guides/forge/bring-existing-app-any-language), and monitoring.

## You need a REST-first public API

Connect RPC is Forge's native surface: your proto file is the API, and browsers call it as plain HTTP and JSON. REST-shaped URLs are available through [Vanguard transcoding and generated OpenAPI](/guides/forge/rest-and-openapi-from-connect), but they are a projection of the proto. If your contract is a hand-shaped OpenAPI document that clients already depend on, with its own URL design, you will be working against the grain. Keep your framework's router and deploy it as a [Dockerfile app](/guides/forge/bring-existing-app-any-language) instead.

## Postgres isn't your database

Forge's schema, ORM, migration linter, seeds and managed database all assume Postgres. MySQL, SQLite and non-relational stores are not supported for the generated stack, and Reliant hosting provisions only Postgres. An app you bring from a Dockerfile can talk to anything over HTTPS, but a hosted workload reaches the internet only over TCP 80 and 443 ([the full list](/hosting/limits#what-hosting-does-not-do)), so a database on another port is reachable only from a workload bound to a cluster you operate.

## Your backend isn't a container

A service deploys as an image, and a frontend as static files. A function-as-a-service model, a binary you copy onto a VM, or a platform that insists on its own build packs does not map onto Forge's deploy. Static sites are the exception that proves the rule: they ship as files, not an image.

## You need a managed platform feature Reliant hosting doesn't have

Reliant hosting is deliberately small, and the [Limits page](/hosting/limits) is the whole list. The ones that most often decide the question are no hosted cron-kind workloads (a worker that runs its own schedule does run) and no operators or CRDs. Each has a way out: bind that one workload to a cluster you operate and keep the rest hosted. If you need any of them across the board, and don't want to run a cluster, another host is the better choice.

## You want a framework you'll outgrow and replace

Forge holds structure for the life of the project: the layout, the lint rules, the migration discipline and the generated seams are meant to stay. If you want a scaffold you will rip out in a month, a template repository is lighter and will not keep opinions in your way.

## You need a compliance attestation

The docs do not describe a compliance certification for Reliant hosting. If a contract requires an attestation such as SOC 2, settle that before choosing the platform. The Forge framework itself is Apache-2.0 and runs against a cluster you operate, without Reliant hosting.
