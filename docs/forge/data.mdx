Data lets you look at the rows in an environment's database without opening a SQL client or asking an agent to run a query. It is a viewer, not an editor: nothing in it writes, and fixes to data belong in migrations or your application code.

## Where to find it

Choose **Data** in the project sidebar. It follows the environment control in the top bar, so switching from `prod` to `staging` keeps the table you had open when the other environment has it. With all environments selected it asks you to choose one. Every view is in the URL (database, table, filters, sort, page), so you can send a colleague a link to exactly the rows you are looking at.

## What you see

An environment can have several databases, a managed one and any you declared as external, and a selector at the top lists them with their access policy. A rail on the left lists the tables and views you may read. Choose one and you get a grid.

- **Filters.** Add a condition per chip: a column, an operator that fits its type (text columns get `LIKE` and `ILIKE`, nullable ones get `IS NULL`) and a value. Conditions are combined with AND. Values are sent as text and Postgres converts them, so `42`, `2026-01-31` and `true` all work, and a value it can't convert comes back as the server's own error.
- **Sort and columns.** Click a header to sort ascending, then descending, then back to the default. The column picker hides what you don't need.
- **Paging.** 25, 50 (the default), 100, 200 or 500 rows per page. The total starts as the planner's estimate (about `1.2k`), and you can ask for an exact count, which is capped at `10,000+`.
- **A row's page.** A table with a primary key links each row to a page showing every column. A foreign key is a link to the row it references, and a **Related** section lists the tables whose foreign keys point at this row, each with a count and a link to its grid filtered to that row. That is the quickest way from a user to everything that is theirs.
- **Save as a panel.** A filtered, sorted view can be saved as a panel on one of your dashboards, so a question you ask often becomes a chart or table you can find again.

## Who can read what

The browser reads through the same read-only role as [`forge db query`](/hosting/managed-postgres#read-the-data-safely). Postgres itself keeps that role out of every write and out of any column marked `forge:secret`, so a secret column is neither listed nor readable, and a table the role can't select looks the same as one that doesn't exist.

You need the organization's `db:query` grant, which owners and admins hold. Whether a read also needs a reason is the environment's `data_access.db_query` policy, which you can set in the environment's KCL:

| Policy | Effect |
|---|---|
| `open` | Anyone who may query can browse. The default for a local or ephemeral environment. |
| `audited` | A person with the grant confirms the environment and gives a reason, once per browser tab session. The default for every other environment. |
| `deny` | Nobody can. The page still opens and says why it shows no data. |

In an audited environment each read writes an audit record with the reason, and opening a database also appears in the **Activity** feed with who opened it and why. Reads are rate-limited per person, so a very wide Related section may ask you to wait a moment. An audited environment admits a signed-in person with the grant, never a machine credential.

## When it can't show data

The page says what is wrong rather than showing an empty grid: you lack the grant, the environment denies reads, the environment hasn't recorded what it deploys yet (deploy once), the database can't be reached, or the control plane serving you doesn't have the data browser configured yet. In that last case the page says so and points you to `forge db query`, which works in the meantime. The browser needs the control plane to be able to reach the database: managed databases on Reliant hosting are reached through the platform, and an external database needs a route declared for it ([Managed Postgres](/hosting/managed-postgres#bring-your-own-database)).

## Limits

- **Availability follows the platform.** The browser needs the control plane serving your organization to have direct database reads set up for the environment. When it doesn't, the page says it can't browse data yet, and `forge db query` is the way to read rows until it can.
- It is read-only. There is no editing, inserting or deleting.
- It shows tables and views, never what the read-only role can't select.
- It has no SQL box. For an arbitrary read-only statement use `forge db query <env> "<sql>" --confirm-env <env> --reason "<why>"`.
- Database size, connections and backup status aren't shown here yet; see [Services](/forge/services#services-workers-jobs-sites-and-the-database).
