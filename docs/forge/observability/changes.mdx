</Info>

A **change** is one piece of app behavior that can differ between people without a deploy. The same object covers three jobs:

- **Everyone**: one variant for every caller. This is remote config.
- **Some people**: one variant for a stable percentage of an audience. This is a gradual rollout.
- **Compare versions**: a stable percentage split across variants, measured against one success metric. This is an A/B test.

Before any of those, you can **preview** a change to teammates, who see their chosen variant and are never measured. **Stop** is the kill switch: everyone gets the default, previews included. One change moves from preview to an experiment to everyone without being recreated, and without changing a call site.

Cohorts are sticky. A change names its unit, the thing that stays together: a `user` (the signed-in user id), an `account` (an org or team id) or a `visitor` (an anonymous id your app holds with consent). The same unit always gets the same outcome, and raising a percentage only adds units: lowering it and raising it again brings back the same ones. An audience is optional and is one attribute matched against a list of values, such as `plan` in `pro, team`.

## Declare a change

Your code decides what a change can be. Write it once in `changes.yaml` at the project root (forge v1.10.0 or later):

```yaml
version: 1
changes:
  new-checkout:
    description: Shorter checkout flow
    type: bool # bool | string | number | json
    default: control # a variant name
    variants:
      control: false
      treatment: true
  hero.copy:
    type: string
    default: a
    variants:
      a: Ship faster
      b: Deploy in one command
```

Each change has a `type` (`bool`, `string`, `number` or `json`), one to 32 named `variants` whose values have that type, a `default` that names one of them, and an optional `description` the console shows. The default applies when the change is off and to everyone its delivery does not select. A project can declare up to 200 changes.

Run `reliant forge generate`. It writes typed accessors: `internal/changes/changes_gen.go` for a Go backend, and `src/lib/changes_gen.ts` for each frontend that depends on `@reliantlabs/forge-web-runtime`. An invalid file fails `forge generate` and every release build, with each problem and its line number.

Every release carries the declaration. The control plane uses it to refuse launching, ramping or rolling out a variant that the environment's current release does not declare. You can still draft, preview and stop a change before the release that declares it ships.

## Evaluate it in your code

Evaluation is local: the app reads the environment's snapshot and decides without a network call per request. It never errors. A change the snapshot does not carry, or a snapshot that could not load, gives you the default written in your code.

In Go, open one store per process. On Reliant hosting, `FORGE_CHANGES_FILE` (`changes.EnvFile`) names the snapshot file:

```go
store := changes.OpenFile(ctx, os.Getenv(changes.EnvFile), changes.Options{})
defer store.Close()

ec := changes.EvalContext{TargetingKey: userID, Attributes: map[string]string{"plan": plan}}
if changes.Bool(store.Evaluate(ctx, "new-checkout", ec), false) {
	// the new checkout
}
```

`String`, `Float64` and `Decode` read the other types. The generated accessor does the same in one call: `appchanges.NewCheckout(ctx, store, ec)`. If you evaluate through OpenFeature, register the provider from `forge/pkg/changes/openfeature` instead and keep your call sites vendor-neutral:

```go
of.SetProviderAndWait(forgeof.NewProvider(store))
```

In the browser:

```ts
import { loadChanges, changeBool } from "@reliantlabs/forge-web-runtime";

const changes = await loadChanges(); // GET /_forge/changes.json; never rejects
if (changeBool(changes.evaluate("new-checkout", { targetingKey: userId }), false)) {
  // the new checkout
}
```

`changeString`, `changeNumber` and `changeJson` read the other types. With OpenFeature's web SDK, use `OpenFeature.setProvider(forgeChangesProvider(await loadChanges()))`.

Each useful evaluation records the [product event](/forge/observability/product-analytics) `flag_evaluated`, with the change, its variant, run, unit and reason, once per unit, change, run and variant per day. That is what an experiment's results count. Measure the outcome with your own events (`observe.Track`, `track()`).

A local `forge env up dev` stack serves no snapshot, so every change evaluates to its default. To try a variant locally in Go, point `FORGE_CHANGES_FILE` at a snapshot file and edit it.

## How changes reach your app

On Reliant hosting the platform writes each environment's snapshot for you whenever a change moves:

- A static site serves it at `/_forge/changes.json` on its own origin. A page reads it once, so a new revision applies on the page's next load and a treatment never switches mid-interaction.
- A hosted backend reads it from the file `FORGE_CHANGES_FILE` names and re-reads it every 10 seconds.

Stop takes effect as fast as that refresh.

## Run a change

Run changes from the **Experiments** page of the [Forge console](https://forge.reliantlabs.io), one per app, under **Analytics** in the project sidebar. If your sidebar does not list it yet, open `/forge/p/<app>/experiments`. It lists each change with its environment, mode and share, and lets you draft, preview, launch, ramp, roll out and stop one.

An agent can do the same with the [`list_changes`](/reference/tools#list_changes), [`get_change`](/reference/tools#get_change) and [`manage_change`](/reference/tools#manage_change) tools, as you and with the same audit trail. Every move is recorded with who made it and how it was approved.

A person approves production. In a protected environment (prod), launching, ramping up and rolling out need either a console session or a one-time code emailed to the person the credential acts for. Stop, ending a run and ramping down never wait for anyone. An API token needs the `changes:write` scope to draft, preview and stop, and `changes:launch` to launch, ramp, roll out and end a run; grant them in [Settings → API tokens](https://forge.reliantlabs.io/settings/tokens).

## Read the results

Each experiment run has a readout, on the change's page or from the agent tool [`change_results`](/reference/tools#change_results). It is built from your product events:

- **Who counts.** Units are counted in the variant they were assigned, whether or not they saw it (intent-to-treat).
- **One success metric.** The metric is binary: did the unit send a given event within a window after assignment, 168 hours unless you set another. Units whose window has not closed are pending, never counted as non-converters.
- **A sample-ratio check.** If the variants' sizes do not match the planned split, assignment is broken and no effect can be trusted.
- **Intervals.** Each variant's conversion rate, and each treatment's lift over the control, comes with a confidence interval at a 0.05 significance level.
- **A verdict.** No data, sample-ratio check failed, inconclusive (with the reason), treatment better or treatment worse. A result stays inconclusive until every variant has a minimum sample, 100 units unless you set another.

Decide once, at the sample size you planned, not at the first significant look. Once the run ends, or the change leaves experiment mode, the readout is final and its numbers stop moving.

## What it does not do

These are outside the first version of Forge Changes:

- no automatic ramps, and no automatic stop on a metric
- no segment query language: an audience is one attribute and a list of values
- no mutual exclusion layers between experiments
- no sequential testing
- no traffic splitting at the load balancer
