Nothing on this page means your app is free of vulnerabilities, and a page that says "not scanned" means exactly that: unknown, not clean.
</Warning>

A software bill of materials (SBOM) is the list of every package inside something you ship: the operating-system packages in a container image, the Go modules in a binary, the npm packages behind a frontend. A vulnerability scanner matches that list against a database of known advisories (CVEs and GitHub security advisories) and reports which of your packages are affected. New advisories are published every day against software nobody changed, so the useful question isn't only "was it clean when I shipped it" but "is what's running now still clean".

## How it works

When forge cuts a release, it generates a CycloneDX SBOM for every artifact the release contains, with a pinned, checksum-verified copy of syft, and records the SBOM's digest on the release as evidence. The SBOM is not part of the release's identity, so adding one never changes a release's digest. For an environment on Reliant hosting, forge uploads each SBOM to the control plane, which re-derives its digest, stores it, scans it with grype in a sandboxed worker (an SBOM is untrusted input), and rescans the SBOMs of deployed releases every day against its own copy of the vulnerability database. The control plane's findings are the record.

What the SBOM is made from depends on the artifact. An image forge built, or a prebuilt image pinned by digest, is read from the image, so it covers OS packages and language packages in every layer, in any language. A Go binary is read from its build info. A static site has no package metadata in its bundle, so its SBOM is made from the frontend's lockfile, excluding dev dependencies. It says **from lockfile**, and it lists what the site depends on, which can be more than the built bundle ships.

An environment's findings are those of the release in its newest promotion. Findings are tracked per environment, so Reliant can tell you when a vulnerability was first seen and when it was resolved.

## Where to find it

In the project sidebar, open **Security**. **Vulnerabilities** is the list, and **SBOMs** shows, for each release the scoped environments run, every artifact, where its SBOM came from (image, registry image, binary, lockfile or CI), its format and size, and how far its scan got. The environment control in the top bar scopes both pages, and the Vulnerabilities page can also be pointed at a specific release.

## What you see

The page opens with severity counts: critical, high, medium, low, negligible and unknown. Below is one row per advisory and package, most severe first, then known-exploited first. A row shows the advisory id, its severity, the affected package and version, whether a fix exists and which versions fix it, and where it runs. Filters (minimum severity, fixable or not, known-exploited only, include exempt findings) live in the URL, so a filtered view can be shared.

Opening a row shows the advisory's description and references, its CVSS score, its EPSS score (the probability of exploitation in the next 30 days) and whether it is on CISA's Known Exploited Vulnerabilities (KEV) list. It lists the releases and artifacts that contain it, when it was first seen, and the history per environment. If you have declared an exemption for it, that appears with its reason and expiry, and **Gate verdicts** shows what each promotion's `vuln_gate` decided about it (pass, warn, block or overridden) and in which mode.

The page never shows "no vulnerabilities" unless that is proven: every artifact has an SBOM, its newest scan succeeded, and the database was current. Otherwise it says what state it's in:

| State | Meaning |
|---|---|
| Not scanned | A release has no SBOM, for instance one cut before this feature, or one whose SBOM could not be generated. Unknown, not clean. |
| Scan pending | The SBOM is stored and its first scan hasn't finished. |
| Scan failed | The newest scan failed. The previous successful scan's findings are shown, with when it ran. |
| Stale database | The newest scan used a vulnerability database past its freshness bound. Advisories published since are missing, so this is not a clean bill. |
| Nothing deployed | The environment has no release yet. |

## What is live and what is coming

| Piece | Status |
|---|---|
| `reliant forge ci vuln-scan` (govulncheck for Go, `npm audit` for frontends) over your source tree, as a CI gate | Live. It stores nothing and doesn't read an SBOM. |
| The `vuln_gate` policy in an environment's KCL (`forge.VulnPolicy`) | Declared and recorded in the release, but nothing evaluates it yet, so it blocks no deploy today. |
| SBOM per artifact at the release cut, scanning, `forge vuln` commands, `vuln_gate` as a real gate | In review in forge, graded warn-first: a project below the release that introduces the gate sees "would block" and nothing is blocked. |
| Control-plane storage and scanning of SBOMs, the read API, and the daily rescan | Partly merged (the API definition and the findings store); recording, scanning, the read API and the rescan are in review. |
| The Security pages in the Reliant app | In review. Until a control plane serves findings, the page says it doesn't report vulnerabilities yet and that nothing there means your project is clean. |
| **Patch** and **Patch with agent** | Coming. The buttons are planned: Patch would run a deterministic dependency bump and open a pull request, and Patch with agent would hand a failing build to an agent. Neither automates patching today. |

When the rollout lands, a project does not need setup: SBOMs are generated at every cut. For now, plan on the [source-tree scan](#run-the-scan-you-have-today) and treat the pages above as preview.

## Run the scan you have today

```bash
reliant forge ci vuln-scan
```

This runs govulncheck over every Go module and `npm audit` over each frontend, and fails when a Go advisory your code actually calls, or an npm advisory of high or critical severity, is found. It fails rather than pass if a scanner can't run. An advisory with no fix that can't reach your code can be accepted in `forge.yaml` under `ci.vuln_scan.exemptions`, by its `GO-` or `GHSA-` id, with a reason and an expiry date. It is one of the checks `reliant forge ci gate` runs, which a scaffolded project's `task ci` wraps. See the [CLI reference](/reference/cli#reliant-forge-ci-vuln-scan).

## Who can read findings

A list of exploitable vulnerabilities is an attack map, so reading findings needs its own `vuln:read` grant in your organization, or for the one environment. No deploy permission implies it, so the CI token that records releases can't read findings unless it was minted with that scope. Every read is scoped to your organization, and a project outside it looks like it doesn't exist.

## Limits

- Scanning reads **SBOMs per release**. A package that isn't in a release's SBOM can't be reported, and a runtime dependency installed after the build isn't seen.
- A scan is only as current as its database. The control plane rescans daily, and shows a stale database as a state, never as clean.
- A lockfile SBOM for a static site overstates the bundle by including build-time packages.
- Reliant hosting reads vulnerabilities for its own environments. A self-hosted environment is judged by forge on your machine, not by the control plane.
- A scan finds known advisories. It doesn't find bugs in your own code.
