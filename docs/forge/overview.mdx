Forge is Reliant's framework for building, running and deploying software. Where Reliant is the harness, the agents, workflows and machines that do the work, Forge is the foundation they build on: the Go and React app itself, with the tests, deploys and monitoring that make it something you can run in production rather than a demo.

A forge project holds Go services (Connect RPC, callable from a browser as plain HTTP+JSON), background workers, jobs, Kubernetes operators and CLIs, plus Next.js, Vite or Expo frontends and plain static sites. From the first commit it has a local dev stack that comes up with one command, a Postgres schema with generated data access, structured logs, traces and metrics on every boundary, secrets handling, linters, tests, CI, and `dev`, `staging` and `prod` environments, with the last two already set up to deploy to Reliant hosting.

Ready to try it? The [Forge quick start](/forge/quick-start) goes from a prompt to a deployed URL.

## Why a framework, and why this one

An agent that writes an app from scratch has to invent everything around the code too: how it is configured, how it is tested, how it ships, how you find out it is broken. Each of those inventions is a place for the result to be subtly different from the last app, and a place for the agent to be confidently wrong. Forge removes the invention. The structure is the same in every project, the commands are the same, and the production practices are already in place, so an agent (or you) spends the effort on the part that is specific to your app.

It keeps that structure by regenerating the plumbing (API stubs, data access, typed config, frontend hooks, dashboards) from two inputs you own, your protobuf API and your SQL migrations. It never touches the files where your logic lives, so regenerating is always safe. [Project anatomy](/forge/project-anatomy) explains which files are which.

Forge is built to be driven by an agent. Ask Reliant to "build me an app that…" or start the **Build an App** workflow, and the agent uses the same commands a person would. The binary describes itself, so an agent asks it rather than guessing: `forge project capabilities` lists every command, and `forge skill list` the playbooks that ship with it.

## What you get

### Production defaults from the first commit

Structured logs, traces and metrics on every boundary, health probes, graceful shutdown and secrets kept out of git are not features you add later; they are in the scaffold. Linters check whole classes of problems, from architecture and migrations to generated-file drift, and `forge lint` is the same gate your CI runs. Tests are generated alongside the code, including a CRUD lifecycle test that runs against a real Postgres. The day-to-day loop is in [Adding a feature](/forge/adding-features).

### Environments you declare, releases you build once

Every place the app runs is an environment, declared as code under `deploy/kcl/`. A new project has `dev` on your machine and `staging` and `prod` on Reliant hosting. `forge env deploy` builds your artifacts once, cuts an immutable release, shows you a plan of what will change, and applies it only after you approve. Promoting to production ships the exact release staging ran, with `forge env deploy prod --from staging`, so what you tested is what goes live. [Environments & deploys](/forge/environments-and-deploys) covers releases, plans, rollback and deploying to a Kubernetes cluster you run.

### Hosting on Reliant

Publishing is one command, with no cluster, registry or DNS to arrange first. Reliant hosting runs your services, workers and jobs, gives the app a managed Postgres, publishes frontends as static sites behind a CDN, gives everything a hostname, and supports [custom domains](/forge/custom-domains) and managed [secrets](/forge/secrets). A project that is only a static site, such as a landing page, can be published on the free static tier without a compute plan. Anything that runs a process needs a Reliant Compute plan; see [Hosting on Reliant](/forge/hosting) for what is hosted, what is not, and how a deploy waits on billing, and the [pricing page](https://reliantlabs.io/pricing) for current plans and prices.

### Observability without configuration

An app deployed to Reliant hosting reports on itself from its first deploy: generated dashboards for every service and frontend, default alerts, browser error tracking with source maps, and logs, traces and metrics linked to each other. Locally, `forge env up` runs the same stack, so what you see in development is what you see in production. After a deploy, `forge obs check <env>` judges the release against the one before it and exits non-zero when it made things worse, which is the signal an agent or a CI job needs to know whether to roll on or stop. See [Observability](/forge/observability).

### Static sites, with or without a backend

A landing page, docs site, SPA or PWA with no backend is a complete forge project: one static frontend, dev, staging and prod environments, and no server to run. An existing Vite or Next.js app can be adopted in place with `forge project new --in-place --kind site`. Agents can load the `deploy/static-site` skill for the details.

## How Forge and Reliant fit together

Reliant's cloud runs your agents; a machine you choose, your computer or a Reliant cloud machine, runs their tools; and Forge is what they are building and running there. The Forge CLI ships inside the `reliant` binary, so `reliant forge …` works wherever Reliant does, signed in as you, and agents' shells have it already. See [Forge through Reliant](/cli/forge) for what that gives you.

The two products meet in a few places. The **Build an App** workflow scopes an app with you and scaffolds it as a Forge project, and **Move to Forge** ports an existing codebase into one a component at a time. The **Apps** and **Observability** areas in the Reliant sidebar show the releases, environments, logs, traces, dashboards and alerts of the Forge projects you deploy. And a [workflow](/workflows/overview) can call a deployed Forge app's API, so an agent decides while the app holds the data and enforces the rules.
