Services answers "what is my app running right now, and is it healthy?" It is one table with a row for everything a deploy put in an environment: the services and workers (any long-running process), cron jobs and one-off jobs, the static site, and the managed database. It reads from the same telemetry that powers the project Overview and Observability, so the numbers agree across pages.

## Where to find it

Open your project and choose **Services** in the sidebar. The environment control in the top bar sets the scope: pick `prod` to see prod, or all environments to see every row with an environment tag. The page opens on the last 24 hours for the request figures. For an app that has never been deployed, the page says nothing is deployed yet instead of showing an empty table.

## What the table shows

Each row has a name with its kind and environment, a status, and then these columns:

| Column | What it is |
|---|---|
| Status | The platform's health verdict for the workload, with the reason when it isn't healthy. A workload that restarted in the window says how many times. |
| Ready | Instances ready over instances desired, such as `2/3`. A shortfall is highlighted. |
| CPU, Memory | The busiest instance of each container, added up over the containers. Hover to see each container's own figure. |
| Req/s, p95, Errors | Request rate, 95th-percentile latency and error rate over the window. |
| Release | The release the workload runs, linked to its page. |

A row opens the service's own page. Its header repeats the status, kind, ready count, release and environment, and links to **Logs** and **Traces** already filtered to that service, and to **Restart, config and events** on the workload page. Below that are charts for instances, requests, p95 latency, errors, CPU and memory, an **Instances** table (each instance's state, restarts, last exit reason, age and node), the app's **custom metrics** that this service reports, and the **recent deploys** of that environment.

## Services, workers, jobs, sites and the database

Rows come from four places. Long-running workloads and cron jobs come from what the platform observes running. A job that only shows up in its runs appears with its latest run. The static site and the managed database come from the environment's deploy status.

A **cron job or job** has no request figures: its Req/s, p95 and Errors cells are empty, because it serves no requests. A **worker** also serves none. The page says the kind as the platform reports it, which is the Kubernetes kind (Deployment, StatefulSet, CronJob, Job), so a forge worker shows as a Deployment that serves no requests. A **static site** shows its URL and release.

The **managed database** row opens a page of its own. It lists the environments that have one, with their provision status, and links each to **Data** to browse its tables ([Data](/forge/data)). Its **Status and backups** section is marked coming soon: the database's size, connections, CPU, memory and last backup aren't reported in the app yet. Backups themselves exist at the platform level (see [Managed Postgres](/hosting/managed-postgres#backups-and-point-in-time-restore)), but you can't see their state on this page today.

## What you need for the numbers

Status, readiness, CPU and memory come from the platform watching your workloads, so they appear for anything running on [Reliant hosting](/hosting/overview) without setup. Request rate, latency and error rate come from each service's own OpenTelemetry traces. A forge-built service sends them automatically. An app forge didn't build, such as one deployed from its own Dockerfile, shows a dash in those columns until it exports traces; see [Send OpenTelemetry from any app](/guides/observability/send-opentelemetry-from-any-app). Until a workload has been seen, the page says "Nothing has reported in this scope yet. Workloads appear once Reliant sees their pods."

## Limits

CPU and memory are reported per container, not per instance. The instance table shows state, restarts and age for each instance, and the container figures sit under it. An instance's age is measured from the first telemetry the platform saw, so for an instance older than the window it is a lower bound. Services shows the current state and the recent window, not history: for a longer view use [dashboards](/hosting/observability/dashboards-and-alerts), and for restarts and crash loops from a terminal use `reliant forge obs workloads <env>`.
