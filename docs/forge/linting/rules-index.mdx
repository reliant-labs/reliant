## How to read the table

The **Rollout** column is the `introduced_in` release, then `->` and the `gates_from` release for a rule that is, or recently was, in its grace period. A single release (`v0.1.40`) means the rule has gated since that release or earlier; the table was audited back to v0.1.40. If your `forge_version` is below the `gates_from` release, the rule's findings are warnings with a note. See [the rollout](/forge/linting/rollout).

The **Group** column is how forge groups the rules in its own source; it is not the same as a lane flag. A **Codemod** is a command that makes the fix for you.

Severity is a property of the finding, not the rule, because some rules emit both. The family pages give the default for each.

## Not graded by lint.rules

A few things in a lint report are not forge rules, so `lint.rules` rejects them as keys and points at the dial that does govern them.

| Finding | Governed by |
|---------|-------------|
| `forge-frontend-typecheck` | `lint.frontend.typecheck` (`error`, `warn` or `off`) |
| `contract` findings | `contracts.exclude` and `//forge:exclude-contract: <why>` |
| `buf` findings | `buf.yaml` (`lint.use`, `lint.except`) |
| golangci-lint, eslint and stylelint findings | `.golangci.yml` and the frontend's eslint config |
| `*-unavailable` (a lane that could not run) | `lint.allow_skip`, or `--allow-skip LANE=REASON` |
| a malformed `forge:lint-disable` (no reason) | add the reason to the directive |
| `forge-lint-rules` (a bad `lint.rules` entry) | fix the entry; it is always an error |
