A new forge project is set up to deploy to Reliant's own hosting. Its `staging` and `prod` environments already point there, so publishing is one command from the project directory, with no cluster, registry or DNS to arrange first:

```bash
reliant forge env deploy staging               # build, push, cut a release, show the plan, deploy it
reliant forge env deploy prod --from staging   # ship exactly what staging runs
```

Ask the agent in your project to "deploy it" and it takes this same path. The `dev` environment stays on your machine; only `staging` and `prod` are hosted. How releases, plans and promotion work is the same on every target and is covered in [Environments & deploys](/forge/environments-and-deploys); this page is about what hosting itself provides.

## What gets hosted

Hosting runs three kinds of workload: **services**, **workers** (background processors) and **jobs** (one-off tasks such as the database migration that runs before each rollout). In a hosted environment, every service and worker in your project runs in one workload called `api` (the binary's `server` command), so the browser reaches every service at one origin with one sign-in cookie. Your frontend is published separately as a **static site** on Reliant's static hosting and CDN. Every workload and site gets a generated hostname the moment it deploys.

Your app's database is a **managed Postgres**: a dedicated database the platform creates for the environment, retained if you delete the environment. Your services receive its connection string automatically, and it is reachable only from inside the platform, so migrations run as part of the deploy rather than from your laptop.

Because the frontend is served as static files, a hosted frontend must be a static export. New forge frontends are scaffolded that way, and `forge lint --static-export` names anything in your code that the export cannot serve (a dynamic `[id]` route, a server action, `cookies()`). A frontend that needs a server at request time ships as a workload instead.

Telemetry is collected from the first deploy too: see [Observability](/forge/observability).

## Billing

Paid app hosting requires an independent, organization-wide **pay-as-you-go usage billing agreement**, authorized explicitly by an owner or admin under **Settings → Billing → Usage & invoices → App hosting billing**. There is no base fee and no machine purchase is required. CPU, memory and storage are billed from first use at the displayed usage rates; machine subscriptions include no separately spendable app hosting allowance.

Choose a positive **monthly admission budget** and accept the displayed policy before continuing to checkout. A saved card, AI wallet credit, machine subscription or checkout return alone does not activate hosting: the server must verify the agreement's funding. The budget controls admission and suspension against measured usage, not a guaranteed maximum invoice. Enforcement can lag and in-flight workloads can keep accruing charges; storage is not deleted. Changing the consented budget is not currently supported in the app.

Independent hosting billing is rolling out separately. If the app says it is unavailable, buying a machine plan does not enable it. Hosting authorization does not add an observability allowance or unlock longer product-event retention; [observability billing](/account/observability-billing) remains separate.

Static sites are the exception. They run no process, just files behind the CDN, so an organization with no plan gets a free tier for them:

- **One static site per organization**, counted across all of its environments. Deploying a second one is queued like any other billing hold (below) until you remove a site or enable independent app hosting billing.
- **1 GiB of storage.** Reliant keeps a release's files three times (live, its archive and the previous release), so in practice a release of about 340 MiB or less fits. A larger one is held with the size in the message; shrink the site or subscribe.
- **10 GiB of traffic per calendar month** (UTC) for the organization. The organization's owner is notified at 80% and 100%, and past the limit the site answers `429` until the month rolls over.

A project that is only a qualifying free static site, such as a landing page, can therefore be published without paid hosting authorization. A hosted backend needs the independent usage agreement, even though its frontend is static.

## Queued deploys

You do not have to set up billing before your first deploy. If required app hosting billing is not active, the deploy is **queued, not refused**. Reliant builds and records the release as usual, then holds it. Nothing is running yet, and nothing needs to be re-run: once billing is set up, the hold is released automatically and the deploy goes live. In the meantime:

- `forge env deploy` prints one block (what it waits on, why, what to do, a link, and that there is nothing to re-run) and exits with code **7**. Seven means "queued on a person", not "failed", so a CI job can treat it differently from a real error. `--json` reports the same facts, and `forge env status <env>` also exits 7 while the deploy is queued.
- `forge env deploy --wait` (or `forge env status <env> --wait`) blocks until the deploy is live.
- The environment's page in **Apps** (**Environments → \<env\>**) shows a "Waiting on billing" banner. Someone who can manage billing gets a **Set up billing** button that returns them to the environment afterwards; anyone else is told that only an admin can set it up, with a **Copy link** button to send along. The environment is marked queued in the Apps navigation, and a desktop notification tells you once when the deploy goes live or fails.
- A newer deploy to the same environment replaces a queued one.

Some deploys are refused rather than queued, with the reason printed: when a resource limit is exceeded, funding cannot be determined, or the admission budget has been reached. Follow the reported action; a budget refusal must not be treated as authorization to retry unattended.

## Stopping and deleting an environment

`forge env stop <env>` suspends a hosted environment's workloads (they stop running and stop costing compute) and `forge env start <env>` resumes them. `forge env delete <env>` tears the environment down; its managed database is retained. These act on the hosted environment, unlike `forge env down`, which only stops the local processes `forge env up` started.

## What hosting does not run

Hosting shares machines between customers, so it refuses anything that needs control over the cluster. The deploy tells you before publishing, naming the workload and the field.

| Not available on hosting | Why |
|---|---|
| Cron-kind workloads | Not metered yet; a worker that runs its own scheduler (`forge scaffold worker <name> --kind cron`) is fine |
| Operators, RBAC, CRDs | No Kubernetes API access on shared machines |
| Sidecars, volumes, security-context and pod overrides | The platform builds the pod itself |
| Node selectors, tolerations, priority classes | The platform decides placement |
| Domains written into the workload spec | Domains are managed separately: see [Custom domains](/forge/custom-domains) |

For any of these, bind that one workload to a cluster you operate and keep the rest hosted; see [Hosting somewhere else](/forge/environments-and-deploys#hosting-somewhere-else).
