A typical team assembles its path to production from many vendors: a framework, CI, deploys, hosting, a database, auth, secrets, logs and traces, error tracking, alerts, feature flags, security scanners and an AI assistant or two. Reliant covers most of that path in one product, and this page lists what, which tools it stands in for, and where each part is documented. It also says where Reliant stops, because a replacement list that hides its gaps isn't useful when you are deciding what to keep.

The reason one product can cover so much is that every part reads the same description of your app. The sections below explain that description first, then the replacement map, then what you get from having it all in one place that separate tools can't give you.

## How it works

Reliant keeps one declared model of your app: its services and RPCs, its schema, its environments and workloads, its releases, its secrets and its telemetry. Forge, the open-source CLI and framework, builds that model and keeps it in your repository. Reliant Cloud and the Reliant app read it to host, monitor, gate and operate the app. Because the release verdict, the error tracker, the alerts and your agents all read the same model, an error can name the release that caused it, an alert can reach an agent with the traces attached, and a migration can be checked against what the running release can survive. [Why Reliant](/getting-started/why-reliant) explains those seams in more detail.

There are two ways to build the model.

### New app: scaffold it

For a new app, Forge scaffolds the model and generates the code around it. You write three inputs and run `forge generate`:

| Input | Holds | Forge derives from it |
|---|---|---|
| `proto/services/<svc>/v1/*.proto` | The API | Connect RPC handlers, typed frontend hooks, the auth chain, per-RPC telemetry |
| `db/migrations/*.up.sql` | The schema | The ORM and entity layer, CRUD, migration-safety checks, seed data, lifecycle tests |
| `deploy/kcl/<env>/main.k` | Each environment: workloads, where they run, databases, secrets, observability, release policy | Rendered manifests, the local dev stack, hosted resources, alerts, dashboards, release gates |

Everything in the replacement map below is on from the first commit in a scaffolded app. [Two sources of truth](/forge/concepts/two-sources-of-truth) and [Project anatomy](/forge/project-anatomy) cover the layout, and the [Forge quick start](/forge/quick-start) takes one from a prompt to a URL.

### Existing app: describe it with a manifest

An app that already exists, in any language, gets the same model without a rewrite. You declare metadata about the app, and Forge and Reliant Cloud manage the tools around it. Your code, Dockerfile, CI and deploy tool stay as they are. The manifest comes in two forms:

- **An env document**, `deploy/envs/<env>.yaml`: plain YAML that needs no `forge.yaml`. This is the smallest form, and it is what `forge obs init` writes. The one below turns on hosted monitoring for an app in any language:

  ```yaml deploy/envs/prod.yaml
  apiVersion: forge.dev/env/v1
  project: "shop"
  env: "prod"
  control_plane: {}  # Reliant's control plane
  observability:
    enabled: true
    destination: {token_from_control_plane: true}
  ```

- **KCL**, `deploy/kcl/<env>/main.k`: written by `forge project new --in-place --kind app` (from the app's Dockerfile and compose file) or `--kind site` (for a Vite or Next.js app), when you want Forge to build and deploy it.

You grow the manifest as you adopt more, and every step stands alone, so you can stop after any of them:

| Step | You get | Guide |
|---|---|---|
| Linters | Findings with file and line, such as unsafe migrations, as a CI step | [Migration safety rules](/forge/linting/rules-migrations) |
| Hosted monitoring | Dashboards, error issues and alerts from standard `OTEL_*` variables, in any language | [Send OpenTelemetry from any app](/guides/observability/send-opentelemetry-from-any-app) |
| Record the deploys your CI makes | Deploy markers and a verdict per release, with your pipeline unchanged | [Keep Helm, Fly.io or Cloud Run](/guides/hosting/keep-helm-fly-cloud-run) |
| Parity with your deploy tool | Proof that what Forge would ship is what runs, read-only; then Forge builds and promotes while your tool still deploys | [Detect config drift](/guides/hosting/detect-config-drift) |
| Forge drives deploys | Environments, build once and promote by digest, managed Postgres, secrets, hosting | [Bring an existing app](/guides/forge/bring-existing-app-any-language) |

[Migrate an existing app](/forge/migrate-an-existing-app) is the entry point for this path.

What each form turns on:

| You have | What works |
|---|---|
| No manifest at all | The linters (migration safety, tracing, slow tests) and the agent tooling: skills and the Forge MCP server |
| An env document (`deploy/envs/<env>.yaml`) | Hosted monitoring from OpenTelemetry (dashboards, error issues, alerts, a verdict per release), and the deploys your own CI makes, recorded by listing those workloads as `runtime: {type: external}` |
| KCL from `forge project new --in-place` | Everything Forge does for a deployed app: parity checks against your deploy tool, build once and promote by digest, release gates, hosting, managed Postgres, secrets, preview environments and security scans per release |

Neither form gets everything a scaffold does. The automatic per-RPC tracing, the service graph and the dashboards derived from your code need Forge's generated RPC layer, so they belong to scaffolded apps. Deeper instrumentation for an existing app comes from Forge's runtime libraries, or from porting a service to codegen.

## The replacement map

Each row names the tools Reliant stands in for, the Reliant feature that does it, and the page that explains it. Vendor names say which job is being done; they are not a comparison, and Reliant doesn't claim parity with a vendor's full product. A row marked **partial** covers only part of that job. Most observability and delivery features need Reliant Cloud for the hosted version, and Forge runs the local versions anywhere.

## What having it all in one place gets you

Each item below needs facts from two or more of the categories above. A single-category vendor can't do it on its own, and with separate tools you would integrate each of them yourself.

- **Readable browser stacks with no upload step.** The build knows your source maps and the monitoring knows the errors, so the maps are filed privately with the release at build time, never served publicly, and resolve minified stacks into issues. No CI step uploads anything. See [Frontend errors, issues and source maps](/hosting/observability/dashboards-and-alerts#frontend-errors-issues-and-source-maps).
- **Alert to fix pull request.** An alert becomes an issue, an agent investigates it with the traces, logs and data it can reach, and a person labels it ready for the fix pull request. Autopilot never merges. See [Autopilot](/guides/autopilot).
- **Suspect commits and regressions.** Errors are tied to releases and releases to commits, so every issue lists suspect commits, and a fixed issue reopens as a regression only when a newer release brings it back. See [Find the release that caused an error](/guides/observability/find-release-that-caused-error).
- **Rollback floors.** Migrations and releases know about each other, so nobody can deploy a release older than a breaking migration, and a migration gates its rollout. See [Safe migrations](/deep-dives/safe-migrations) and [Release gates](/forge/deploy/release-gates).
- **Tracing with no instrumentation.** Because codegen knows every RPC, each one is traced, and a service graph and dashboards come from the code. This is for scaffolded apps. See [What every boundary records](/hosting/observability/signals).
- **Profile-guided builds.** Production profiles feed the next build with `forge pgo pull`. See the [`forge pgo` reference](/reference/cli#reliant-forge-pgo).
- **DORA metrics with no integration work.** The release ledger already records every deploy, so delivery metrics are a view of it. See [Release promotion](/forge/deploy/releases-and-promotion).
- **Agents that deploy inside gates.** An agent that ships through Forge goes through the same plans, approvals and release gates as a person. See [Deploy your app with a coding agent](/guides/forge/deploy-with-a-coding-agent).
- **Evidence on each release (partial).** A release carries its SBOM and check results today. Signed attestations are not available yet. See [Vulnerabilities](/forge/security/vulnerabilities).
- **Full-stack pull request environments (partial).** A preview environment gets its own managed Postgres and runs your migrations, and Forge can seed a dev database from your schema. A preview starts with your schema and no rows today. See [Preview environments for every pull request](/guides/hosting/preview-environment-every-pull-request).
- **Which environments run a vulnerable build (partial).** The SBOM per release and the ledger of what each environment runs can be joined. See [Vulnerabilities](/forge/security/vulnerabilities).
- **Experiments on your own events (partial, beta).** A change can be measured against the product events you already send. Hosted sites and backends receive each environment's changes, and the Experiments screen shows whether a change has reached them. Apps outside Reliant hosting cannot fetch changes yet. See [Feature flags and experiments](/forge/observability/changes).

## Coming soon

These are not available yet, and there are no dates:

- Automatic rollback, with canary and progressive delivery. Today a release gets a verdict and you recover by [redeploying an earlier release](/guides/hosting/recover-from-bad-deploy) or rolling forward.
- Image signing, attestation and admission, so only signed images run.
- Cost visibility, per workload and environment.
- Autoscaling on Reliant hosting. Hosting runs the replicas you declare today. On a cluster you run, `forge.Autoscale` already scales a service or worker on CPU: see [Autoscaling](/forge/deploy/autoscaling).
- [Reliant Engine](/getting-started/concepts#reliant-engine-coming-soon), which runs Reliant workflows inside your own product, under your brand.

## Where it doesn't fit, and what you keep

Reliant hosting is deliberately small. It runs one region (us-central1), has no autoscaling, no hosted cron-kind workloads or operators, and hosts frontends as static exports only, with no server-side rendering. [Limits](/hosting/limits) is the whole list. Forge is also a poor fit for some work and some stacks; [When not to use Forge](/forge/when-not-to-use-forge) says which. Any of these can be handled by binding one workload to a cluster you run and keeping the rest hosted.

You don't have to replace anything you want to keep. Each seam is meant to be used on its own:

- **Telemetry.** Send OpenTelemetry to Reliant from any app, or point an environment at your own backend. See [Send OpenTelemetry from any app](/guides/observability/send-opentelemetry-from-any-app) and [bring your own](/forge/deploy/escape-hatches#bring-your-own-database-identity-provider-or-telemetry-backend).
- **Deploys.** Keep Helm, Fly.io, Cloud Run or Argo CD with `forge.OnExternal`. See [Keep your deploy tool](/guides/hosting/keep-helm-fly-cloud-run).
- **Database and identity.** Use your own Postgres or your own identity provider. See [bring your own](/forge/deploy/escape-hatches#bring-your-own-database-identity-provider-or-telemetry-backend).
- **Integrations, not replacements.** PagerDuty and Slack receive Reliant's alerts, and GitHub Actions stays your CI runner. Reliant delivers to them rather than replacing them.
