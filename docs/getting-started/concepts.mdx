Reliant is a cloud service. Its servers run your agents and call the AI model, and a **daemon** on a machine you choose does the hands-on work with your code. Everything else in Reliant is built from the handful of concepts below.

## How the pieces fit

You use Reliant from the web app or the desktop app. When you send a message, Reliant's servers run the agent loop: they call the model, and whenever the model wants to read a file or run a command, they send that request to your machine's daemon and pass the result back to the model. Your repository stays on that machine. See [Privacy & Security](/help/privacy) for exactly what is stored where.

### Machine and daemon

A **machine** is where your agents' tools run, and the **daemon** is the small program on it that carries those tools out. A machine is either **your own computer** (or another computer you own, such as a workstation or server) or a **Reliant cloud machine** that Reliant hosts for you. Cloud machines suspend after a period of inactivity, don't bill for compute while suspended (the disk is still billed), and wake automatically when you next send a message. Manage them in **Settings → Machines**.

**Related**: [Machines](/machines/overview)

### Chat

A **chat** is one conversation with an agent or a workflow, tied to a project. You can run many chats at once, each on its own branch or [worktree](/features/worktrees), and step away while they work.

### Project

A **project** is a code repository, or several, that your agents work in. A cloud machine gets its copy by cloning from GitHub, which you connect in **Settings → GitHub**.

## Forge

Reliant and Forge are two halves of one workflow. Reliant is the harness: the agents, workflows and machines that do the work. **Forge** is the foundation: the framework for the app those agents build and run. Forge is built into the `reliant` binary, so everything below is available as `reliant forge …`.

### Forge project

A **forge project** is a repository with a fixed structure: Go services defined in protobuf, SQL migrations, background workers and jobs, and Next.js, Vite or Expo frontends or static sites. Forge generates the plumbing (API stubs, data access, typed config, frontend hooks, dashboards) from your protobuf API and your SQL migrations, and never touches the files where your logic lives. A project with only a static frontend, such as a landing page, is a complete forge project too.

**Related**: [Forge overview](/forge/overview), [Project anatomy](/forge/project-anatomy)

### Environment and release

An **environment** is a place the project runs, declared as code under `deploy/kcl/`. A new project has `dev` on your machine, and `staging` and `prod` on Reliant hosting. A **release** is an immutable build of the project, cut once by `forge env deploy` and promoted unchanged from one environment to the next, so what you tested in staging is what goes to prod. Every deploy shows a plan of what will change and waits for your approval.

**Related**: [Environments & deploys](/forge/environments-and-deploys)

### Hosting

**Reliant hosting** is where `staging` and `prod` run by default: your services, workers and jobs, a managed Postgres, and frontends published as static sites behind a CDN, each with a hostname, with custom domains and managed secrets. It needs a Reliant Compute plan, except for a single static site per organization, which has a free tier. See the [pricing page](https://reliantlabs.io/pricing) for current plans.

**Related**: [Hosting on Reliant](/forge/hosting)

### Build an App workflow

**Build an App** is the built-in Reliant workflow that connects the two: it scopes an app with you, scaffolds it as a forge project, builds it, and verifies the running result. **Move to Forge** ports an existing codebase into a forge project one component at a time. Once an app is deployed, the **Apps** and **Observability** areas of Reliant show its releases, logs, traces, dashboards and alerts.

**Related**: [Forge quick start](/forge/quick-start), [Observability](/forge/observability)

## The essentials

These three concepts are all you need to start building workflows.

### Workflow

A **workflow** is a YAML file that defines a multi-step process. It specifies what steps to run, in what order, and under what conditions.

The simplest workflow is the default `agent` loop: send your message to the LLM, execute tool calls, repeat until done — the same thing every ADE does. More interesting workflows chain multiple agents, run steps in parallel, loop until tests pass, or branch based on results. That's what makes Reliant different.

Workflows live in `.reliant/workflows/` and are version-controlled with your code.

**Related**: [Workflow Overview](/workflows/overview)

### Node

A **node** is a single step in a workflow. Each node does one thing:

| Node Type | What it does |
| --- | --- |
| `workflow` | Runs another workflow, most often an agent (`builtin://agent`) |
| `run` | Executes a shell command (e.g., `npm test`) |
| `action` | Performs a built-in operation, such as calling the model, running tools, compacting history, or asking for approval |
| `loop` | Repeats a sub-workflow while a condition is true |

There are more node kinds for routing, joining parallel branches and invoking tools directly. The [Nodes reference](/reference/nodes) lists every one.

Nodes connect via **edges** that define execution flow — including conditional routing (e.g., "if tests pass, go to deploy; if they fail, go to fix").

**Related**: [Creating Custom Workflows](/workflows/custom-workflows)

### Thread

A **thread** is the conversation history — the messages exchanged between you, the AI, and between agents. Threads matter most in multi-agent workflows where you control whether agents share context:

| Thread Mode | Behavior |
| --- | --- |
| `inherit` | Agent uses the parent's thread (sees everything) |
| `fork` | Agent starts with a copy of the thread (then diverges) |
| `new` | Agent starts with an empty thread (fully isolated) |

**Related**: [Threads](/features/threads)

## Building blocks

These concepts come into play as your workflows get more sophisticated.

### Preset

A **preset** bundles parameter values into a reusable configuration: model selection, system prompt, temperature, tool access. Think of presets as agent personalities — the same workflow can behave differently with different presets.

The "researcher" preset might use lower temperature with read-only tools. The "code reviewer" preset might use a specific system prompt. You can create custom presets in `.reliant/presets/`.

**Related**: [Presets](/workflows/presets)

### Execution mode

Controls how much autonomy the agent has: **Auto** (full autonomy), **Manual** (approve each action), or **Plan** (read-only exploration). You can switch modes mid-conversation.

**Related**: [Execution Modes](/workflows/overview#execution-modes)

### Worktree (Workspace)

A **worktree** is an isolated Git working directory on your machine. Reliant uses worktrees to let parallel agents work on separate branches without interfering, or to let you work on multiple branches simultaneously.

In the UI, these appear as "Workspaces."

**Related**: [Worktrees](/features/worktrees)

## Advanced

These are used in advanced workflow definitions. You don't need them right away.

### CEL (Common Expression Language)

The expression language used in workflow conditions and dynamic values:

```yaml
# Edge condition (bare CEL)
condition: nodes.run_tests.exit_code == 0

# Interpolation in strings
content: "Result: {{nodes.step.output}}"
```

**Related**: [CEL Expressions](/reference/cel-expressions)

### MCP (Model Context Protocol)

A standard for connecting AI assistants to external tools and data sources. Reliant includes built-in MCP servers and supports adding your own for database queries, API integrations, and custom tools.

**Related**: [MCP Servers](/settings/mcp-servers)

### Tool

A capability the AI can use — reading files, searching code, running commands, making edits. Tools can be built-in, MCP-provided, or workflow-defined (response tools for structured output).
