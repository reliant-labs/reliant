An **automation** starts a run without anyone typing. "Every weekday at 9, review yesterday's failed CI runs." "When an issue is opened in `acme/shopfront`, triage it." "When the nightly workflow fails, open a follow-up." The run is an ordinary chat you can open afterwards, with the full transcript, so you can see exactly what the agent did.

## Declare, then activate

Automations have two halves, and keeping them apart is what makes a workflow shareable.

A workflow **declares when it should run** in a `triggers:` block of its YAML. The declaration says the source (a schedule, a webhook, an integration event, another workflow's outcome), an optional filter, and how the event's data becomes the workflow's inputs. Declaring a trigger fires nothing.

You then **activate** it, which says as whom and where: your account, a project, the [machine](/machines/overview) whose tools the run uses (or no machine), and, for an integration event, which connected account it listens through. In the app, a workflow's detail page lists its declared triggers with an **Activate** button. The activation re-reads the declaration every time it fires, so editing the workflow's `triggers:` block changes the automation. If you rename or remove the declaration, the activation is marked **broken** and fires nothing until you restore it.

```yaml
name: issue-triage
description: Triage new GitHub issues and a weekday morning digest
entry: [triage]

inputs:
  issue_number:
    type: integer
    default: 0
    description: The issue to triage (set by the trigger)

triggers:
  - name: new-issue
    description: Triage each new issue as it is opened
    integration:
      integration: github
      events: [issues.opened]
      match:
        repository: acme/shopfront
    filter: "trigger.payload.data.issue.user.login != 'dependabot[bot]'"
    inputs:
      issue_number: "{{ trigger.payload.data.issue.number }}"
    prompt: "Triage issue #{{ trigger.payload.data.issue.number }}"
  - name: weekday-digest
    description: Summarise open issues every weekday morning
    schedule:
      cron: ["0 9 * * 1-5"]
      timezone: America/New_York
      overlap: skip

nodes:
  - id: triage
    type: workflow
    ref: builtin://agent
    args:
      model:
        tags: [moderate]
```

Each entry has a unique `name` and exactly one source. The fields around the source are the same for every kind:

| Field | Purpose |
|-------|---------|
| `name` | Unique within the workflow; what an activation refers to |
| `description` | Shown to whoever chooses what to activate |
| `filter` | A [CEL](/reference/cel-expressions) expression over `trigger`; the event fires only if it is true. Not allowed on schedules |
| `origin_filter` | A CEL expression over `trigger`, evaluated before `filter`, that decides by *who caused the event*. The default ignores the workflow's own echoes. See [Telling your own writes apart](#telling-your-own-writes-apart). Not allowed on schedules |
| `inputs` | Sets workflow inputs from the event: input name to a template over `trigger` |
| `prompt` | The first message of the run, as a template over `trigger`. An activation's own message overrides it |

Inside templates and filters, `trigger.payload` is the event's data and `trigger.kind` says what fired. Unknown keys in a `triggers:` block are errors, not ignored: a mistyped `filtr:` would otherwise mean a trigger that fires on everything.

For an integration trigger, validation also checks the filter, inputs and prompt against the payload the integration declares for its events, so a read that payload can never satisfy is an error before the trigger fires. For example, GitHub's `issue.labels` is a list of label names: write `!('wontfix' in trigger.payload.data.issue.labels)`, not `l.name`.

### One declaration, many activations: `trigger.activation`

A filter, an `inputs` mapping and a `prompt` can also read the activation they fire for, so each activation carries its own settings and the declaration does not need them pasted in:

| Expression | Is |
|------------|----|
| `trigger.activation.params.<input>` | A value the activation sets for one of the workflow's declared inputs |
| `trigger.activation.id` | The activation's id |
| `trigger.activation.owner.user_id` | The user the activation's runs execute as |
| `trigger.activation.owner.github_id` | The GitHub user id of the connection the activation listens through, as a string; empty when it has none |

A pack that watches a list of repositories declares an input for it and filters on that input. Each activation then names its own repositories:

```yaml
name: issue-triage
inputs:
  repos:
    type: array
    default: []
  team:
    type: string
    default: platform
  issue_number:
    type: integer
    default: 0
triggers:
  - name: new-issue
    integration:
      integration: github
      events: [issues.opened]
    filter: "trigger.payload.attributes.repository in trigger.activation.params.repos"
    inputs:
      issue_number: "{{ trigger.payload.data.issue.number }}"
    prompt: "{{ trigger.activation.params.team }} is triaging #{{ trigger.payload.data.issue.number }}"
```

Activate it once with `params: {repos: [acme/web, acme/docs], team: frontend}` and again with `params: {repos: [acme/api]}`; an issue in `acme/api` fires only the second. An event that no activation's list admits is recorded as skipped on each, with the filter in the reason.

- `trigger.activation.params` holds the workflow's declared inputs **except the ones the trigger's `inputs` mapping sets from the event** (the event's value always wins, so an activation may not set them).
- It is what the run will receive: the input's default is applied when the activation does not set it, and each value has its declared type. An unset list with no default is `[]`, so a filter on it matches nothing instead of failing.
- Validation types it from the workflow's inputs. `trigger.activation.params.repo` for a `repos` input, or a read of a field of a string param, is an error when the workflow is saved.
- Creating an activation checks its params the same way: a param that names no input (with a "did you mean"), or has the wrong type, is refused.
- It exists only in a trigger's `filter`, `inputs`, `prompt` and `dedupe_key`. A run's own nodes read `inputs.*`, where the same values arrive, and the rest of `trigger.*`.
- Try it before activating: `reliant workflow validate --trigger-payload '{...}' --activation-params '{"repos": ["acme/web"]}'` runs every declared trigger against a sample event and sample params, and the `cel_eval` tool and `reliant workflow eval --scope trigger` take `activation_params` too. `--owner-github-id` supplies `trigger.activation.owner.github_id`.

#### Who may start a run

Trust is a CEL filter over data the trigger already has; there is no table of trusted people to maintain. `trigger.sender` is who the source says sent the event, and `trigger.activation.owner.github_id` is you, by the GitHub connection the activation listens through. Both are strings, so a list of trusted ids is an array of strings (`"583231"`, quoted: CEL does not match the number `583231` against the string).

```yaml
inputs:
  trusted_ids: {type: array, default: []}
triggers:
  - name: new-issue
    integration: {integration: github, events: [issues.opened]}
    filter: >-
      trigger.sender.verified &&
      (trigger.sender.id == trigger.activation.owner.github_id ||
       trigger.sender.id in trigger.activation.params.trusted_ids)
```

With no `trusted_ids` set, only you can start it. An activation with no GitHub connection has an empty `github_id`, which never equals a verified sender's id, so only its `trusted_ids` admit anyone. Comparing a sender id with a number is an error when the workflow is saved.

## Telling your own writes apart

An automation that writes to the thing it watches hears itself. A reviewer posts a review on a pull request and the review comes back as an `issue_comment.created`; a responder pushes a fix and the push comes back as `pull_request.synchronize`. Without a guard, a workflow that reacts to either would run forever.

Reliant records every change an integration action makes on a run's behalf (a comment, review, label, pull request) *before* it makes it, and when a webhook arrives it checks whether one of those writes caused it. The answer is `trigger.origin`, available in `filter`, `inputs` and `prompt`:

| Field | Type | Meaning |
|-------|------|---------|
| `trigger.origin.caused_by_reliant` | bool | Reliant wrote the thing this event reports, at any confidence |
| `trigger.origin.confidence` | string | `exact`: the event's own object id (a comment, review or pull request number) is one a run's write produced. `intent`: no id matched yet, but the event matches a recent write on the same target and content (the webhook can arrive before the write's own response does). `app`: it came from Reliant's GitHub App, run unknown. `claimed`: a push whose commit carries a `Reliant-Run:` trailer, which anyone can write, so it is only ever a reason to ignore, never to trust. `none`: nothing says Reliant caused it |
| `trigger.origin.run_id` | string | The run (chat id) that made the write |
| `trigger.origin.workflow` | string | The workflow that run executed |
| `trigger.origin.trigger_name` | string | The declared trigger that launched that run, when one did |
| `trigger.origin.same_workflow` | bool | That run is a run of *this trigger's own workflow*: the event is its own echo |
| `trigger.origin.actor` | string | Who the write was made as: `app` (the GitHub App), `owner` (your own token) or `unknown` |
| `trigger.origin.lineage_depth` | int | How many event-driven hops led to the run that made the write. A chain stops at 5 |

Every field is always present. An event nothing attributed reads `caused_by_reliant: false`, `confidence: 'none'`, empty strings and `lineage_depth: 0`, so a filter never fails with "no such key". The run's own details (`run_id`, `workflow`, `trigger_name`) are filled only when the run is *yours*: a different user's trigger on the same repository learns that Reliant caused the event and nothing about whose run.

### `origin_filter`

`origin_filter` is a CEL bool, evaluated before `filter`. A false skips the event. When you do not write one, this is what runs:

```yaml
origin_filter: "!(trigger.origin.same_workflow && trigger.origin.confidence in ['exact', 'intent'])"
```

So a workflow ignores its own echoes by default, and only when Reliant is confident they are its own: an `app` or `claimed` origin says Reliant did it but not which run, so it is not treated as this workflow's. To change that, write your own:

```yaml
triggers:
  - name: on-push
    integration:
      integration: github
      events: [pull_request.synchronize]
    # Hear everything, including this workflow's own writes.
    origin_filter: "true"

  - name: on-comment
    integration:
      integration: github
      events: [issue_comment.created]
    # Ignore this workflow's own echoes, except the ones a particular trigger of
    # its own caused: one deliberate re-trigger.
    origin_filter: "!trigger.origin.same_workflow || trigger.origin.trigger_name == 'responder-push'"
```

Validation compiles `origin_filter` and checks it against the same typed `trigger` the filter sees, so a misspelled field (`trigger.origin.same_workfow`) is an error when you save the workflow, not a trigger that quietly never matches.

### Skipped events say why

An event the `origin_filter` rejects is recorded as **skipped** with the reason, so the automation's history explains it:

```text
origin_filter rejected: caused by run 4f1c… of this workflow (exact match): !(trigger.origin.same_workflow && trigger.origin.confidence in ['exact', 'intent'])
```

### The loop cap

Whatever `origin_filter` says, a chain of event-driven launches stops at **5 hops**. A run launched by an event that one of its ancestors' writes caused inherits that ancestor's chain plus one; a launch that would be the sixth is skipped with `loop guard: launch chain is already 5 hops deep (max 5)`. No expression can override it, so two workflows that deliberately re-trigger each other with `origin_filter: "true"` still stop. The cap counts other users' runs too.

### What can and cannot be attributed

Only writes Reliant makes itself are attributed: a `type: action` node, or an integration tool an agent calls. Those are recorded exactly. What an agent does through a **shell** is not:

| Write | Attribution |
|-------|-------------|
| An integration action or tool (`issue.comment`, `pr.review.create`, `pr.create`, `issue.labels.add`, ...) | `exact` or `intent` |
| A comment, review or pull request made through Reliant's GitHub App without a recorded write | `app` |
| A `git push` whose commit message ends in a `Reliant-Run:` trailer | `claimed` |
| `gh` or `git push` run by an agent in a shell with your own login | **Not attributable.** To GitHub it is you |

If an agent in a shell can write to GitHub as you, give the writing to an action node, and keep the shell for work on the checkout.

## Unattended by design

Nobody is watching an automation's run. The agent is told to decide and proceed rather than ask, questions and approvals resolve immediately with no answer instead of waiting, and a run that hits trouble records it rather than parking forever. Design workflows for this: give them everything they need in the prompt and inputs, and assume nothing can be clarified mid-run.

A workflow that should only ever start from its triggers, never from a chat, can set `automation_only: true`.

## Watching your automations

**Workflows → Automations** lists every automation across your projects, with a "coming up" timeline of the next 24 hours of scheduled runs and each automation's health, computed from its last ten firings:

| Health | Meaning |
|--------|---------|
| Healthy | No failure recently and at least one completed run |
| Degraded | A failure in the window, or three skipped scheduled fires in a row |
| Failing | The two most recent resolved firings both failed |
| Broken | The workflow it activates is gone, renamed its trigger, or changed kind |
| Unknown | Never fired, or nothing has resolved yet |

A run that launched and then failed counts as a failure, not just a launch that errored. Opening an automation shows its history: each firing, what it did (launched, skipped, failed) and a link to the run it started.

## From the command line

`reliant trigger` manages **schedule** automations: `create`, `list`, `get`, `update`, `enable`, `disable`, `fire`, `events` and `delete`. Webhook, integration and workflow-event automations are enabled from the app. An agent can write and test a workflow but cannot enable one, so `create`, `update` and `enable` refuse to run from an agent's shell; only you turn an automation on. See [Schedules](/automations/schedules) for the commands.
