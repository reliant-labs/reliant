title: "Choosing a machine in workflows"
description: "How Reliant decides which machine runs a chat or a workflow, and how to pin one with daemon:"
---

A project can be installed on several machines, and each chat has its own machine: you pick it on the new-chat screen, or change it later with **Connect a machine**. A chat with no machine pinned runs on your [default machine](/machines/overview#your-default-machine), and a branched chat runs on the machine that holds its workspace. An automation picks its own machine when you enable it, and a `daemon:` in a workflow can send work somewhere else again.

When a workflow run has to choose, Reliant resolves it in a fixed order, from the most specific instruction to the least:

```text
Node daemon  →  Workflow daemon  →  Chat's or automation's machine  →  Default machine
```

A `daemon:` on a single node wins over a `daemon:` on the whole workflow, which wins over the machine the chat or automation was started with, which wins over your default machine.

## Automations

When you enable an [automation](/automations/overview) you choose its machine, or **No machine** if the workflow allows it. The runs it starts use that machine's tools, whichever machines your chats use. If you leave it unset for a project that has several candidates, you are asked to choose; an unattended run is never sent somewhere by guesswork.

## The `daemon:` field

A workflow, or any node in it, can name where its tools run. The shorthand takes a kind or a machine name:

```yaml
name: build-on-cloud
description: Plan on whichever machine is default, run the build on a cloud machine
entry: [plan, build]
daemon: local

nodes:
  - id: plan
    type: workflow
    ref: builtin://agent
  - id: build
    type: run
    daemon: cloud
    command: make build

edges:
  - from: plan
    default: build
```

`local`, `cloud` and `any` are kinds; any other string is matched against machine names. Here the workflow defaults to your own computer, and the `build` node overrides that to run on a cloud machine.

For more control, use a selector. Every field you give must match:

```yaml
name: runner-by-selector
entry: [build]

nodes:
  - id: build
    type: run
    daemon:
      type: cloud
      labels:
        gpu: "true"
    command: make build
```

A selector may contain `id`, `name`, `type` (`local`, `cloud` or `any`), `labels` and `pool`. `labels`, alone or next to `id`, `name` or `type`, narrows the match: every label listed must be present on the machine. A machine advertises the labels it was started with (`reliant daemon start --label gpu=true`) when it connects, and a selector's `labels` match those while it is connected. `pool` places the work instead, as described below.

The value can also be a CEL expression, such as `"{{ inputs.where }}"`, which may produce a string or a map with the same keys.

## Pinning a pool instead of a machine

A name or an id pins one machine. When that machine is replaced, renamed, asleep or busy, every run that names it waits for it, even while another machine that could do the work sits idle. For work that any of several machines can do, such as a CI gate or a nightly build, pin a machine pool instead:

```yaml
name: gate
entry: [test]
daemon:
  pool: ci            # one of your machine pools

nodes:
  - id: test
    type: run
    timeout: 30m
    command: make test
  - id: bench
    type: run
    timeout: 1h
    daemon:
      pool: gpu       # a node-level pool wins over the workflow's
    command: make bench

edges:
  - from: test
    default: bench
```

**`daemon: {pool: <name>}`** places the work on one member of your machine pool of that name. It is chosen the way a pool-bound automation's run is: the least-loaded member that can take work, skipping members that are not synced to the pool's agreed workflow catalog, and never more than the pool's `max_runs_per_member` live runs on one member. When every member is full the run waits for a slot, and a sleeping member is woken. `pool` stands alone: combined with `id`, `name`, `type` or `labels` it is a validation error, because the pool chooses the machine itself. Naming a pool you do not have fails validation when the workflow is saved, and fails the run if the pool is deleted afterwards.
Placement happens **once**. A workflow-level `pool` picks a machine when the run starts, and every later step of the run uses that machine. A node-level one picks a machine the first time the node runs, and every iteration of a loop around it reuses that machine. The placement holds one of the member's `max_runs_per_member` slots for as long as the run is live, and a run's later placements on a member it already holds take no second slot.

The order is the one above: a node's `daemon:` wins over the workflow's, which wins over the chat's or automation's machine. A run an automation already placed on a pool stays on the member it was placed on when the workflow names the same pool, so the run never leaves its checkout.

<Note>
Pinning a machine by name or id keeps working unchanged. [`reliant workflow lint`](/workflows/lint#daemon-machine-pin) warns about it, so a workflow that should survive a machine swap moves to a pool.
</Note>

<Warning>
A `daemon:` makes the workflow need a machine. It cannot run as a [no-machine run](/automations/no-machine-runs), and the workflow builder warns you about it.
</Warning>

## Machine status

| Status | Meaning |
|--------|---------|
| active | Connected and working |
| idle | Connected, not recently active |
| disconnected | Not connected. A cloud machine in this state is woken when something needs it |

A running daemon sends a heartbeat every 15 seconds and is treated as gone after 30 seconds without one.
