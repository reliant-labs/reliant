Presets are saved configurations of workflow parameters for switching between different agent behaviors. Instead of manually configuring model, tools and system prompts each time you run a workflow, you select a preset that bundles all these settings together.

![Manage and view your saved agent configurations](/images/screenshots/presets-list.png)

Think of presets as profiles for your agents. A researcher preset configures an agent for thorough investigation with low temperature for accuracy. A code reviewer preset focuses on quality feedback with access to search tools. When you select a preset, all its parameters apply at once.

## How Presets Work

Presets use tag-based matching to connect with workflows. Every preset declares a `tag` that specifies what kind of workflow inputs it targets. When you load presets for a workflow, Reliant matches the preset's tag against the workflow's tag or a group's tag for multi-agent workflows. Only presets with matching tags appear as options.

A preset with `tag: agent` works with any workflow whose `presets:` block declares `tag: agent`, or that has a group tagged `agent`. The same researcher preset can configure a standalone agent workflow, or configure just the research phase of a multi-phase workflow—the tag matching handles it automatically.

Presets can be partial. A preset doesn't need to specify every parameter the workflow accepts. It might only set `model` and `temperature`, leaving other parameters to their defaults or to be configured inline.

However, every parameter a preset *does* specify must exist in the target workflow. Presets can't include unknown or extra parameters—strict validation catches typos and stale parameters early rather than silently ignoring them.

When multiple presets match different groups in a workflow, each group gets its own preset selection. A multi-agent workflow might have one group configured with the researcher preset and another with the code reviewer preset.

### Targeting Top-Level Inputs with "default"

In multi-group workflows, you may need to apply a preset to the workflow's top-level inputs (those not in any group). The special group name `default` targets these ungrouped inputs.

```yaml
# In a workflow node that calls a sub-workflow
- id: my_agent
  type: workflow
  ref: builtin://agent
  presets:
    default: researcher  # Applies to top-level inputs (model, tools, etc.)
    implementer: general # Applies to the implementer group
```

Because `default` has this special meaning, you can't name your own input groups `default`. If you try, the workflow will fail validation with an error indicating that `default` is reserved.

### Provider-Agnostic Model Selection

Presets use tag-based model selection to work across different AI providers. Instead of hardcoding a specific model, presets specify what they need semantically:

```yaml
params:
  model:
    tags: [flagship]  # Use the best available model
```

When you run a workflow with this preset, Reliant selects the best matching model from your configured providers. If you have Anthropic configured, it picks Anthropic's top model; if you have OpenAI, OpenAI's. This means the same presets work regardless of which providers you've set up.

Available tags describe model characteristics:

- `powerful` — The frontier tier, for when capability matters more than cost; its models run at the highest thinking level
- `flagship` — Best quality for complex tasks
- `moderate` — Good balance of quality and cost
- `fast` — Quick responses for simple tasks
- `cheap` — Lowest cost for budget-conscious usage
- `reasoning` — Extended thinking capability
- `local` — Runs on local hardware (Ollama, LM Studio, etc.)

When you specify multiple tags, Reliant uses **weighted best-match scoring**. Earlier tags have higher priority. A preset with `tags: [local, fast]` prefers models with both tags, but falls back to local-only or fast-only models if no perfect match exists. This enables graceful degradation—presets work whether or not users have local models configured.

```yaml
tags: [flagship, reasoning]  # Prefer flagship+reasoning, fall back to flagship-only
tags: [local, cheap]         # Prefer local (free), fall back to cheap cloud models
```

If you need a specific model regardless of tags, you can still use explicit IDs:

```yaml
params:
  model:
    id: your-model-id  # Always use this specific model (see the Models reference)
```

See [LLM Guide](/reference/llm-guide) for complete details on model selection and available tags.

## Built-in Presets

Reliant includes fifteen built-in presets. They are available immediately without configuration. Models are chosen by tag, so each resolves to whatever your providers offer: `flagship` is the best available, `moderate` is a balance of quality and cost, and `fast` is the quickest. Tools named `tag:...` are groups; `tag:coding:default` is the standard coding set (files, shell, search, web, planning).

| Preset | Model | Key tools | Purpose |
|--------|-------|-----------|---------|
| `general` | flagship | `tag:coding:default` | Versatile coding assistant with a discovery-first approach. Can spawn most of the other presets. |
| `researcher` | flagship | `tag:shell`, `tag:web`, `view`, `code_context` | Codebase investigation and analysis. For understanding, not changing. |
| `planner` | flagship | `view`, `tag:shell`, `code_context`, `create_plan` | Turns research into step-by-step implementation plans. Produces plans, not code. |
| `implementer` | moderate | `tag:coding:default`, `prove_test` | Implements well-specified changes by following detailed instructions. |
| `code_reviewer` | flagship | `tag:shell`, `tag:web`, `view`, `code_context` | Code review orchestrator. Spawns reviewers and produces a unified report; does not modify code. |
| `tester` | moderate | `view`, `write`, `edit`, `tag:shell`, `code_context`, `prove_test` | Builds test harnesses and writes unit, integration and end-to-end tests. |
| `debug` | flagship | `view`, `tag:shell`, `code_context` | Debugging orchestrator. Coordinates research and testing to isolate a bug without fixing it. |
| `refactor` | moderate | `view`, `edit`, `write`, `find_replace`, `move_code`, `tag:shell`, `code_context` | Systematic structural improvement: assess, verify tests, transform incrementally. |
| `git` | fast | `tag:shell`, `view` | Commits, branching and version control. Loads the conflict-resolver skill for hard merges. |
| `documentation` | moderate | `view`, `write`, `edit`, `tag:shell`, `fetch` | Narrative-driven technical writing. |
| `ux` | flagship | `fetch`, `view`, `write`, `edit`, `tag:shell`, planning tools, `component_library`, browser tools | UI design and implementation, with a browser to check the result. |
| `forge` | flagship | `tag:coding:default`, `ask_user`, `tag:web`, browser tools | General-purpose agent for Forge app generation, able to spawn all the others. |
| `forge_implementer` | moderate | `tag:coding:default`, `component_library`, `prove_test` | Implements one seam of a Forge app, with the component library preloaded. Has no browser, by design. |
| `migrate` | flagship | `tag:coding:default` | Guides the move from Claude Code, Cursor, Codex or Windsurf. Used by [Import](/guides/import). |
| `workflow_builder` | flagship | `tag:workflow`, `tag:shell`, `tag:web`, `skill`, `view` | Builds and edits workflows, with the `workflow-builder` skill loaded. Used by [Create a Workflow](/guides/create-a-workflow). |

The table summarizes the preset files that ship in the Reliant source (`internal/workflow/builtin/presets/`). For a preset's complete tool list, spawn list and system prompt, open **Settings → Presets** and choose **View** on it.

### Detailed Examples

**researcher** is ideal when you need to understand a codebase before making changes. It follows a methodical investigation process: planning and scope definition, architecture and codebase analysis, pattern recognition, and historical analysis. The agent maps dependencies, identifies conventions, and documents findings—producing research that informs implementation decisions.

**refactor** handles structural code changes safely. It uses specialized tools like `find_replace` for renaming across files and `move_code` for relocating functions. The strict methodology requires: assess and plan the changes, verify tests pass before starting, execute incremental transformations, and verify behavior preservation after each step.

**debug** coordinates the debugging process by spawning specialized agents rather than doing everything itself. It delegates investigation to researchers and test isolation to testers. The goal is identifying the root cause with high confidence before any fix is attempted.

## Creating Custom Presets

Custom presets live in `.reliant/presets/` in your project directory. Each preset is a YAML file:

```yaml
name: careful-reviewer
description: Conservative code review with strict quality standards
tag: agent
params:
  model:
    tags: [flagship]  # Use the best available model for thorough review
    temperature: 0.2
  tools:
    - view
    - tag:shell
    - code_context
  system_prompt: |
    You are a meticulous code reviewer with extremely high standards.

    Review every change with these priorities:
    1. Security vulnerabilities - treat any potential issue as critical
    2. Data integrity - ensure no data loss or corruption is possible
    3. Error handling - verify all failure modes are handled gracefully
    4. Test coverage - require tests for any new or modified code paths

    Be conservative. When in doubt, request clarification rather than
    approving code that might have issues.
```

### Preset Structure

```yaml
name: preset-name           # Required: identifier for the preset
description: What it does   # Optional: shown in preset picker
tag: agent                  # Required: matches workflow/group tags
params:                     # Required: parameter values to apply
  model:
    tags: [moderate]        # Tag-based selection (provider-agnostic)
    temperature: 0.7
  tools:
    - tool-name
    - tag:tool-group
  system_prompt: |
    Instructions for the agent...
```

The `tag` field determines which workflows and groups this preset can configure. Most presets use `tag: agent` to match the standard agent workflow inputs.

### Configurable Parameters

**model**: The AI model to use. Specify by explicit ID (`{ id: "<model id>" }`, from the [Models reference](/reference/models)), by semantic tags (`{ tags: [flagship] }`), or constrain to a specific provider (`{ tags: [moderate], provider: "anthropic" }`). Tag-based selection makes presets provider-agnostic—they work with whatever providers you have configured. The tags are the ones listed [above](#provider-agnostic-model-selection).

**temperature** and **thinking_level**: Settings of the `model` block (`model: { tags: [flagship], temperature: 0.2, thinking_level: high }`), not parameters of their own. Temperature runs from 0 to 2: lower values (0.1-0.3) produce focused, repeatable output for research and debugging, higher values (0.7-1.0) more varied output for brainstorming. `thinking_level` is `low`, `medium`, `high` or `xhigh`, clamped to what the chosen model supports.

**system_prompt**: Instructions defining the agent's role, approach, and constraints. This is where you customize behavior most significantly.

**tools**: Tools the agent can access. Specify by name (`view`, `edit`, `shell`) or by tag (`tag:coding:default`, `tag:shell`, `tag:web`, `tag:mcp`).

**spawn_presets** and **skills**: The presets this agent may [spawn](/workflows/spawn) as sub-agents (empty disables spawning), and the [skills](/features/skills) preloaded into it.

A preset can set only what the target workflow declares as an input. The built-in `agent` workflow takes `mode`, `model`, `tools`, `spawn_presets`, `skills` and `system_prompt`; other workflows declare their own, and a group's inputs are whatever that group lists.

### Provider policy: `providers:`

A preset can say which providers a run prefers and what it does when they are rate-limited. It sits beside `params`, not inside it, and it is plain data (no expressions):

```yaml
name: claude-only-reviewer
tag: agent
params:
  model:
    tags: [flagship]
providers:
  prefer: [claude, "claude:work@acme.com"]   # ordered; "<driver>" or "<driver>:<account email, label or id>"
  on_limit: wait                              # wait (the default) | fallback
  # on_limit: fallback
  # fallback: gpt-5.6-sol@codex               # "<model>@<driver>", required with on_limit: fallback
```

| Key | Meaning |
|-----|---------|
| `prefer` | Providers to run on, in order. A tier with no provider of its own resolves on the first one that serves it. An account (`claude:work@acme.com`) is a preference, not a pin: if that account is limited, the run moves to another account and says so. |
| `on_limit` | `wait` holds the run until the limit resets. `fallback` continues on `fallback` until then, then returns. Falling back to another provider is never the default. |
| `fallback` | The model to continue on. It must be on a different provider from the run's own, and it is only valid with `on_limit: fallback`. |

Unknown keys, unknown providers and a `fallback` with no model are rejected when the preset loads.

**Who wins.** For a sub-agent: the `providers` argument of its `spawn` call, then its preset's `providers:`, then what it inherits from its parent. Each field resolves on its own, so a spawn that only sets `prefer` keeps the preset's `on_limit`. The root of a chat takes the chat's own choice (the **If \<provider\> is rate-limited** row in the model settings), then the preset, then the Settings default (Settings → AI → Your providers). A model pinned as `<model>@<driver>` still decides which provider the run is on; the policy applies around it.

### Tool Specification

```yaml
params:
  tools:
    # Individual tools by name
    - view
    - edit
    - shell

    # Tool groups by tag
    - tag:coding:default    # The standard coding set: files, shell, web, planning
    - tag:shell      # The shell, plus shell_output, shell_wait, shell_kill and shell_list
    - tag:web        # fetch and web search
```

Using tags lets you reference logical groups without listing each tool.

Tool filters also support advanced expressions:

- `!tag:shell` — exclude an entire tag after includes
- `mcp__server__*` — include all MCP tools from a server via wildcard
- `!mcp__server__tool` — remove a specific tool

This means you can combine broad includes (`tag:coding:default`) with precise exclusions for safer preset defaults.

## Config-as-Code

Presets in `.reliant/presets/` are regular files that can be checked into version control:

**Team standardization**: Share agent configurations across your team. Everyone uses the same carefully tuned presets.

**Project-specific customization**: A security-focused project might have stricter code review presets. A documentation project might have presets optimized for technical writing.

**Iterative improvement**: Refine your presets and commit the improvements. Your agent configurations evolve alongside your codebase.

**Override built-ins**: Project presets with the same name as built-in presets take precedence. Create a `general.yaml` in your project to customize the general preset without changing Reliant itself.

### Where presets come from

A project sees three kinds of preset:

| Kind | Where it lives | Shared | Edited |
|------|----------------|--------|--------|
| **Built-in** | Shipped with Reliant | Everyone | Never; copy it to a new preset instead |
| **Project** | `.reliant/presets/*.yaml` in the project | Through git | In your editor. The app shows them but does not change the files |
| **Yours** | Your Reliant account, per project | No | In the app |

A project preset with a built-in's name replaces that built-in. Your own presets cannot reuse a built-in or project preset's name: saving one with a taken name is refused, so a name always means one preset.

The machine the project is on syncs `.reliant/presets/` to Reliant every couple of seconds, so a preset file you save is available without a restart. Presets are discovered like workflows: in the project root's `.reliant/presets/` and in each nested repository's. A root preset wins its bare name; otherwise a bare name is the nested repository's preset (the first by path when several declare it), and `<repo>/<name>`, such as `control-plane/implementer`, names one repository's preset exactly. Each machine's presets are kept separately, as [workflows are](/workflows/custom-workflows#workflows-on-more-than-one-machine). Workflows follow a different rule: a workflow of your own shadows a project workflow of the same `name:` (see [Workflow file location](/workflows/custom-workflows#workflow-file-location)).

## Examples

### Specialized Debugging Preset

For complex debugging sessions requiring maximum context:

```yaml
name: deep-debug
description: Thorough debugging with extensive context gathering
tag: agent
params:
  model:
    tags: [flagship]  # Use the best available model for complex debugging
    temperature: 0.1
  tools:
    - tag:coding:default
  system_prompt: |
    You are debugging a complex issue. Before attempting any fix:

    1. Gather comprehensive context
       - Read all relevant source files completely
       - Trace the execution path that triggers the bug
       - Identify all components involved

    2. Form and test hypotheses
       - List possible causes
       - Design tests to confirm or rule out each hypothesis
       - Document your reasoning

    3. Implement the minimal fix
       - Change only what's necessary
       - Preserve existing behavior except for the bug
       - Add a test that would have caught this bug

    Never guess. Always verify with actual code and tests.
```

### Fast Implementation Preset

For straightforward tasks where speed matters:

```yaml
name: quick-impl
description: Fast implementation for simple, well-understood tasks
tag: agent
params:
  model:
    tags: [fast]  # Prioritize speed for simple tasks
    temperature: 0.7
  tools:
    - tag:coding:default
  system_prompt: |
    Implement the requested feature efficiently.

    Focus on:
    - Clear, idiomatic code
    - Following existing patterns in the codebase
    - Basic error handling

    Move quickly but don't sacrifice code quality.
```

### Security Audit Preset

For security-focused code review:

```yaml
name: security-audit
description: Security-focused code analysis
tag: agent
params:
  model:
    tags: [flagship, reasoning]  # Security requires deep analysis
    temperature: 0.2
  tools:
    - view
    - tag:shell
    - code_context
  system_prompt: |
    You are a security auditor reviewing code for vulnerabilities.

    Check systematically for:
    - Injection vulnerabilities (SQL, command, XSS)
    - Authentication and authorization issues
    - Sensitive data exposure
    - Insecure dependencies
    - Cryptographic weaknesses
    - Input validation gaps

    For each finding, provide:
    - Severity (Critical/High/Medium/Low)
    - Location (file and line numbers)
    - Description of the vulnerability
    - Proof of concept if applicable
    - Recommended remediation
```

## Managing Presets in the App

Presets can be created as YAML files, and the app has three places to pick and manage them.

### Picking a preset in a chat

The chat composer's settings (the **Show all settings** button beside the model) have a **Preset** page listing the presets that fit the selected workflow, grouped as **User**, **Project** and **Built-in**. Choosing one applies all of its parameters; **None (use defaults)** goes back to the workflow's own defaults.

### Settings → Presets

**Settings → Presets** lists every preset in the current project: **Your presets** (yours and the project's), **Built-in**, and any that **Failed to load**, with the reason. Each row's menu has **View**, which shows everything the preset sets; **Copy to new preset** on a built-in; **Edit** and **Delete** on your own; and **Hide from preset picker**, which keeps a preset out of the composer without deleting it. Project presets are changed by editing their YAML files, so the app offers no edit or delete for them.

### A workflow's presets

In **Workflows → Library**, open a workflow: its **Presets** section lists the presets that fit it, and **Default presets…** sets which preset each of its groups starts with when a chat or run begins.

## Creating Presets in the App

Wherever the app shows a workflow's input group as a form, such as **Run…** on a workflow's page, the Enable dialog, or a step in the workflow builder, changing the group's values marks it **Modified from** the preset it started from, and offers two ways to keep the change:

- **Save as new** asks for a name and saves the group's current values as a new preset of your own.
- **Update**, shown with the preset's name, writes them back into the preset you started from, when it is one of yours.

You can also start from a built-in: in **Settings → Presets**, choose **Copy to new preset** on it and edit the copy.

Presets made in the app are saved to your account, in the current project, and are available immediately. To share one with your team, write it as a file in `.reliant/presets/` instead.

### What Gets Saved

- Model (including its temperature and thinking level), tools, system prompt
- Tag (inherited from current workflow/group)

Only explicitly configured parameters are saved. Default values aren't included, so the preset works across different workflows sharing the same tag.

### Best Practices

**Name presets descriptively.** Use names indicating purpose: `fast-prototyping`, `careful-refactor`, `security-audit`. Avoid generic names like `my-preset`.

**Write useful descriptions.** Include what makes the preset different: "Lower temperature for deterministic debugging" or "Opus model for complex architectural decisions."

**Start from built-in presets.** If one is close to what you need, select it first, make adjustments, then save as new.
