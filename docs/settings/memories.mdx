Memories are markdown files that provide persistent context to every conversation in a project. They're automatically loaded and included in the system prompt, giving the AI assistant relevant background about your codebase, conventions, and preferences.

## Context Files

Reliant reads these context files on the chat's [machine](/machines/overview):

| File | Purpose | Git Status |
| --- | --- | --- |
| `~/.reliant/reliant.md` | **Global context** — your preferences for every project on that machine | Not in a repository |
| `reliant.md` in the project root | **Project context** — shared guidelines, architecture notes, conventions | Commit to repository |
| `reliant.local.md` in the project root | **Personal context** — your local notes and preferences for this project | Add to .gitignore |
| `reliant.md` in each nested repository | **Repository context** — for a project made of several repositories | Commit to that repository |
| `reliant.local.md` in each nested repository | **Personal context** for that repository | Add to .gitignore |

Every file that exists is loaded and included in every conversation. A `reliant.local.md` is read wherever a `reliant.md` is, in the project root and in each nested repository, and comes right after that `reliant.md`, so your personal notes have the last word. It is loaded even when there is no `reliant.md` beside it.

## The `reliant.md` a new project starts with

When you add a project in Reliant and it has no `reliant.md` yet, Reliant writes one in the project root, so the file exists before you have written anything. It has these parts:

- **Guidelines** and **Key Context**, two empty lists for you to fill in with your conventions and background.
- **What Reliant can do**, a short routing guide for the agent. A chat agent only knows what is in front of it, and without this section it tends to answer "run it on a cron job" or "deploy it to a server" when Reliant has a built-in way to do the same thing. The section tells the agent which Reliant feature fits which kind of request: something that should run on its own (on a schedule, from a webhook, or when a GitHub, Gmail, Slack or Twilio event arrives) is a [workflow with a trigger](/automations/overview); an agent that acts on outside services uses [integrations](/integrations/overview); work that needs a person's approval pauses the run; and code that has to keep running or be deployed (a backend, workers, cron jobs, Kubernetes operators, a CLI, a web or mobile app, a static site) is a [forge](/features/deploy-and-host) project. It also tells the agent to propose the Reliant option and say what it commits you to, to defer to any tool you named yourself, and to check the Reliant docs before recommending outside infrastructure.
- **Code navigation** and **Available Skills**, which point the agent at the code-search, Reliant configuration and workflow-building skills.

Because it is an ordinary project file, it is yours to change. Edit the routing section if your team has standards that differ ("we deploy everything to our own cluster"), trim it if you want shorter context, or delete the whole file if you would rather the agent get no such guidance. Nothing else in Reliant depends on it. A project that already has its own `reliant.md` keeps it untouched.

## What to Include

### Project Context (`reliant.md`)

Include information that benefits everyone working on the project:

```markdown
# Project Overview

Brief description of what this project does and its architecture.

## Key Patterns

- We use repository pattern for data access
- All API endpoints go through the `/api/v1` prefix
- Components follow atomic design (atoms, molecules, organisms)

## Important Files

- `src/config.ts` - All configuration
- `src/api/routes.ts` - API route definitions
- `src/db/schema.ts` - Database schema

## Conventions

- Use `pnpm` not `npm`
- Tests go in `__tests__` directories
- Prefer named exports over default exports
```

### Personal Context (`reliant.local.md`)

A `reliant.local.md` in the project root holds your personal preferences and local setup for the project. Keep it out of git (add it to `.gitignore`) so it stays yours. In a project made of several repositories, a `reliant.local.md` beside a repository's `reliant.md` does the same for that one repository. For preferences that apply to every project, use the [global context file](#global-context) instead.

```markdown
# My Setup

## Local Services

- Database: `docker compose up db`
- Backend: `pnpm dev:api` on port 3001
- Frontend: `pnpm dev` on port 3000

## Preferences

- I prefer verbose explanations
- Always suggest tests for new code
- I'm working on the authentication feature this week

## Notes

- The legacy auth system is in `src/auth/legacy` - don't modify
- Alice owns the billing module
```

## Projects with several repositories

A project can hold several git repositories side by side. Reliant finds each nested repository and loads its `reliant.md` and `reliant.local.md` as that repository's context, labelled with the repository's path, so the agent knows which rules apply where. Put what applies to the whole project in the root `reliant.md` and what applies to one repository in that repository's own file.

Together, the repositories' files (each repository's `reliant.md` and `reliant.local.md`) may take up to a tenth of the model's context window; any that don't fit are left out, and the agent is told where they are so it reads them before working in that repository. The project root's `reliant.md` and `reliant.local.md` are always included in full. Parent directories above the project are not searched.

## Best Practices

**Keep it concise** — Context files are included in every conversation. Large files consume tokens without proportional benefit.

**Update regularly** — As your project evolves, keep context files current. Outdated information is worse than no information.

**Separate concerns** — Put team knowledge in `reliant.md`, your notes for one project in its `reliant.local.md`, and preferences for every project in your global `~/.reliant/reliant.md`.

**Use structure** — Headings and bullet points are easier to scan than prose.

**Avoid secrets** — Never put API keys, passwords, or sensitive data in context files.

## Global Context

You can also add global context that applies to all projects. Create a `reliant.md` file in your global config directory:

```text
~/.reliant/reliant.md
```

This is useful for personal preferences that should apply everywhere:

```markdown
# Global Preferences

- I prefer concise responses
- Always use TypeScript, never plain JavaScript
- Include examples with explanations
```

Global context is loaded before project context, so project-specific context can override global defaults.
