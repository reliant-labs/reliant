Memories are markdown files that provide persistent context to every conversation in a project. They're automatically loaded and included in the system prompt, giving the AI assistant relevant background about your codebase, conventions, and preferences.

## Context Files

Reliant reads these context files on the chat's [machine](/machines/overview):

| File | Purpose | Git Status |
| --- | --- | --- |
| `~/.reliant/reliant.md` | **Global context** — your preferences for every project on that machine | Not in a repository |
| `reliant.md` in the project root | **Project context** — shared guidelines, architecture notes, conventions | Commit to repository |
| `reliant.local.md` in the project root | **Personal context** — your local notes and preferences for this project | Add to .gitignore |

Existing files in these locations are included in conversations unless a workflow explicitly excludes automatic saved memories. The root `reliant.local.md` comes after the root `reliant.md`, so your personal notes have the last word; it is loaded even when there is no `reliant.md` beside it.

## The `reliant.md` a new project starts with

When you add a project in Reliant and it has no `reliant.md` yet, Reliant writes one in the project root, so the file exists before you have written anything. It has these parts:

- **Guidelines** and **Key Context**, two empty lists for you to fill in with your conventions and background.
- **Code navigation** and **Available Skills**, which point the agent at the code-search, Reliant configuration and workflow-building skills.

Because it is an ordinary project file, it is yours to change: edit it, trim it, or delete it. Nothing else in Reliant depends on it. A project that already has its own `reliant.md` keeps it untouched.

## What Reliant can do

Separately from your memory files, Reliant gives every conversation, in every project, a short routing guide. A chat agent only knows what is in front of it, and without this guide it tends to answer "run it on a cron job" or "deploy it to Vercel" when Reliant has a built-in way to do the same thing. The guide tells the agent which Reliant feature fits which kind of request: something that should run on its own (on a schedule, from a webhook, or when a GitHub, Gmail, Slack or Twilio event arrives) is a [workflow with a trigger](/automations/overview); an agent that acts on outside services uses [integrations](/integrations/overview); work that needs a person's approval pauses the run; and anything that will be deployed is a [forge](/features/deploy-and-host) project. That includes a frontend with no backend (a landing page, a marketing or docs site, a single-page app or a PWA) as much as a backend, workers, cron jobs, Kubernetes operators, a CLI or a mobile app. It also tells the agent to propose the Reliant option and say what it commits you to, to use any tool or platform you named yourself, and to check the Reliant docs before recommending outside infrastructure.

The guide comes with Reliant rather than living in a file, so every project gets the current version, including projects created before it existed. Your own memory still has the last word: if your team has standards that differ ("we deploy everything to our own cluster"), say so in `reliant.md` and the agent follows it.

Projects created by older versions of Reliant had a copy of this guide written into their `reliant.md`, under a `## What Reliant can do` heading. Reliant leaves that file alone on disk but skips that section when it loads your memory, so the agent reads only the current guide. You can delete the section from the file whenever you like.

## What to Include

### Project Context (`reliant.md`)

Include information that benefits everyone working on the project:

```markdown
# Project Overview

Brief description of what this project does and its architecture.

## Key Patterns

- We use repository pattern for data access
- All API endpoints go through the `/api/v1` prefix
- Components follow atomic design (atoms, molecules, organisms)

## Important Files

- `src/config.ts` - All configuration
- `src/api/routes.ts` - API route definitions
- `src/db/schema.ts` - Database schema

## Conventions

- Use `pnpm` not `npm`
- Tests go in `__tests__` directories
- Prefer named exports over default exports
```

### Personal Context (`reliant.local.md`)

A `reliant.local.md` in the project root holds your personal preferences and local setup for the project. Keep it out of git (add it to `.gitignore`) so it stays yours. For preferences that apply to every project, use the [global context file](#global-context) instead.

```markdown
# My Setup

## Local Services

- Database: `docker compose up db`
- Backend: `pnpm dev:api` on port 3001
- Frontend: `pnpm dev` on port 3000

## Preferences

- I prefer verbose explanations
- Always suggest tests for new code
- I'm working on the authentication feature this week

## Notes

- The legacy auth system is in `src/auth/legacy` - don't modify
- Alice owns the billing module
```

## Projects with several repositories

A project can hold several git repositories side by side. Reliant still discovers nested repositories, but it does not automatically include their `reliant.md` or `reliant.local.md` files in model context. Put project-wide guidance in the project root's memory; for repository-specific instructions, point the agent to the relevant file there and ask it to read that file before working in the repository. Those files remain accessible to an agent with filesystem access.

This change does not affect discovery of nested repository skills or presets. Parent directories above the project are not searched for project memory.

## Best Practices

**Keep it concise** — Context files are included in every conversation. Large files consume tokens without proportional benefit.

**Update regularly** — As your project evolves, keep context files current. Outdated information is worse than no information.

**Separate concerns** — Put team knowledge in `reliant.md`, your notes for one project in its `reliant.local.md`, and preferences for every project in your global `~/.reliant/reliant.md`.

**Use structure** — Headings and bullet points are easier to scan than prose.

**Avoid secrets** — Never put API keys, passwords, or sensitive data in context files.

## Global Context

You can also add global context that applies to all projects. Create a `reliant.md` file in your global config directory:

```text
~/.reliant/reliant.md
```

This is useful for personal preferences that should apply everywhere:

```markdown
# Global Preferences

- I prefer concise responses
- Always use TypeScript, never plain JavaScript
- Include examples with explanations
```

Global context is loaded before project context, so project-specific context can override global defaults.
