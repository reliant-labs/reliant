A **connector** is anything that lets an agent reach beyond your repository. Reliant has two kinds, and the **Connectors** page under **Agents** puts them side by side as two tabs, **Integrations** and **MCP servers**. Each tab is the same list you get in **Settings → Integrations** and **Settings → MCP Servers**, so you can manage either from either place.

## Integrations

An [integration](/integrations/overview) connects Reliant to GitHub, Gmail, Slack, Twilio or any HTTP API. A workflow can **act** through it (open an issue, send an email, post a message) and **listen** to it (start a run when an issue is opened or a message arrives). Integrations run on Reliant's servers, not on a sandbox, which is why they also work in [no-machine runs](/automations/no-machine-runs) that fire while your laptop is shut.

To add one, choose **Connect** on the Integrations tab and pick the service. GitHub, Gmail, Google Calendar, Google Sheets and Slack send you through the service's own consent screen; Twilio takes its Account SID and Auth Token, and the HTTP integration takes an API key. Reliant checks the connection works before it saves it, and labels it with the account's name. You can keep several connections to one integration, such as two Slack workspaces. Each has its own page: [GitHub](/integrations/github), [Gmail](/integrations/gmail), [Google Calendar](/integrations/google-calendar), [Google Sheets](/integrations/google-sheets), [Slack](/integrations/slack), [Twilio](/integrations/twilio), [HTTP](/integrations/http).

## MCP servers

[MCP servers](/settings/mcp-servers) implement the Model Context Protocol, an open standard for giving an assistant extra tools and context: a filesystem server, a database, a browser, an internal API. They are standalone programs, and the agent sandbox starts them. Reliant reads their configuration from `mcp.json` files at three scopes: global (`~/.reliant/mcp.json`), project (`<project>/.reliant/mcp.json`) and project-local and gitignored (`<project>/.reliant.local/mcp.json`). Later scopes override earlier ones. The MCP servers tab lists them with their status and last error, and **Add Custom** takes a name, a stdio or SSE transport, a command or URL, arguments and environment variables, and the scope to save to.

## Which one to use

| You want an agent to… | Use |
|---|---|
| Open pull requests, comment on issues, post to Slack, send email or SMS | An integration |
| Start a workflow when something happens in one of those services | An integration trigger |
| Do either of the above with no computer of yours online | An integration, in a [no-machine run](/automations/no-machine-runs) |
| Query a database, read local files or drive a tool that lives on your sandbox | An MCP server |
| Use a third-party tool that ships as an MCP server | An MCP server |

Because MCP servers run on the sandbox, a chat or run with no sandbox doesn't have them. Integrations are available either way.

## Limits

An integration is an account you authorised, so it can only do what that account's permissions allow, and a revoked token needs a reconnect. An MCP server runs with the access of the sandbox it starts on, and credentials in its environment belong to that sandbox. A project-scope `mcp.json` is committed with the repository, so never put a secret in it: reference an environment variable (`"GITHUB_TOKEN": "${GITHUB_TOKEN}"`) or use the gitignored project-local scope.
