title: "GitHub"
description: "Act on repositories, issues and pull requests, and start runs when they change"

The GitHub integration lets a workflow or agent act on GitHub as you, and start a run when something happens in a repository. It is separate from the [GitHub connection used to clone and push](/features/git-integration); both can be connected, and neither needs the other.

## Access

Reliant acts through the Reliant GitHub App, signed in as you. What it can do is the intersection of the App's permissions and what you can see, and only in repositories where the App is installed. GitHub answers a repository the App cannot reach with "not found" rather than "forbidden", so a **not found** error on a repository you know exists usually means the App is not installed there. A fine-grained personal access token is also accepted as a connection.

### Acting as the Reliant bot

An [automation](/automations/overview#who-an-automation-acts-as) can instead write as `reliant-labs[bot]`, the App itself, by choosing **Reliant bot** under *Writes as* when you create or edit it. The pull requests, comments and reviews then belong to the bot, so you can approve and merge what an agent opens. Reliant mints a token for the bot per call:

1. It checks that **your own account has push access** to the repository (cached for ten minutes). The bot cannot do anything you could not.
2. It looks up the App's installation for that one repository. If the App is not installed there, the write fails and says so.
3. It mints an installation token scoped to **that repository** and to only what the action needs: `issues` for comments and labels, `pull_requests` for reviews and review replies, `pull_requests` plus read on `contents` for opening a pull request. It lasts an hour and is cached until shortly before it expires.

Only writes use the bot. Reads use your own access. Every comment, review, pull request and issue the bot writes ends with a footer naming the automation and its owner. A write the bot cannot make (you cannot push, the App is not installed or lacks a permission) is an error, never a quiet fallback to your name. The one exception is a deployment that has no App key at all, which acts as the owner.

On a self-hosted deployment there is no control plane to mint tokens, so Reliant bot is refused when you save; use your own connection, or a separate bot account saved as a connection and named in the action's `connection`.

## Actions

| Action | What it does | Changes GitHub |
|--------|--------------|----------------|
| `user.get` | The account the connection acts as | no |
| `issue.create` | Open an issue with a title, body, labels and assignees | yes |
| `issue.get` | Read an issue (or a pull request's conversation) | no |
| `issue.search` | Find issues and pull requests with GitHub search syntax, such as `repo:acme/app is:open "marker"` | no |
| `issue.comment` | Comment on an issue or pull request | yes |
| `issue.comment.update` | Edit a comment by id | yes |
| `issue.comment.list` | The comments on an issue or pull request, with an optional `since` time; follows pagination | no |
| `issue.update` | Change state, title or body, or **replace** the label and assignee lists | yes |
| `issue.labels.add` | Add one label, leaving the others alone | yes |
| `issue.labels.remove` | Remove one label, leaving the others alone | yes |
| `labels.create` | Create a repository label (name, color, description). Idempotent: a label that already exists is left as it is and the result says `created: false` | yes |
| `labels.list` | The labels a repository defines, with color and description; follows pagination | no |
| `pr.get` | Read a pull request: head and base, mergeability | no |
| `pr.list_files` | The files a pull request changes, with diff hunks | no |
| `pr.create` | Open a pull request from a pushed branch, as a draft or ready | yes |
| `pr.update` | Change a pull request's title, body or base branch, or close or reopen it | yes |
| `pr.review.create` | Submit a review: comment, approve or request changes | yes |
| `pr.reviews.list` | The reviews on a pull request, with verdicts | no |
| `pr.review_comments.list` | The inline comments on a pull request's diff, with an optional `since` time | no |
| `pr.review_comment.reply` | Reply in an inline review thread | yes |
| `repo.list_for_user` | Repositories the connection can see | no |
| `app.installations.list` | The accounts the Reliant GitHub App is installed on that you can access | no |
| `app.installation_repositories.list` | Repositories the App is installed on **and** you can see, across your installations, each with its `installation_id` and `can_push` | no |
| `users.search` | Find GitHub accounts by login or name; each hit carries the numeric `id` | no |
| `user.get_by_id` | Look up an account by its numeric id | no |
| `repo.get` | A repository's metadata, including its default branch | no |
| `repo.get_content` | Read a file, or list a directory, at a branch, tag or commit | no |
| `repo.get_tree` | Every file path in a repository or directory | no |
| `code.search` | GitHub code search | no |
| `workflow.dispatch` | Run an Actions workflow that has a `workflow_dispatch` trigger | yes |
| `check_run.create` | Report a check (queued, running or finished) on one commit, which a ruleset can require. **Workflow steps only**; acts as the Reliant App | yes |
| `check_run.update` | Move a check run on, or set its conclusion and details. **Workflow steps only**; acts as the Reliant App | yes |
| `check_run.list` | The check runs on one commit, by name and App; follows pagination | no |

The four `app.*`, `users.search` and `user.get_by_id` actions are what the value types below list their options from. The two `app.*` actions need a GitHub App user token (the hosted connection, or an oauth2 connection to a GitHub App), not a personal access token.

Use them as `github/<action>@1`. Repository parameters are `owner` and `repo`, the two halves of `owner/repo`.

Every action that creates or updates something returns the object's `id`, its GraphQL `node_id` and its `html_url`, so a later step can refer to it or recognise it. The list actions follow GitHub's pagination (up to 1,000 items; `issue.search` returns one page and takes `page`) and return `{items: [...]}`. Each item names its author by `user` (the login) and `user_id` (the number, which GitHub never reuses).

### Value types

GitHub defines types a workflow input can have, so a form can offer the right choices instead of a text box. A value is a plain string; `multi: true` makes an input a list.

| Type | Value | Picker lists |
|---|---|---|
| `github.repository` | `owner/name` | Repositories the App is installed on that you can see (`app.installation_repositories.list`). A repository outside that set never fires an automation. Warns when the Reliant bot is writing somewhere you lack push access |
| `github.label` | the label name | The labels of a repository, taken from a `repository` scope. A label that does not exist yet is accepted |
| `github.user` | the numeric account id, as a string | Accounts matching what you type. Stored by id because a login can be renamed and claimed by someone else |
| `github.installation` | the numeric installation id, as a string | The accounts the App is installed on. Narrows `github.repository` |

```yaml
inputs:
  repos:
    type: github.repository
    multi: true
    required: true
  skip_label:
    type: github.label
    scope: { repository: repos }
    default: skip-review
```

An agent can read any of them with `get_integration_schema github.repository`.

**Where the types come from.** `github.repository` lists the repositories the Reliant GitHub App is installed on that you can see, not every repository your account can reach (`repo.list_for_user`). That is deliberate: it is the set GitHub events are delivered for, so a repository you can pick is one an automation can fire for. Each option carries whether you can push there, and when a workflow writes as the Reliant bot the picker warns about repositories where you lack push access, because the bot writes only where you can. A stored value that is no longer listed (the App was removed, the repository renamed) stays visible, marked as no longer reachable, until you change it.

**Types on events.** Event attributes carry types too: `repository` is a `github.repository`, `label` a `github.label`, and `sender_id` a `github.user` (the numeric id of whoever acted). A trigger can scope by an input of the matching type, and validation checks the two agree:

```yaml
inputs:
  repos:
    type: github.repository
    multi: true
    required: true
    min_items: 1
triggers:
  - name: pr-opened
    integration:
      integration: github
      events: [pull_request.opened]
      match: {repository: {input: repos}}   # only the repositories the user picked
```

The event is routed only when its `repository` is one of the input's values, so an event for any other repository is dropped before anything is recorded, and a scope with no values matches nothing. Mark the input `required` so it must be chosen when the automation is turned on; an automation missing it shows **Needs setup**. `match` entries combine: a literal (`is_pull_request: "true"`) and an input scope can sit side by side, and the trigger's `filter` still runs afterwards for anything a scope cannot say (drafts, labels, who sent it).

`github.user` values are numeric ids as strings, so `trigger.sender.id in trigger.activation.params.trusted_ids` works unchanged.

### Labels: add and remove, don't replace

`issue.update` sets the **whole** label list. Two runs that each read the labels, change them and write them back can undo each other. `issue.labels.add` and `issue.labels.remove` each send one request for one label and GitHub applies it on its own, so use them to claim a task (`agent:in-progress`) or release it. `issue.labels.remove` on a label the issue does not carry fails with *not found*.

### Creating a pack's labels

`issue.labels.add` creates a missing label, but with GitHub's default color and no description. To set a pack up, create its labels first with `labels.create`; it is safe to run on every setup because GitHub's "already exists" answer is treated as success and nothing about the existing label changes (use `labels.list` to read its color). Any other failure, such as a missing permission, still fails.

```yaml
- id: ensure_ready_label
  type: action
  uses: github/labels.create@1
  with:
    owner: acme
    repo: app
    name: "agent:ready"
    color: "0e8a16"
    description: An agent may pick this up
```

### Pull requests are created without labels

GitHub's API opens a pull request with no labels. After `pr.create`, add them with `issue.labels.add` and the returned `number`.

### Merging is deliberately not an action

There is no merge action, and `pr.update` cannot merge, whatever it is given. A person merges. Approving stays available through `pr.review.create` with the `APPROVE` verdict, so whether a workflow may approve is something you decide in the workflow.

### Check runs come from the App

GitHub lets only an App write a check run, so `check_run.create` and `check_run.update` work only in an automation that acts as the Reliant App (its acting identity); acting as its owner, GitHub answers 403. The bot's token for them carries the `checks` permission alone. They are workflow steps, never agent tools: what a check reports about a commit is the workflow's record, not something an agent may post about its own work.

A check is tied to one exact commit (`head_sha` is the full 40-character SHA), so a push leaves the new head with no passing run. A branch ruleset can require a check by name **from the Reliant App**. In a repository with a merge queue, the required check must also be reported on each merge group's commit: trigger on `check_suite.requested` with `branch` starting `gh-readonly-queue/`, and report there.

### Unattended runs

Automation runs have nobody watching them, so an unattended run is not handed an action that changes GitHub (the **yes** rows above) unless the workflow step names it in its `tools`. Read-only actions are always reachable. See [Unattended by design](/automations/overview#unattended-by-design).

## Events

| Trigger | `events` value |
|---------|----------------|
| Issue opened, closed, reopened, edited | `issues.opened`, `issues.closed`, `issues.reopened`, `issues.edited` |
| Issue labeled or unlabeled, assigned | `issues.labeled`, `issues.unlabeled`, `issues.assigned` |
| Comment on an issue or pull request | `issue_comment.created` |
| Pull request opened, reopened, updated, closed or merged, ready for review | `pull_request.opened`, `pull_request.reopened`, `pull_request.synchronize`, `pull_request.closed`, `pull_request.ready_for_review` |
| Pull request labeled or unlabeled | `pull_request.labeled`, `pull_request.unlabeled` |
| Review requested | `pull_request.review_requested` |
| Review submitted | `pull_request_review.submitted` |
| Comment on a line of a pull request's diff, or a reply in that thread | `pull_request_review_comment.created` |
| Push | `push` |
| Actions run finished | `workflow_run.completed` |
| A check finished (one job), or all of a commit's checks | `check_run.completed`, `check_suite.completed` |
| A commit (a push, or a merge queue's merge group) asks the App for its checks | `check_suite.requested` |

Each event's payload is declared, so `get_integration_schema` lists it and validation checks a trigger's `filter`, `inputs` and `prompt` against it: reading a top-level key the event never carries (`data.issue` on an inline diff comment) is an error before the trigger fires. Lists of names, such as `issue.labels` and `pull_request.labels`, hold strings.

You can narrow a trigger with `match`, either to a fixed value (`repository: acme/app`) or to an input's values (`repository: {input: repos}`, see [Value types](#value-types)). Every event carries `repository` (`owner/name`), `installation_id`, `sender`, `sender_id` (the numeric id of whoever acted, which survives a rename) and `action`; individual events add more:

| Attribute | On |
|-----------|----|
| `label` | `issues.labeled`, `issues.unlabeled`, `pull_request.labeled`, `pull_request.unlabeled` |
| `assignee` | `issues.assigned` |
| `branch`, `base_branch` | every pull request event, `pull_request_review.submitted`, `pull_request_review_comment.created` |
| `merged` | `pull_request.closed` |
| `requested_reviewer` | `pull_request.review_requested` |
| `state` | `pull_request_review.submitted` (`approved`, `changes_requested`, `commented`) |
| `mentions_reliant` | `issue_comment.created`, `pull_request_review_comment.created` |
| `is_pull_request` | `issue_comment.created` |
| `is_reply` | `pull_request_review_comment.created` (`"true"` for a reply, `"false"` for the first comment of a thread) |
| `branch`, `tag` | `push` (one or the other) |
| `conclusion`, `branch` | `workflow_run.completed`, `check_run.completed`, `check_suite.completed` |
| `workflow` | `workflow_run.completed` |
| `name`, `app` | `check_run.completed` (the check's name, and the slug of the App that ran it, `github-actions` for Actions) |
| `app` | `check_suite.completed`, `check_suite.requested` |
| `branch` | `check_suite.requested` (a merge group's is `gh-readonly-queue/<base>/pr-<number>-<sha>`) |

Boolean-like attributes are the strings `"true"` and `"false"`; quote them in YAML.

Comments written by **Reliant's own bot** never fire `issue_comment.created` or `pull_request_review_comment.created`, so a run that comments or replies as the bot cannot trigger itself. Comments from any other bot (Dependabot, a CI app, a review tool) do fire them: filter on `trigger.sender` if you want to ignore one. The bot is recognised by its numeric GitHub id, never its login; a deployment with its own App sets `RELIANT_GITHUB_BOT_USER_ID` to that bot's id.

### Your workflow's own writes

Every other event a run can cause (a label it adds, a pull request it opens, a review it submits, a push it makes) does reach your triggers, and a workflow that writes to what it watches would otherwise hear itself. Reliant records each mutating GitHub action a run makes before it makes it, then attributes the webhook that follows. That is `trigger.origin`, and by default a trigger ignores events its own workflow's runs caused:

```yaml
# The default, written out:
origin_filter: "!(trigger.origin.same_workflow && trigger.origin.confidence in ['exact', 'intent'])"
```

What the webhook carries, and so what an event is matched on:

| Event | Matched on |
|-------|------------|
| `issue_comment.created`, `pull_request_review.submitted`, `pull_request_review_comment.created` | The comment's or review's own id (`exact`), else the pull request or issue it is on plus a digest of its full body (`intent`) |
| `pull_request.opened` | The head branch of a `pr.create` (`intent`), then the pull request's own number (`exact`) |
| `issues.labeled`, `issues.unlabeled`, `pull_request.labeled`, `pull_request.unlabeled` | The issue or pull request and the label (`intent`) |
| `pull_request.synchronize`, `push` | The pull request or branch and the head commit (`intent`), or a `Reliant-Run:` commit trailer (`claimed`) |

The digest is of the whole body as written, before the recorded payload truncates long text, and ignores the line-ending and trailing-space changes GitHub makes. A write that provably failed (a 4xx) is not matched; one that may have been applied (a timeout, a 5xx) is.

An event Reliant's GitHub App caused but no recorded write explains is `app`: Reliant did it, run unknown. It is not treated as the workflow's own, so the default lets it through; write `origin_filter: "!trigger.origin.caused_by_reliant"` to ignore it as well. See [Telling your own writes apart](/automations/overview#telling-your-own-writes-apart) for the full field list, `origin_filter` examples and the loop cap.

Writes an agent makes through its shell (`gh`, `git push`) are not recorded and look, to GitHub, like you. Do the writing in an action node, or a push's `Reliant-Run:` trailer is the only thing marking it, and that can only be a reason to ignore an event, never to trust one.

### What the GitHub App needs

These are the App's settings, made once by whoever owns it. On Reliant's hosted deployment that is Reliant.

| Setting | Value |
|---------|-------|
| Repository permission: Metadata | Read |
| Repository permission: Issues | Read and write |
| Repository permission: Pull requests | Read and write |
| Repository permission: Contents | Read and write |
| Subscribe to events | Issues, Issue comment, Pull request, Pull request review, Pull request review comment, Push, Workflow run, Check run, Check suite |

The `labeled`, `unlabeled`, `reopened` and `review_requested` actions arrive under the **Pull request** and **Issues** events, so they need no separate subscription. Without the Pull request review comment, Check run and Check suite subscriptions, those three triggers never fire; without Contents write, the bot cannot open a pull request. After changing permissions, every installation has to accept the update before it takes effect.

## Example: review each new pull request

```yaml
name: pr-reviewer
description: Review each pull request when it is opened and comment on it
entry: [review]

inputs:
  pull_number:
    type: integer
    default: 0
    description: The pull request to review (set by the trigger)
  repo_full_name:
    type: string
    default: ""
    description: owner/name of the repository (set by the trigger)

triggers:
  - name: pr-opened
    integration:
      integration: github
      events: [pull_request.opened]
      match:
        repository: acme/shopfront
    inputs:
      pull_number: "{{ trigger.payload.data.pull_request.number }}"
      repo_full_name: "{{ trigger.payload.data.repository.full_name }}"
    prompt: "Review pull request #{{ trigger.payload.data.pull_request.number }} in {{ trigger.payload.data.repository.full_name }}"

nodes:
  - id: review
    type: workflow
    ref: builtin://agent
    args:
      tools: ["tag:web"]
```

The agent here is limited to web tools so the example needs no machine. Give it the integration's tools or a machine with a checkout if it should read the diff and post the review itself.
