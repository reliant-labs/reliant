# Runbook — reliant

What to do when reliant's servers alert or misbehave. reliant does not deploy
itself: control-plane deploys it (prod on GKE, its dev stack on k3d) and owns
the platform runbook, `docs/runbook.md` in the control-plane repository. This
file covers what belongs to reliant. Internal: `docs/.mintignore` keeps it off
the docs site.

## The server roles

One binary, `reliant`, runs as three roles plus a migration job
(`deploy/kcl/workloads.k`). Each role's `service.name` in traces, metrics and
logs is its workload name (`dev-docs/observability.md`).

| Workload | Command | What it does | Serves |
|---|---|---|---|
| `reliant-migrate` | `reliant db migrate up` | Applies `db/migrations` before the other workloads start | — |
| `reliant-api-server` | `reliant server api` | Every `reliant.v1.*` Connect service, for the web app, Electron, the CLI and the SDK | `:9090` (grpc) |
| `reliant-temporal-worker` | `reliant server worker` | Temporal workflows and activities: chat turns, `call_llm`, tool execution, spawns | nothing; it only dials out |
| `daemon-gateway` | `reliant server gateway` | The bidirectional stream every daemon dials; tool calls reach daemons over NATS | `:9190` (grpc) |

The API, worker and gateway need Postgres and NATS, and the API and worker
also need Temporal. None of them can reach a user's files. Only the daemon,
which may run on another machine, can.

## Health

Every role serves its probes on `HEALTH_PORT`, a listener separate from the
serving port. In a pod that is `8081` for all three roles. Unset, the
gateway's default is `8080` and the other roles' is `8081`.

| Path | Meaning |
|---|---|
| `/health`, `/healthz` | Liveness: the process is up. Failing it restarts the pod |
| `/ready`, `/readyz` | Readiness: dependencies are reachable. Failing it only takes the pod out of traffic, and restarts nothing |

control-plane's probes (kubelet, the GKE health check) use `/health` and
`/ready`. `/healthz` and `/readyz` are forge's names for the same checks, the
ones `forge project doctor` uses (`LIVENESS_PATHS` and `READINESS_PATHS` in
`proto/reliant/config/v1`). The JSON `/health` the web client reads is a
different endpoint, on the API's serving port.

## Where to look

- **Prod telemetry:** the forge console, https://forge.reliantlabs.io
  (sign-in required). Prod is control-plane's env, so run
  `reliant forge obs status prod` and `reliant forge obs check prod` from a
  control-plane checkout.
- **Dashboards:** `deploy/observability/dashboards/`. `reliant-overview.json`
  is hand-written. `reliant-frontend_gen.json` and the per-service alert specs
  in `deploy/observability/spec/` are regenerated by `forge generate`.
- **Dev stack logs:** `.forge/logs/dev/<workload>.log` in the checkout that ran
  `forge env up dev`. The browser console is in `frontend_web.log`, as
  `[browser:<level>]` lines. `./.reliant/tools/log-search.sh --errors` greps all
  of them. The `dev-logs` skill has the full map, including control-plane's
  stack.
- **Past incidents:** `dev-docs/incidents/`.

## Alerts

forge's built-in rules, with their thresholds, are in
`deploy/observability/alert-defaults_gen.json`. These are the reliant-specific
first checks:

- **ServiceErrorRateHigh** (more than 5% server errors over 5m, critical).
  Open the service's dashboard to see which rpc and which `code`. Then read
  that `procedure`'s ERROR logs and follow a `trace_id`. If a release just
  rolled out, `reliant forge obs check prod` judges it.
- **ServiceLatencyP95High** (p95 above 1s over 10m). In a slow trace, every
  SQL statement is a span. A slow chat turn is usually the
  worker (`call_llm`, tool execution), not the API.
- **ServiceSilent on `daemon-gateway`**. Daemons are not connecting. Check the
  gateway's readiness and its NATS connection before anything in the daemon.
- **WorkloadCrashLooping or OOMKilled**. Read the workload's last log lines
  before the restart. Prod resources are control-plane's
  (`deploy/kcl/lib/resources.k` there).
- **ReleaseRegressed or DeployFailed**. Releases and rollbacks belong to
  control-plane's `rc-train` workflow. See control-plane `docs/runbook.md`,
  "Releases: the rc-train workflow cuts and promotes".

## Database

reliant's tables (chats, projects, worktrees, threads, messages, …) live in
their own database on control-plane's prod Postgres. Backups, restore and
point-in-time recovery are in control-plane `docs/runbook.md`, "Database
recovery (prod)". Schema changes are forward-only forge migrations
(`db/migrations/`). Each one declares whether the previous release survives it
(`-- forge:backward-compatible` or `-- forge:breaks-rollback`), so read that
line first before rolling back past one.
