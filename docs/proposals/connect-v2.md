# Proposal: connect-go v2 support, side by side with v1

**Status:** implemented in two PRs (section 4(i)); the API reference at the end is taken from the implementation. The forge owner approved the move (v1 and v2 supported side by side). The decisions in section 7 are still open.
**Date:** 2026-11-19
**Scope:** forge (`pkg/`, templates, codegen, CLI, analyzers). Sections 5 and 6 describe how projects and the two consumers (reliant, control-plane) migrate afterwards; that work is not part of the forge PR.

## 1. Summary and why

forge generates and runs Connect RPC services on `connectrpc.com/connect` v1. connect-go v2 (`connectrpc.com/connect/v2`, currently v2.0.2) is a redesign of the Go API on the same wire protocol. forge's own `go.mod` already requires both majors (`connect v1.21.1`, `connect/v2 v2.0.2`, `otelconnect v0.12.0`, `vanguard v0.5.0`); `pkg/serverkit/rest.go` already uses v2 as the vanguard bridge. What is missing is everything else: generated code, `forge/pkg`, tool installation, analyzers.

What v2 gives a forge project:

- **Simple-style handlers.** A handler is `func(ctx, *pb.Req) (*pb.Resp, error)`. No `connect.Request[T]` / `connect.Response[T]` wrappers, no `.Msg`, no `connect.NewResponse`. Most of forge's generated handler code (CRUD shims, scaffolded stubs, tdd rows) gets shorter.
- **Uniform function interceptors.** `connect.ServerInterceptor` and `connect.ClientInterceptor` are `func(next) next` over every RPC kind. forge's ~45 interceptor constructors stop having to implement three methods (unary, streaming client, streaming handler) each.
- **`CallInfo` metadata.** Headers, trailers and peer address are read from a `*connect.CallInfo` on the context instead of from request/response wrappers.
- **Bounded read limits by default.** 4 MiB per message on servers and clients; v1 was unbounded, so any caller could make a server buffer an arbitrary message.
- **Plain errors never leak.** An error returned from a handler that is not a `*connect.Error` is not serialized in v2. In v1 its `Error()` text reached the client as `CodeUnknown`.
- **In-process transport.** `connectinprocess` connects a client to a `*connect.Server` without a listener, which makes forge's generated component tests faster and less flaky.
- **vanguard v0.5 is native.** vanguard v0.5 is v2-only and mounts REST routes straight from a `*connect.Server`; a v2 project needs no v1-to-v2 bridge.

connect-go v1 remains supported upstream (fixes and security updates on the v1 branch). Nothing here forces a project off v1. This proposal makes v2 available, keeps v1 fully working, and gets the two consumers onto v2 on their own schedule.

## 2. Constraints

1. **forge is semver, major locked at 1.** A forge release must not break a project that is still on connect v1. Every v1 symbol in `forge/pkg` keeps its signature and behaviour; every v1 template keeps rendering for a v1 project. v1 tests pass unmodified.
2. **The wire must not change.** reliant and control-plane serve web (connect-es), Electron, the Go SDK and old daemon builds that are already deployed. Header names, content types, envelope flags, error JSON, gRPC trailers and codecs are identical in v1 and v2 (`wire-compat.md`). Only defaults differ; section 4(e) pins each.
3. **One major per project.** The v1 and v2 `protoc-gen-connect-go` plugins emit the same package name (`<pkg>v1connect`) and the same file name, so one project generates one major. Mid-migration, a module can import both runtimes (v2 says so), but its generated packages are one or the other.
4. **No `Deprecated:` marker yet.** consumers run staticcheck SA1019 on non-test code, so a machine-readable marker on v1 `forge/pkg` APIs would turn every v1 consumer's lint red when it pins the release. v1 APIs get a prose note in this release (section 4(f)).
5. **forge's own lint rollout rule applies.** A new lint rule or a tightened one needs a row in `internal/cli/lint/lint_rollout_table.go` and warns before it gates.

## 4. Design

### (a) Connect major selection

A new small package `internal/connectmajor` answers one question per project: v1 or v2.

**Detection rule.** Parse the project root `go.mod` with `golang.org/x/mod/modfile` (forge already does this in several places; no shared helper exists today). The project is **v2 if and only if `connectrpc.com/connect/v2` is a direct require** (no `// indirect` comment). Otherwise it is v1. A direct require of both v1 and v2 is v2: a repository in the middle of the migration chose v2 by running `go get connectrpc.com/connect/v2` (step 1 of section 5).

Presence alone is not a signal. otelconnect v0.12 and vanguard v0.5 pull the other major in as an indirect dependency, so most v1 projects that pin a recent forge already have `connect/v2` in `go.sum`. Keying on the direct require keeps every existing project on v1 with no action.

A root `go.mod` with no connect require, or no `go.mod` at all, is v1; there is no `gen/go.mod` fallback (the detector reads one file). There is **no `forge.yaml` override**, deliberately: `go.mod` is the declaration, and a second source could disagree with what the module compiles against. The one case an override would serve (a v1 project that directly requires `connect/v2` for an unrelated reason, for example to use `connectinprocess` in one test) is met by keeping that require indirect or by migrating. If it turns up in dogfooding an override can be added later without breaking anything.

`connectmajor.Detect(dir)` returns a `Major` exposing `RuntimeImport()`, `PluginModule()` and `VersionModule()`. It is computed once per `forge generate` in `pipelineContext` (`internal/cli/generate_pipeline.go`) and passed to codegen (`ServiceTemplateData`, project and bootstrap template data, `routesView`) as a `ConnectV2 bool` plus the runtime import path; `generator.ProjectGenerator` gets it for birth files. Go emitters (`generator.go`, `scaffold/rpc.go`, `crud_gen.go`, `service_stub_gen.go`) branch on it.

**Plugin install.** `requiredProtoTools` in `internal/cli/tools.go` becomes a function of the major:

| Major | `Module`                                              | `VersionModule`             |
| ----- | ----------------------------------------------------- | --------------------------- |
| v1    | `connectrpc.com/connect/cmd/protoc-gen-connect-go`    | `connectrpc.com/connect`    |
| v2    | `connectrpc.com/connect/v2/cmd/protoc-gen-connect-go` | `connectrpc.com/connect/v2` |

The binary name is `protoc-gen-connect-go` for both, which is why `buf.gen.yaml` needs no edit and why the cache must not key on the name. The installed-tool cache key (`generate_cache.go`, `generate_toolpins.go`) includes the module path and the resolved version, so a v1 binary can never satisfy a v2 lookup. The bootstrap script in `generator/dx_files.go` installs the module for the project's major (and stops using `@latest`: it resolves the go.mod version like `generate` does). The `tools.go.tmpl` blank import and the preflight's `goToolPackageHint` follow the major.

**One major per project.** Because the plugins emit the same package and file names, a project cannot mix generated majors. Mid-migration, hand-written code may import both runtimes (v2 allows it); the generated packages are whichever major `forge generate` last ran for. `forge generate` refuses nothing here; the build tells you if `service.go` and `_gen.go` disagree.

### (b) `forge/pkg` layout

**Same package, new symbols, `V2` suffix.** The v2 variant of exported symbol `X` is `XV2`:

```go
svcerr.Interceptor()   connect.Interceptor            // unchanged
svcerr.InterceptorV2() connectv2.ServerInterceptor    // new
observe.Chain(...)     []connect.Interceptor          // unchanged
observe.ChainV2(...)   []connectv2.ServerInterceptor  // new
serverkit.ChainDeps    / serverkit.ChainDepsV2
```

Inside `forge/pkg`, v2 imports use fixed aliases: `connectv2 "connectrpc.com/connect/v2"`, `"connectrpc.com/connect/v2/connecthttp"`, `connectv2proto "connectrpc.com/connect/v2/connectproto"`. v1 stays `"connectrpc.com/connect"`. `XV2` means the server side. A client-side variant is spelled `XClientV2` where the v1 type was used on both sides and the distinction matters.

**Connect-neutral symbols where v2 has no connect type.** v2 simple handlers are `func(ctx, *Req) (*Resp, error)`. For `crud.Handle*`, `tdd.Case` and `tdd.HandlerFunc` the v2 shape contains no connect type except `Code`, so a `V2` twin would be a duplicate of a neutral thing. In those cases the symbol is connect-neutral. `crud` gets `crud.Create`, `Get`, `Update`, `Delete` and `List`, each returning `func(context.Context, *Req) (*Resp, error)`; the v1 `Handle*` functions are thin wrappers over them (unwrap `req.Msg`, wrap `connect.NewResponse`) and their v1 tests pass unchanged. `tdd` is the exception that keeps the suffix: `CaseV2` carries `WantErr connectv2.Code`, so it does name a connect type, and generic types cannot be overloaded, so `CaseV2`, `RPCCaseV2`, `HandlerFuncV2`, `TableRPCV2`, `RunRPCCasesV2` and `AssertConnectErrorV2` are new names. `tdd`'s connect-free symbols (`ContractCase`, `TableContract`, `E2EClient`, `NewMock`, in-process `AssertScaffoldStub`, `WithTimeout`) are shared by both majors. The package docs state the naming choice.

**Why this layout.** It is the precedent otelconnect v0.12 set: `NewInterceptor` (v1) beside `NewServerInterceptor` (v2) in one package. It gives shared unexported internals for free (classification tables, header handling, the connect-free cores), no new import paths for consumers, predictable names for codegen and for the migration ("add `V2`"), and a mechanical rename (drop the suffix) when a future forge major retires v1. The cost is noisier godoc and a package that imports both majors; both are already in forge's go.mod.

Rejected alternatives:

- **Sibling subpackages (`pkg/svcerr/svcerrv2`, ...).** Clean godoc, but ~14 new packages in `project libraries`, shared internals would have to move to `internal/` cores, and generic types still need their own package-qualified copies. Rejected as more surface for no semantic gain. `tdd` kept the `V2` suffix for the same reason (its generic types name a v2 code).
- **A parallel `pkg/v2/...` tree.** It reads like a forge major, which it is not (this is a minor release), and it either duplicates the connect-free API (two `middleware.GetUser`s, two claims contexts, so a v2 interceptor's claims are invisible to a v1 helper) or forces mixed imports. Rejected.

Dual-major error inspection is **not** a new API: `svcerr.Wrap`, `WrapOr`, `NotFound`, `Code`/`IsClassified`, `crud`'s passthrough, `authn`'s claims error and `tdd.AssertConnectError` simply recognise both majors' `*connect.Error`. `svcerr.ToConnect(v2err)` returns a v1 `*connect.Error` with the same code, message and details (a wire error when the v2 error is remote), so v1 code reading a v2 error keeps working. Connect-free packages (`orm`, `config`, `testkit.Slow`, `middleware.GetUser`/`ClaimsFromContext`/`ContextWithClaims`/`ProcedureDeadlines`, `observe.NewHTTPClient`, `serverkit.Run`/`Worker`/`Probes`/`OpenDB`) are reused as-is. `querycapture` is internal-only and gets the same dual recognition.

### (c) Interceptors per `*connect.Server`

In v1 a handler carried its options. In v2 interceptors belong to the Server, and `connecthttp.Mount(mux, server, opts...)` registers one mux pattern per procedure plus a `/pkg.Svc/` subtree per service. Several Servers can therefore share a mux as long as their services are disjoint, which is the case: a service is mounted once.

The V2 mount API builds **one Server per distinct chain**:

- `mountkit.RegistrarV2` is `interface{ RegisterV2(server *connectv2.Server) }`. A service's `RegisterV2` registers its handler on the Server it is given (`<pkg>connect.Register<Svc>Handler(server, s)`), and it coexists with the v1 `Register(mux, ...connect.HandlerOption)` on one type, which is what lets a project migrate service by service in hand-written code. HTTP and webhook registrars (`HTTPRegistrar`, `WebhookRegistrar`) are pure net/http and unchanged.
- `mountkit.MuxV2` owns the grouping. `NewMuxV2(mux, interceptors, httpOpts...)` holds the shared chain; `MuxV2.Register(register, mountOpts...)` mounts a service on the shared Server when the mount carries no per-mount options of its own, and otherwise on a Server of its own (shared chain, then the mount's `WithInterceptorsV2`, which sits inside the shared chain). The shared Server is `connecthttp.Mount`-ed incrementally through a pattern filter, so services still register one at a time. `Register` returns the proto service names from the Server's specs, the same values a v1 mount returns. `RegisterServiceV2(m, svc, mountOpts...)` is the `RegistrarV2` + `HTTPRegistrar` + `WebhookRegistrar` composite of v1's `RegisterService`. `NewMuxV2` prepends `connecthttp.WithReadMaxBytes(0)` so an unset limit is v1's unbounded.
- `serverkit.Server` gains `ServerInterceptors`, `HTTPOptions` and `ChainV2` beside `HandlerOpts` and `Chain`; `Server.Mount(path, svc, ...)` type-switches (a `RegistrarV2` on a v2-configured Server goes through `RegisterServiceV2`; one major's service on a Server configured only for the other panics rather than silently dropping its chain). `serverkit.RoutesV2` is `interface{ RegisterV2(mux *mountkit.MuxV2) []string }` (`RoutesFuncV2` adapts a func), and `ListenerDeps` takes `ChainV2` and `RoutesV2` beside the v1 pair; both pairs on one mux is allowed when the audiences match.
- The generated mounts (`mounts_services_gen`, `routes_gen`, `providers-graph`, `cmd-svc-mount-gen`) take a `*mountkit.MuxV2` in place of `(mux, opts ...connect.HandlerOption)` and call `m.Register(svc.RegisterV2, ...)`; the grouping lives in `MuxV2`, so the templates do not compute chains themselves.

Interceptor order is unchanged: in both majors the first interceptor is outermost (v2: `connect.go`, "interceptors fire in argument order. The first wraps the outermost call").

### (d) Interceptor identity: slots, not func comparison

v1 code compares interceptor interface values in two places: `svcerr.IsInterceptor`/`WithInterceptor` (is the svcerr interceptor already in this slice?) and the `serverkit.Omit` sentinel (a type implementing `Interceptor`, used to omit a slot). v2 interceptors are funcs and are not comparable.

The design is that identity lives in the chain builder, not in the interceptor value:

- **Slots are a nil default plus a `NoX bool` field.** `ChainDepsV2` keeps the named slots `ChainDeps` has (`Trace`, `Deadline`, `Audit`, `RateLimit`, `Activity`, `StreamDrain`, `Validate`, plus the `Outer` and `Extras` lists). A nil interceptor field means "forge's default"; `NoAudit`, `NoTrace`, `NoActivity`, `NoStreamDrain`, `NoValidate`, `NoDeadline` drop the slot; setting a slot and its `NoX` is an error. `RateLimit` nil means none. The deadline slot is three fields because v1 overloaded it: `Deadline` (a value; zero is the forge default), `DeadlineOverride` (a non-nil func replaces the forge interceptor in the same position, v1's "any non-`Deadline` interceptor in `Deps.Deadline`") and `NoDeadline`. Nil entries in `Outer`/`Extras` are errors, as in v1. No `Omit` sentinel exists in v2.
- **`svcerr.InterceptorV2` is installed by position, not by identity.** It is idempotent: a second copy sees an error the first already converted and passes it through with the same verdict, and only the outermost copy running for a call delivers the verdict's metadata (4(e)). `ChainV2`/`observe.ChainV2` therefore append it unconditionally as the last (innermost) argument of `connectv2.NewServer` through `svcerr.WithInterceptorV2`, and a caller that also passed one is harmless. There is no `svcerr.IsInterceptorV2`, and nothing in v2 compares funcs. A bare `[]ServerInterceptor` assembled by hand carries no guarantee that svcerr is present, which is why `serverkit.NewChainV2` is the supported way to build one.
- `AuthenticatorV2` (`ServerInterceptor() connectv2.ServerInterceptor; Audience(); Caller()`) replaces the embedded `connect.Interceptor`, which a func type cannot satisfy. `AuthForV2` and `AuthWithCallerV2` mirror `AuthFor`/`AuthWithCaller`. A v1 interceptor was also its own claims lookup (`Claims()`); a func has no methods, so `AuthPolicyV2` and `authn.Policy.ClaimsReader()` supply the lookup, and `AuthForV2` leaves `Caller` nil, which makes the default audit and activity slots refuse rather than guess.
- Tests assert chain composition through the builder's own output (a slot-ordered description of the chain), not through func identity.

### (e) Errors and wire parity

The wire protocol is unchanged (`wire-compat.md`: header names, content types, envelope flags, error JSON, gRPC trailers, details, codecs, compression, GET handling, default protocols). The V2 builders pin the behaviours that default differently: error conversion, error metadata, read limits and the unknown-method 404.

**`svcerr.InterceptorV2` semantics.** It runs in the **same position as v1: innermost**, directly around the handler. (This is deliberate: an outermost placement would hand logging, metrics and tracing interceptors an unconverted plain error, where in v1 they see the already-classified code. In v2 the scrub happens at the transport after the whole chain returns, so any position inside the chain produces the same wire error; innermost also preserves what the rest of the chain observes.) It does what v1 does, using one shared classification core:

1. A `*connect.Error` of either major that is local passes through, as a v2 error.
2. A svcerr-classified error is converted by `ToConnectV2` (code, user-safe message, reason header and metadata, details via `connectv2proto`).
3. A context error keeps its canceled/deadline-exceeded mapping.
4. Any other plain error becomes `CodeInternal` with `svcerr.InternalMessage` and the cause attached via `WithCause` (the cause stays visible to `errors.Is` server-side and is never sent). This is exactly what v1 `svcerr.Interceptor` does today, so a deployed client sees the same message in v1 and v2.
5. **Remote-error re-localisation.** A `*connect.Error` marked `IsRemote()` that a handler returns (it came from an upstream client call) would be scrubbed by v2 to `CodeInternal`, empty message, no details. v1 passed code, message and details through. The V2 interceptor re-creates it with `connectv2.NewError(code, message)`, copies every detail with `WithDetail`, and attaches the original with `WithCause`. There is no un-remote method, so re-creation is the only way. A v1 wire error (a v1 client in the same process, `IsWireError`) is treated the same way. As in v1, metadata annotated on a remote error is withheld, not forwarded.

**Metadata delivery.** A v2 `*connect.Error` carries no metadata, while a v1 error sends `Meta()` (svcerr's reason header and `WithMetadata` entries, which frontends route on). `svcerr` keeps the reason and metadata in an unexported cause on the v2 error and writes them onto the call where v1 sends them: the **response headers** for a unary Connect-protocol call, the **trailers** otherwise (streaming Connect end-of-stream metadata, gRPC and gRPC-Web trailers). Values are **appended**, in the order and multiplicity the verdict carries them, as v1's header merge appends. Delivery happens **once per call**: the outermost `InterceptorV2` running for the call claims delivery (keyed on the call's `CallInfo`, so a nested in-process call still delivers its own), and inner copies leave it to the outer one, so a header is never doubled.

**Reading metadata on the client.** A v1 client read the metadata from the error it got back (`ce.Meta().Get(svcerr.ReasonHeader)`, Meta holding the response headers and trailers). A v2 `*connect.Error` carries none, and the headers and trailers land in the call's `CallInfo`, which code holding only the error cannot reach. `svcerr.ClientInterceptorV2()` attaches a copy of a failed call's response headers and trailers to the error (unary, and every stream operation; a gRPC trailers-only response is read from its headers alone, as v1 did), wrapping it so `errors.As` and `connect.CodeOf` see the same `*connect.Error`. `svcerr.MetaOf(err) http.Header` reads it back, and for an error that never crossed a v2 client it answers what `ToConnect` would send (a v1 wire error answers with its `Meta`), so one reader serves a handler unit test, an in-process call and a networked one: `svcerr.MetaOf(err).Get(svcerr.ReasonHeader)` replaces `ce.Meta().Get(svcerr.ReasonHeader)`. Every forge-built v2 client installs the interceptor first (`observe.ClientStackV2`, `servicecatalog.NewClientV2`, `testkit.NewConnectClientV2`, the generated e2e harness). A handler that forwards such an error still sends no upstream metadata, as v1 withheld a wire error's; `svcerr.ReasonOf` stays the server-side reader and reports no received reason.

**Interceptors that reject without calling next.** An authentication interceptor that refuses a call never reaches the innermost svcerr, so a v1 error's metadata (typically the reason a denial is routed on) would be lost. `svcerr.RejectV2(ctx, err)` is the one call such an interceptor makes: it returns the verdict as a `*connectv2.Error` and delivers the metadata by the same rules, leaving delivery to an outer `InterceptorV2` when one is running. `authn.NewInterceptorV2`, `auth`'s `ConnectInterceptorV2` and the other v2 rejecting interceptors use it; it has no v1 twin because a v1 interceptor returns the `*connect.Error` and the v1 transport sends its `Meta`.

So behind `svcerr` there is **no** wire delta for plain errors, and forge does not ship a separate "v1-compatible error interceptor" that leaks `err.Error()`: both consumers run `svcerr` in every production chain (`serverkit.NewChain`, `observe.Chain`), and v1-behind-svcerr already redacts. What needs checking in a consumer is any Server **not** built by `ChainV2` (or without `svcerr.InterceptorV2`): test servers and `wirecheck`-style harnesses (section 6).

**Read limits.** v1 was unbounded by default; v2 defaults to 4 MiB on `Mount` and `NewTransport`, and exceeding it is `resource_exhausted`. forge already passes an explicit read limit on the server path (`payloadCap` in `serverkit/chain.go`); the V2 builders map it to `connecthttp.WithReadMaxBytes(n)`, with 0 and negative values meaning unlimited (`WithReadMaxBytes(0)`), exactly as v1 treats them. When nothing is set where v1 was unbounded, the V2 builder passes `WithReadMaxBytes(0)`. forge-built v2 **clients** (`testkit`, `servicecatalog.NewClientV2`, `observe` client config) default to `connecthttp.WithReadMaxBytes(0)` unless the caller sets one, because v1 clients were unbounded. The send limit is unbounded by default in both majors and is forwarded as today. `WithCodecs` and `WithCompressors` are not exposed.

**Unknown methods keep v1's 404.** A request for an unknown method of a mounted service got a plain HTTP 404 (`404 page not found`, text/plain) from v1's generated handler, whose path switch ends in `http.NotFound`, on every protocol. `connecthttp.Mount` instead answers an RPC-shaped POST with an `unimplemented` RPC error (Connect 501 with a JSON body, gRPC `grpc-status` 12). Clients detect version skew (an older build calling an rpc a live service has retired) by that 404, so forge keeps it: `mountkit.MountV2` is `connecthttp.Mount` with each service's `/pkg.Svc/` subtree pattern served by `http.NotFoundHandler`, and `MuxV2` and `testkit.NewConnectClientV2` mount through it. The response is byte-identical to v1's over Connect, gRPC and gRPC-Web (`TestRegisterServiceV2_UnknownMethodIsV1NotFound`). An unknown service is the mux's own 404 under both majors. A v2 server mounted by hand with `connecthttp.Mount` does not get this; mount it with `mountkit.MountV2`.

### (f) Deprecation

In this release v1 `forge/pkg` symbols get a **prose** note only ("connect-go v2 projects use `XV2`"); there is no `Deprecated:` paragraph. A machine-readable marker makes `staticcheck` SA1019 fail in every consumer that lints non-test code, and a forge minor release must not turn a consumer's gate red on pin (the same reason forge's lint rules warn before they gate). The formal `Deprecated:` marker lands in a later release, after reliant and control-plane have migrated and no first-party v1 caller is left. Removal of v1 is a forge major and is the owner's decision.

### (g) What a v2 project gets from generation

- **`service.go`.** `func (s *Service) RegisterV2(server *connect.Server) { <pkg>connect.Register<Svc>Handler(server, s) }` (import `connect "connectrpc.com/connect/v2"`), satisfying `mountkit.RegistrarV2`. `RegisterHTTP` is unchanged. The file is user-owned and written once, so it has this shape only for newly scaffolded services; a migrating project adds the method by hand (section 5).
- **Handlers.** Bare-message signatures for all four rpc kinds: `Get(ctx, *pb.Req) (*pb.Resp, error)`; server stream `(ctx, *pb.Req, <Svc><Method>ServerStream) error`; client stream `(ctx, <Svc><Method>ServerStream) (*pb.Resp, error)`; bidi `(ctx, <Svc><Method>ServerStream) error`. CRUD shims call the neutral `crud` cores and read request headers through `CallInfoForServerContext` where they need them.
- **Mounts.** `mounts_services_gen`, `routes_gen`, `providers-graph` and `cmd-svc-mount-gen` take a `*mountkit.MuxV2`: `MountFunc` is `func(c *Components, m *mountkit.MuxV2, cfg *config.Config, logger *slog.Logger) []string`, each service mounts with `m.Register(svc.RegisterV2, o.<Svc>...)` plus `RegisterHTTP`/`RegisterWebhookRoutes` on `m.Mux()`, and route sets implement `serverkit.RoutesV2`. `MuxV2` does the one-Server-per-chain grouping (4(c)). The auth and chain providers use `serverkit.AuthenticatorV2`, `AuthPolicyV2` and `NewChainV2(ChainDepsV2{...})`, with `ReadMaxBytes`/`SendMaxBytes` carried over, and the listener takes `ChainV2` and `RoutesV2`. Per-service options in owned code become `mountkit.WithInterceptorsV2(...)`.
- **Middleware.** `middleware.go` scaffolds a v2 auth interceptor (`NewAuthInterceptorV2`) written in the function-type style, rejecting through `svcerr.RejectV2`; it is paired with `serverkit.AuthWithCallerV2(aud, ic, middleware.ClaimsFromContext)` only when it stashes claims where that reader looks, and with `AuthForV2` plus explicit audit and activity slots otherwise.
- **Tests.** The scaffolded unit test uses `tdd` V2 rows (`CaseV2{Req: &pb.X{}, Check: func(t, *pb.Resp), WantErr: connect.CodeInvalidArgument}` through `RunRPCCasesV2`); component tests call `testkit.NewConnectClientV2(t, svc.RegisterV2, <pkg>connect.New<Svc>Client, testkit.ServerPrincipalV2(...), testkit.ValidateRequestsV2())`; the e2e harness builds `connect.NewClient(connecthttp.NewTransport(httpClient, baseURL, connecthttp.WithReadMaxBytes(0)))`. `connectinprocess` is available but `NewConnectClientV2` currently serves over `httptest`, so the read limits and protocol behaviour under test are the real ones.
- **Dependencies.** `go.mod.tmpl` requires `connectrpc.com/connect/v2`, `otelconnect` v0.12+, `vanguard` v0.5+; `gen-go.mod.tmpl` and `tools.go.tmpl` follow.
- **Analyzers.** All accept both import paths (resolve the alias from the import spec, treat `connectrpc.com/connect/v2` as the runtime, recognise `Register<X>Handler`): `lint_optional_deps_guard_helpers`, `linter/contract/exclude_directive`, `contractcheck/outbound_io_no_rpc`, `doctor/payload`, `forgeconv/handler_connect_error` and `no_handler_error_mapping` (v2 `NewError` takes a string, so the argument-shape classifier is major-aware), `unwrapped_domain_error` (message updated), `codegen/crud_owner_source` and `unwired_stub_excise`. The `connect-errors` codemod does nothing on v2 code. Each fixture gets a v2 twin.
- **The forge PR's own proof.** With v2 the `project new` default, the e2e corpus scaffolds v2 projects; the tests that write connect-go v1 code into their project, or assert v1 wiring, pass `--connect v1`. A new `TestE2EConnectV2ScaffoldServesRPC` (modelled on `TestE2EScaffoldServerStartup` and `TestE2EPbThroughCrudPlusCustomRpc`) scaffolds `project new --connect v2` with an entity, a custom unary rpc and a server stream, generates, builds, boots the server and calls it with a v2 client and with a raw Connect-JSON request, and runs `forge lint`. Wire parity tests in `pkg/svcerr` serve the same error through a v1 and a v2 chain and compare status, headers and body bytes, including a remote error and a plain error. Each V2 symbol gets a test mirroring its v1 test, over `connecthttp` or `connectinprocess`.

### (h) New projects

`forge project new` scaffolds a new service project on v2 by default (owner decision, 2026-11-19): v2 requires in `go.mod`, v2 plugin in `tools.go`, v2 service templates (it sets `ProjectGenerator.ConnectMajor`). v1 stays selectable with `--connect v1` until reliant and control-plane have migrated; after that, a later PR removes v1 support from forge. `--in-place` with no `--connect` keeps the adopted `go.mod`'s major, and a `cli` or `library` project has no Connect code, so the default does not apply to it. Because detection reads `go.mod`, the flag only has to write the right requires; every later command follows, so existing projects keep their major.

### (i) Delivery

Two PRs, because the runtime can be reviewed and merged without any generated-code change, and everything in the second depends on it.

- **PR 1: runtime, detection, analyzers.** The V2 symbols across `forge/pkg` (section "API reference"), `internal/connectmajor`, v2 plugin selection and cache keying (`requiredProtoTools` per project, tool pins, bootstrap script, buf preflight hint), the analyzer and linter changes, and this document. It changes no generated output: a v1 project renders byte-identically.
- **PR 2: generated code.** The service-level templates (`service.go`, handlers, CRUD shims, unit and component tests, e2e harness) and project-level templates (mounts, routes, providers, cmd, middleware, `go.mod`/`gen-go.mod`/`tools.go`), the Go emitters behind them, `project new --connect v1|v2` with v2 as the default, and `TestE2EConnectV2ScaffoldServesRPC`.

Both PRs hold the same invariant: **v1 output is byte-identical**. No v1 golden file is regenerated. PR 2 also makes v2 the `project new` default, so the e2e corpus covers v2 by default and v1 where a test asks for it with `--connect v1`.

### (j) v1 removal (a later PR)

Once reliant and control-plane are on v2, forge drops connect-go v1 (owner decision). Recorded here so the in-between API is not mistaken for the final one:

- **`svcerr.Wrap` and `WrapOr` return a `*connectv2.Error`.** Today they return v1's, so in a v2 project in-process `connect.CodeOf(err)` and `errors.As(err, &*connectv2.Error)` on their result miss (section 5, step 7). After removal the handler's own `Wrap` result is the v2 error the wire carries, and in-process code reads it with connect's own functions.
- **The `V2` names lose their suffix**, as 4(b) planned: `svcerr.Code` returns a `connectv2.Code` (today `CodeV2`), `ToConnect` returns a `*connectv2.Error` (today `ToConnectV2`), `Interceptor` is today's `InterceptorV2`, and so on across `forge/pkg`. Code that already reads through `svcerr.CodeV2`, `ToConnectV2` and `MetaOf` needs only that rename.
- No parallel `WrapV2` is added in the meantime: `CodeV2`, `ToConnectV2` and `MetaOf` already give in-process code the v2 view, and a third spelling of `Wrap` would be one more name to retire.

## 5. Migrating a forge project from v1 to v2

The sequence follows the connect-go migration guide, with forge steps interleaved. Steps marked (M) are mechanical; (H) need a person or agent.

1. **Pin a forge release that includes this support.** (M)
2. **`go get connectrpc.com/connect/v2`** so it is a _direct_ require. This is what flips `connectmajor` to v2. (M)
3. **`connect-go-v2-migrate -w`, first pass.** Rewrites `buf.gen.yaml` where it needs it (forge's local-plugin entry does not), drops `simple=true`, updates code that does not depend on generated types. The project does not compile until step 6. (M)
4. **`forge generate --keep-on-build-failure`.** Detects v2, installs the v2 plugin from its own module, and emits v2 `_gen` files (mounts, routes, bootstrap, component test helpers) and v2 generated Go. The hand-written code is not ported yet, so the final compile check fails; without the flag generate would roll back everything it wrote. With it the generated files stay on disk, the compile errors are printed (they are the work list for steps 5 to 8), and the run exits non-zero and is not recorded as verified. Step 9's plain `forge generate` checks the tree again. The flag also covers a **post** generate hook (forge.yaml `generate.hooks`) that fails, typically one that compiles part of the project (`go generate`, `go run ./tools/...`): its failure is reported, every later hook still runs, and nothing rolls back. A failed **input** hook (`phase: input`) still rolls the run back: the frontend hooks and mocks are projected from what it writes, so going on would emit and keep output derived from stale or half-written inputs, and the stale-artifact sweep would delete files those inputs no longer name. A hook forge cannot start at all (its command is not on PATH) also rolls back, since porting code does not fix it. (M)
5. **forge's own shapes, by hand.** The migrate tool rewrites the inline `mux.Handle(New<X>Handler(...))` shape and warns on the rest. forge's scaffolded `service.go` `Register` assigns `path, h := ...` first, which the tool warns about and leaves. These PRs do **not** ship a forge codemod. The forge-owned shapes a migrating project edits by hand are: **one `RegisterV2(server *connect.Server)` method per `service.go`** (`<pkg>connect.Register<Svc>Handler(server, s)`, beside the existing `Register`, which can be deleted at the end), and the **scaffolded tdd rows** (`connect.NewRequest(&pb.X{})` and `Check func(*connect.Response[O])` become `CaseV2` rows; `forge project migrate tdd` refuses in a v2 module because it lifts `connect.NewRequest`, which no longer exists). Whether a codemod for these is worth building is decided after measuring the reliant migration (section 7). (H, but small and uniform: one method per service, one table per test.)
6. **`connect-go-v2-migrate -w`, second pass.** Migrates handler signatures, client calls, `NewError` (to `NewError(code, err.Error()).WithCause(err)`), stream loops, header and trailer access, `validate`. (M)
7. **Switch hand-written uses of `forge/pkg` v1 symbols to their V2 forms.** `svcerr.Interceptor` to `InterceptorV2`, `observe.Chain` to `ChainV2`, `serverkit.ChainDeps` to `ChainDepsV2`, `servicecatalog.NewClient` to `NewClientV2`, `tdd.Case` to `tdd.CaseV2`, `crud.HandleGet(op)` to `crud.Get(op)`, `ce.Meta().Get(svcerr.ReasonHeader)` on an error to `svcerr.MetaOf(err).Get(svcerr.ReasonHeader)` (with `svcerr.ClientInterceptorV2()` on any client a project builds itself), and so on (the table in the API reference lists every pair). **In-process error assertions read through svcerr until v1 is removed:** `svcerr.Wrap` and `WrapOr` still return a v1 `*connect.Error` (the wire is unaffected: `svcerr.InterceptorV2` re-encodes it), so on a handler's own `Wrap` result `connect.CodeOf(err)` is `CodeUnknown` and `errors.As(err, &v2err)` is false. A test or in-process caller reads the code with `svcerr.CodeV2(err)` (or `tdd.AssertConnectErrorV2`), the v2 error with `svcerr.ToConnectV2(err)`, and the metadata with `svcerr.MetaOf(err)`; all three read either major and the bare svcerr kinds, so they stay correct when `Wrap` changes (4(j)). This is a rename by convention and can be scripted with `gofmt -r`. (M for the rename; H where a callback signature changed: `authn.Policy.MapErrorV2`, `activity.Deps.ViaFromV2`, the trust classifier and predicate, and a `ChainDeps` slot that used `Omit` or a custom interceptor, which becomes a `NoX` field or a `DeadlineOverride`.)
8. **Hand work the tool warns about.** Custom interceptors rewritten to `ServerInterceptor`/`ClientInterceptor`; `otelconnect` server vs client choice; `connect.WithCodec`/`WithCompression` (none today); the stream header cases that need two `CallInfo`s; `NewWireError`/`IsWireError`. (H)

   **Header reads outside a call.** `connect-go-v2-migrate` rewrites header access to `info, _ := connect.CallInfoForServerContext(ctx)` followed by `info.RequestHeader()…`. That `info` is nil when a unit test calls the handler method directly, so the handler panics. Change that line to `info := serverkit.CallInfoV2(ctx)`, which returns the call's CallInfo, or an empty writable one outside a call; the rest of the handler stays as the tool wrote it. `tdd`'s V2 rows already call every handler through an in-process `connect.Server` (`tdd.CallV2`), so the handler sees a real CallInfo. A v1 row's `Req.Header().Set(…)` becomes the row's `Header: http.Header{…}`, and response-header assertions move to `CheckCallInfo`.

9. **`go mod tidy`, build, `forge lint`, tests.** Fix remaining warnings. (M/H)

Services may be migrated one at a time inside a module (both runtimes can be imported), but the generated packages are one major, so in a forge project the unit of migration is the whole project.

| control-plane | ~978                               | 1701                    | ~103             | ~3          |

The migrate tool does the bulk (handler and client signatures, `NewError`, most header access). The hand work is the interceptor uses (most are `connect.WithInterceptors(...)` at call sites, which go through `ChainV2`; a minority are custom interceptors), the 50 reliant streams, and review.

### Order

1. **Release forge with this support.** Pin it in reliant (bump per reliant `dev-docs/forge-upgrade.md`; record it in the upgrade log in the same PR). That bump alone changes nothing: both repos stay v1.
2. **reliant migrates.**
3. **control-plane pins forge and reliant in lockstep** (`task pin:forge REF=<forge sha> RELIANT=<reliant commit>`; `task pin:forge-coherence` fails skew), then migrates. control-plane `go.mod` pins `github.com/reliant-labs/reliant` and imports its packages, so the reliant pin that carries the migrated reliant is part of control-plane's bump. `reliant.v1` proxying in control-plane (`internal/proxy`, `llmproxy`, `workspaceproxy`) is a raw `httputil.ReverseProxy` and is not affected by the connect major. Only one control-plane file imports reliant's generated connect package (`e2e/user_stories/story_09_full_daemon_flow_test.go`); any other import of a reliant package whose exported API carries connect types has to move with the pin. Check this before the bump.

Both repos merge through their own queues; each phase below is a PR (or a small series) that a steward merges. Nothing here uses `merge:priority` or a release label by default.

### Phases per repo

1. **Tooling and plugin.** `go get connectrpc.com/connect/v2`; `forge generate` installs the v2 plugin; confirm `buf.gen.yaml` (reliant and control-plane use `local: protoc-gen-connect-go`) and the preflight pass. Update any hand-written scripts or CI steps that install the plugin.
2. **Generated code.** Regenerate; commit `gen/` as v2 in one PR. This breaks the build until phase 3, so phases 1 to 4 land as one PR, or as a branch merged together.
3. **Handlers and clients via the migrate tool.** Two passes plus the by-hand forge shapes (`RegisterV2` per service, tdd rows; section 5). Review by package; handler logic is untouched by design.
4. **Mounts and service `Register`.** Generated mounts group by chain. reliant has several distinct chains (user, daemon, gateway; `internal/grpc/user_chain.go`, `daemon_listener.go`); each is one Server.
5. **Custom interceptors** (~68 and ~103 uses; the custom ones) rewritten by hand to `ServerInterceptor`/`ClientInterceptor`; forge-provided ones switch to their V2 forms.
6. **Streams** (reliant's 50): named stream types, `Receive()` loops, client stream constructors that now return an error, and stream-aware interceptors.
7. **Clients with `WithReadMaxBytes(0)`.** Every client transport (`connecthttp.NewTransport(hc, url, connecthttp.WithReadMaxBytes(0))`) unless a limit is chosen on purpose. This covers the daemon's gRPC clients (`cmd/reliant/cmd/daemon_instance.go:226`, `internal/toolexec/daemonruntime/runtime.go:637`, both `WithGRPC()`, which becomes `connecthttp.WithGRPC()`), the Go SDK, the CLI, and server-to-server clients.
8. **Tests.** `wirecheck`, handler unit tests (tdd simple rows), component tests (in-process transport), integration tests asserting 404 for unknown methods (they keep passing behind `MuxV2`; a server mounted by hand with `connecthttp.Mount` must switch to `mountkit.MountV2`).

### Wire verification

Each repo has `internal/wirecheck` (`RoundTrip`: serve an error from a real Connect handler behind the svcerr interceptor and return what a client received). The plan extends it:

- **Byte-identical error bodies.** For representative rpcs (a classified svcerr error with reason and metadata; a plain error; a remote error forwarded from an upstream client call; a context cancel; a validation failure with details; a stream error), serve the same handler through the pre-migration v1 chain and the migrated v2 chain and compare status, headers and body bytes over Connect-JSON, Connect-proto and gRPC. These golden bytes are recorded on the last v1 commit, so a regression after migration is a diff.
- **Old clients against the new server.** An old daemon build (v1 client, `WithGRPC`), the Electron app and the web client (connect-es, JSON and one binary spec) run against a migrated server in a throwaway environment. Cover: a >4 MiB payload (attachment `bytes content`, `tools_daemon` `body`/`data`, workflow yaml, deploy `manifests_layer`) both directions, an error with a user-facing message, and a server-stream.
- **New clients against an old server.** A v2-built daemon against a v1 server, for the rollout window.

### Rollout guard

Both repos ship the **server first**. Old clients keep working because the wire is unchanged, so no client has to move in lockstep and no flag is needed. Clients (daemon, SDK, Electron) follow in ordinary releases. Rolling back is a normal deployment rollback: the wire is the same both ways. The wire verification above is the gate for the server release.

### Risks

- **Remote-error passthrough.** Any handler that calls another Connect service and returns its error depends on re-localisation in `svcerr.InterceptorV2` (4(e)). A Server that is not built through `ChainV2` loses it. Test: the remote-error case in wirecheck, and an audit of every `connect.NewServer`/`Mount` in each repo.
- **Servers outside the standard chain.** A hand-mounted Server without `svcerr` (test servers, small utility listeners) returns plain errors as an empty `CodeUnknown`. The audit finds them. reliant has ~82 handler `fmt.Errorf`/`errors.New` returns and control-plane ~20, some user-facing (for example `internal/handlers/connector`); they are safe behind `svcerr` only because of rule 4 in 4(e), which already redacts them in v1.
- **>4 MiB payloads.** Attachments, `tools_daemon` payloads, deploy manifests, storage browser and dashboard content, RUM data, long transcript lists. Every Server and every client transport must carry the explicit limit (4(e), phase 7). control-plane already sets a 4 MiB server limit explicitly; reliant sets unlimited. Missing one client is the likeliest regression.
- **SDK and public Go surface.** reliant treats the SDK and its Go API as public under its own semver (major 1, backwards compatible). If `sdk/go` or another published package exposes connect types or generated stubs, a v2 migration changes its API. Check which published surfaces expose connect types before phase 1; if there are any, keep the old API and add the new one beside it (the same convention forge uses), and let the owner decide the timing. This is the one item here that might need a decision beyond the plan.
- **vanguard REST.** reliant and control-plane that serve REST through vanguard move from the v1 bridge to the v2-native `vanguard.Mount`; verify the REST routes and their error mapping against the existing tests.
- **Stream interceptors.** Stream drain, idempotency capture (wraps `ServerStream.Send`) and logging status need stream-level tests, not only unary ones.
- **Reviewability.** ~1,800 changed files is a review problem, not a technical one. Phases are cut by package so reviewers can read mechanical diffs by sampling; the migrate tool's report and the golden wire bytes are the evidence.

### Rough sizing

These are estimates for a sequenced, agent-assisted migration with human review, not commitments: reliant about 1 to 2 weeks (streams, several chains, daemon clients, SDK check); control-plane about 1 week (fewer streams, similar volume, much of it mechanical). forge's own PR (packages, templates, plugin, analyzers, e2e) is larger than either and comes first. The calendar time is dominated by queued review and the wire verification, not by editing.

## 7. Open questions for the owner

1. **When do we flip the `project new` default to v2?** Decided (owner, 2026-11-19): now, in PR 2. forge has no outside users, so it goes straight to v2: `project new` defaults to v2, `--connect v1` keeps working until reliant and control-plane migrate, and a later PR then removes v1 support from forge (section 4(h)).
2. **When does the formal `Deprecated:` marker land on v1 `forge/pkg` symbols?** It turns every v1 consumer's staticcheck red on pin. Options: the release after both consumers have migrated (recommended; no first-party caller remains); on a fixed date; with the default flip. Removal of v1 is a forge major regardless.
3. **Should forge ever adopt v2's plain-error redaction as a deliberate behaviour change?** Behind `svcerr` it is already the behaviour, so this only concerns code that returns plain errors outside a forge chain, where this design does nothing to preserve v1's leak of `err.Error()`. The question is whether a future forge major should make redaction a hard guarantee (for example refusing to mount a Server not built by `ChainV2`), or keep it advisory. Recommendation: keep it advisory in v1.x and make the standard chain mandatory in the next major.
4. **Is a `forge fix connect-v2` codemod worth building?** The forge-owned hand edits in a migration are one `RegisterV2` method per `service.go` and the scaffolded tdd rows (section 5, step 5). Neither PR ships a codemod. Measure first: if the reliant migration spends meaningful time on those two shapes, build it before control-plane starts; if the migrate tool plus a handful of edits covers it, do not. Recommendation: decide from the measured reliant effort, not before.

### Wire-affecting defaults, in one place

Server read limit is whatever the chain passes (`payloadCap`), and `MuxV2`/`NewMuxV2` prepend `WithReadMaxBytes(0)`; every forge-built v2 client (`observe.ClientStackV2`, `servicecatalog.NewClientV2`, `testkit.NewConnectClientV2`) starts with `WithReadMaxBytes(0)`; no builder exposes `WithCodecs` or `WithCompressors`. Every forge-built v2 mount (`MuxV2`, `testkit.NewConnectClientV2`) goes through `mountkit.MountV2`, so an unknown method of a mounted service is v1's plain 404.
