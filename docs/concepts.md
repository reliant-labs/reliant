# Concepts

Why Forge is shaped the way it is. Read this after
[getting started](getting-started.md), when you want the reasoning rather
than the steps. For how to use it — deploys, environments, observability,
troubleshooting — see the
[Forge user guide](https://docs.reliantlabs.io/forge/overview).

Most of what follows exists because the alternative was tried and something
broke. Where that is true, the incident is named.

---

## 1. Ownership is the organizing principle

Forge is not a framework your application runs inside. Nothing in `forge/pkg`
ever calls your code — your `serve.go` calls `serverkit.Run`, not the other
way around. Every library is a leaf you call.

The rule that decides what belongs in a library and what stays in your tree
is stated in `serverkit`'s own documentation:

> The line is OWNERSHIP, not size. Anything an application author has a
> legitimate reason to change stays in their serve.go... Absorbing any of
> those into serverkit would take a decision away from the person who has to
> answer for it.

So interceptor order, auth posture, payload caps, and which services this
binary mounts are all visible in a file you own — not buried behind a
`Run()` that does everything. When someone asks in a year why requests are
rejected at 4MB, the answer is a line of your code.

### The anti-photocopy thesis

Nearly every package in `forge/pkg` was extracted from code that used to be
copied into each project. The `middleware` package explains why:

> Field evidence across downstream repos showed the copies stayed
> byte-identical to the templates — zero project intent, pure photocopies of
> security-relevant code that drifted and never received fixes.

The question is never "is this big enough to be a library?" It is **"does a
project ever have intent here?"** If every copy is identical, it should be a
versioned dependency so a fix reaches everyone. If projects legitimately
differ, it stays yours.

`svcerr` came from the same discovery in reverse: four byte-identical
`mapServiceError` switches across handler packages. The duplication was
_earned_ — the documented convention told people to write it that way. Forge
treats "our own convention produces copy-paste" as a signal to extract a
library, not as a documentation problem.

### Three categories of file

| Category                 | What it is                                                   | Regenerated?           |
| ------------------------ | ------------------------------------------------------------ | ---------------------- |
| **Libraries you import** | `serverkit`, `svcerr`, `orm`, `crud`, `obs`                  | No — versioned, bumped |
| **Generated tables**     | `mock_gen.go`, `<entity>_orm.go`, `handlers_crud_ops_gen.go` | Yes, every run         |
| **Scaffold-once, owned** | `serve.go`, `providers.go`, `handlers_crud.go`, migrations   | Never after birth      |

The invariant governing the middle row, from `lifecyclekit`: **generated
files are tables, not programs.** All uniform machinery lives in a library;
the generated file shrinks to per-app data. That is what makes regeneration
safe — there is nothing in a generated file worth hand-editing.

Scaffold-once files are written exactly once, and **deleting one sticks**:
`.forge/scaffolded.json` (committed) records every file forge has scaffolded,
so an absent one reads as a decision and `forge generate` leaves it absent in
every clone. To get forge's version back, ask for it by name:

```bash
forge project rescaffold .github/workflows/ci.yml .pre-commit-config.yaml
```

That re-creates each absent path the way forge scaffolds it for this project
today — CI workflows through the same mapper `forge generate` uses — and it
refuses a path that still exists, so it never overwrites your bytes (that is
`forge project upgrade --force <path>`, which shows the diff first).

A scaffold the project should never have — including one forge has not
written yet, or one whose birth broke the very `forge generate` it was born in
and was rolled back with its record — is **declined** instead of deleted:

```bash
forge project disown cmd/app/cmd/serve.go --absent --reason "serve.go turns composition on; our roots land later"
```

The decline is a `"declined": "<reason>"` entry in `.forge/scaffolded.json`,
written outside `generate`, so a failed run's rollback (which restores that
file to its pre-run bytes) keeps it. `forge project scaffolded` lists declines
with their reasons; `forge project rescaffold <path>` re-adopts one.

### Self-certifying files

Every forge-owned file embeds a SHA-256 of its own body:

```go
// Code generated by forge. DO NOT EDIT.
// forge:hash=528a683f9b60023d43a386beaeb374971eca4850867a3188d66f2af4859b3d89
```

There is deliberately **no central manifest**. A manifest committed from a
work-in-progress branch could leave a clean clone of green `main` unable to
regenerate itself. Provenance travels _with the file_ instead — through
clones, worktrees, cherry-picks and rebases.

Hand-edit a generated file and the next `forge generate` **stops** rather
than reverting your work. That is a materially different promise from a
`DO NOT EDIT` comment, which is only advice.

## 2. Two truths

- **Proto is the wire truth** — services, RPCs, messages, config.
- **SQL migrations are the schema truth** — `db/migrations/*.up.sql`.

Neither derives from the other. They evolve on independent clocks, and
generated conversions map their intersection by name.

Forge used to accept entity declarations in proto annotations
(`(forge.v1.entity)`, `pk:`, `timestamps:`). Those are **retired and
ignored** — they survive only as deprecated tombstones. Delete them if you
find them; do not copy them forward.

### Why introspection instead of declaration

`forge generate` applies your migrations to a **real ephemeral Postgres**,
then reads the schema back out of Postgres's own catalog.

The earlier design used an in-memory SQLite shadow, which needed a
normalization pass and broke the first time a project used something SQLite
could not parse (a schema-qualified table name). Real Postgres needs no
normalization: migrations apply verbatim, and whatever Postgres accepts,
Forge can project.

This is why arbitrary DDL works — `JSONB`, `TEXT[]`, generated columns,
partial indexes, `CHECK` constraints, `::type` casts — without Forge modeling
any of it.

Practically, it means **behavior comes from real columns**:

| You write                   | You get                                                 |
| --------------------------- | ------------------------------------------------------- |
| `created_at` + `updated_at` | managed timestamps                                      |
| `deleted_at`                | soft delete; reads filter it, `Delete` becomes `UPDATE` |
| text columns                | generated list search across them                       |

You never annotate for these. You write the column.

### An entity is both halves

An entity exists where the CRUD quintet is in the proto **and** the matching
table is in the applied schema. Either half alone generates honest nothing —
a CRUD RPC with no table returns `Unimplemented` rather than a guess. A
missing route is accurate information; a runtime 500 is not.

The markers that drive this (`forge project capabilities` prints the current
set):

| Marker              | Effect                                                |
| ------------------- | ----------------------------------------------------- |
| `forge:entity`      | Births the migration and the CRUD quintet             |
| `forge:soft-delete` | Born with `deleted_at`; `Delete` becomes an update    |
| `forge:append-only` | No Update/Delete, plus a trigger rejecting both       |
| `forge:read-only`   | On the entity; a client Create/Update never writes it |
| `forge:secret`      | Writable, but never packed into read responses        |
| `forge:mutation`    | Forces the generated React hook to be a `useMutation` |

## 3. Contracts, and why the LLM story rests on them

Every internal package declares a `contract.go` with three things: the
interface, a `Deps` struct, and a constructor.

```go
package email

type Service interface {
    Send(ctx context.Context, to, subject, body string) error
}

type Deps struct {
    Logger *slog.Logger
    Store  Store          // interface-typed, always
}

func New(deps Deps) (Service, error)
```

**Names are not forced.** The lint rule explains why:

> The names are free because forcing them is an antipattern — `Service` and
> `New` are poor names for a mailer or a store, and forge is meant to promote
> good practice, not conscript packages into bad naming. What is NOT free is
> the signature.

Use `// forge:contract` and `// forge:constructor` when your names differ.
Lint and codegen resolve names through the _same_ detectors, so whatever lint
accepts, generate can wire.

### What you get from it

`forge generate` writes `mock_gen.go` with a mock for **every interface in
the file**, not just the main one:

```go
type MockRepository struct {
	contractkit.Recorder
	GetBookmarkFunc func(context.Context, string) (*db.Bookmark, error)
}

var _ Repository = (*MockRepository)(nil)
```

Three properties matter, and all three matter _more_ when an agent is writing
the tests:

1. **Nothing is hand-rolled.** The mock for a dependency is in the file next
   to the one you are editing. An agent that writes its own fake is doing
   avoidable work and will drift.
2. **Unset methods fail loudly** — `MockRepository.GetBookmarkFunc not set` —
   rather than returning a zero value that makes a test pass for the wrong
   reason.
3. **The compile-time assertion** breaks the build _at the mock_ when the
   contract changes, not at some distant call site three packages away.

Declare dependency interfaces in `contract.go`. An interface declared in
`service.go` gets no mock.

### Deps are interfaces, enforced

`forgeconv-deps-are-interfaces` fails lint on a `Deps` field that is a
concrete struct. This is what makes the all-mock unit test surface real
rather than aspirational, and it is what lets you move a service into its own
process later by swapping one line in composition.

One Go trap worth knowing: **a nil concrete pointer stored in an interface is
a non-nil interface.** A `if deps.X == nil` check silently stops working the
day you convert that field to an interface type.

### Composition is compile-time and by type

Resolution is by type, never by name. If `infra.Repo` does not satisfy
`bookmarks.Repository`, it does not compile. Runtime containers using
reflection or generics are deliberately rejected: a name-matching layer can
silently leave a narrowly-typed field nil, and you find out in production.

`validateDeps()` runs at construction, so a missing dependency fails at boot
rather than on the first request that needs it. That is why constructors
return `(Service, error)`.

### The markers you will meet in Go source

Scaffolded code carries `// forge:*` comments that steer wiring,
observability and contract generation. `forge project annotations --kind go`
prints the authoritative list; this is the orientation.

Two recognition rules apply to all of them: both `// forge:x` and
`//forge:x` are accepted, and the marker must be the **whole comment line**
after stripping comment syntax — so prose that merely mentions a directive is
never mistaken for one.

| Marker                                           | Goes on                                  | Effect                                                                                                                                                         |
| ------------------------------------------------ | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `forge:optional-dep`                             | a `Deps` field                           | The field may be nil. `validateDeps` must not enforce it, and composition emits the typed zero instead of reporting it unresolved. Guard each use.             |
| `forge:optional-checked`                         | a dereference line                       | Silences `--optional-deps-guard` for one deref you know is safe.                                                                                               |
| `forge:constructor`                              | the constructor's doc                    | Names a constructor that isn't `New`, and opts the package IN to the generated observability decorator. Scaffolds stamp it, so packages are born instrumented. |
| `forge:no-observe`                               | the constructor, or one interface method | Opts out of that decorator — whole package, or just the one method. Beats every opt-in.                                                                        |
| `forge:service` (or `forge:contract`)            | the interface's doc                      | Names the contract when it isn't called `Service`.                                                                                                             |
| `forge:exclude-contract: <why>`                  | the package                              | No contract codegen at all — and therefore **no generated mock**. Needs a reason; refused on outbound-I/O and multi-impl packages.                             |
| `forge:external-component` (or `forge:provided`) | the package                              | Constructed by hand in `providers.go`, so the injector skips it — but the mock is still generated.                                                             |
| `forge:not-a-component: <why>`                   | the package                              | The server does not have it (CLI-, daemon- or other-binary-only): no `compose.go` entry, no `Infra` field, `Deps` never resolved — mock still generated.       |
| `forge:outbound-io`                              | the package                              | Declares an outbound boundary; lint then forbids inbound RPCs in it.                                                                                           |

The distinction between the three package opt-outs is the one people get
wrong. `exclude-contract` means _forge does not manage this package_ and
costs you the mock. `external-component` means _forge does not **build** this
package_ but the server still has it — you construct it in `providers.go` and
consumers resolve to that `Infra` field; the right choice when construction is
bespoke (adapter wrapping, two-phase setters, a dialer nil'd on unset env) but
the package is otherwise contract-shaped. `not-a-component` means _the server
does not have this package at all_ — the CLI, a daemon or another binary
builds it — so the generator never asks for its `Deps`, and a server component
that requires it fails `forge generate` rather than quietly wiring a CLI
collaborator into the server. Both of the last two keep the mock.

Without `forge:optional-dep`, a required non-scalar `Deps` field that
resolves to nothing is a loud generate-time or compile-time error. Forge
never emits a silent typed-zero for a required field.

### The advisory analyzers

Three `forge lint` rules are warnings only — they never fail the build — but
they catch the mistakes that survive review, and they are worth running on a
codebase an agent has been working in.

**`--config-deps`** flags scalar `Deps` fields. A `string` or a
`time.Duration` in `Deps` is configuration wearing a collaborator's clothes:
it cannot be mocked, it does not vary per environment, and it has no typed
home. The remediation is written out per finding — the exact proto message,
the `AppConfig` line, and the Go replacement:

```
⚠ [forge-config-deps] internal/email/resend.go:41:2
    internal/email Deps.APIKey is a naked scalar (string) — scalars are
    configuration, not collaborators
    → declare a config block in proto/<project>/config/v1/config.proto:
      `message EmailConfig { string api_key = 1 [(forge.v1.config) = {
        env_var: "EMAIL_API_KEY" }]; }`,
      compose it on AppConfig (`EmailConfig email = <next tag>;`),
      run `forge generate`, and replace `APIKey string`
      with `Cfg *config.EmailConfig`
```

**`--optional-deps-guard`** finds dereferences of a `forge:optional-dep`
field that no nil-check protects — a latent panic on the code path where the
dependency was legitimately not wired. It recognizes early-return guards,
enclosing guards, alias-then-check, and a guard inside a same-package helper
the rpc calls first (`if err := s.gate(ctx); err != nil { return nil, err }`,
where `gate` nil-checks the deps), so it flags the genuinely unguarded case.

**`--frontend-stores`** flags Zustand stores that import generated Connect
clients. Server state belongs in the generated React Query hooks; Zustand is
for client-only state. Mixing them creates two sources of truth for the same
data, and the stale one wins about half the time.

A handful of further flags stay hidden behind `forge lint --help-dev`. Those
are either meaningless outside the forge repo itself, or one-shots you run
during setup and never again — `--suggest-excludes`, which proposes a
`contracts.exclude` list for a freshly migrated project, and
`--suggest-buf-excepts`, which proposes buf lint exceptions when the same
rule fires across more than three protos.

## 4. What "production best practices from day 0" actually means

Concretely, these are on before you write a line of business logic.

### Errors do not leak

`connect.Error.Message()` is literally `err.Error()`. Any error whose text you
did not write is text you publish to anonymous callers — and Postgres writes
things like:

```
relation "accounts" does not exist (SQLSTATE 42P01)
dsn=postgres://app:s3cr3t@db:5432/prod
```

`svcerr.Wrap` handles three cases:

| Input                                             | Result                                                      |
| ------------------------------------------------- | ----------------------------------------------------------- |
| A deliberate sentinel (`svcerr.NotFound("user")`) | Matching code, message preserved                            |
| An existing `*connect.Error`                      | Passed through                                              |
| Anything else                                     | `CodeInternal`, message replaced, original kept server-side |

The model: **what you wrap with `%w` is for the operator; what you pass to
the constructor is for the client.**

The one way to defeat it: `svcerr.InvalidArgument(err.Error())` puts the raw
error back on the wire, because codes you choose keep the message you gave
them. Use `svcerr.WithCause(svcerr.Internal("create failed"), err)` instead:
the outer error decides the code, message, reason and error class; the cause
— even another service's `*connect.Error` — reaches only the log.

`svcerr.WithReason(err, "no_active_subscription")` attaches a stable
snake_case code delivered as a header, so frontends branch on a code rather
than on message text that will change.

### Auth fails closed

A production server **refuses to boot** with no auth provider configured, at
construction time. The library owns that refusal, mode resolution, the
allow-list gate and Bearer extraction; your project owns the validator, the
identity enricher, and what is on the allow-list.

`forge project audit` reports an `unscoped_auth` category that distinguishes
_authenticated_ from _authorized_ — on one real application it found that 85
of 89 authenticated RPCs never resolve the caller, meaning every signed-in
user is treated identically.

### Observability at three boundaries

1. **The RPC edge** — recovery, request-id, logging, tracing, metrics, then
   auth, audit, rate-limit. The `auth → audit` order is load-bearing: audit
   must see the authenticated principal.
2. **Every in-process component call** — the layer that is usually dark. A
   generated decorator routes through a chain you own.
3. **Every database query** — a bun OTel hook makes each one a child span.

The split in the second one is the "tables not programs" rule applied:
`middleware_gen.go` is generated and regenerates when your interface changes;
`observe_chain.go` beside it is yours.

### Tests that cannot lie

Scaffolded test rows assert `Unimplemented`, so they **fail the moment the
handler is implemented**. There is no permissive any-outcome mode in `pkg/tdd`
— you cannot write a row that passes regardless of behavior.

Tests run against a **real ephemeral Postgres**: one server per process, a
fresh uniquely-named database per caller. It downloads and caches its own
Postgres, so no Docker is required.

## 5. Config and secrets

Annotate a proto field once:

```proto
string database_url = 3 [(forge.v1.config) = {
  env_var: "DATABASE_URL", required: true, sensitive: true
}];
```

From that you get env-var loading with precedence (proto default < file < env
< flag), a KCL schema, a per-environment value slot, and typed access.

The file is a YAML or JSON document named by `--config`, or, when the flag is
absent, by the binary's own path variable: `<BINARY>_CONFIG` for a config bound
to a binary (`RELIANT_CONFIG` for `cmd/reliant`), `<PROJECT>_CONFIG` for the
project-global `AppConfig`. No forge binary reads another's variable, so a
shell configured for one app cannot hand its file to the rest. Set to `""`, the
path variable is unset, like every other variable. A process that loads a root
config and a command config (`reliant server api`) reads both from that one
file, whose keys are flat across them, like its flags and env vars; a key
neither declares is an error.

An env var set to the empty string counts as unset, whatever the field's type:
`TEMPORAL_HOST=` keeps the file's or the default's value rather than loading
`""`. Deploy templates, compose files and shell profiles emit `X=` for "not
configured" far more often than anyone means an empty value. An explicitly
empty value is a flag's to set (`--pprof-addr=` turns pprof off,
`--allowed-registries=` clears a defaulted list).

A field can also list `env_var_aliases`: further names it is read from, in
order, when `env_var` is unset. That is for setters forge does not control,
such as `NODE_ENV` or an old name another deployment still exports. An alias
marked `deprecated` prints a notice at startup whenever it is set. Everything
forge renders sets `env_var` alone.

Typed access is a guardrail, not a suggestion: a direct `os.Getenv` /
`os.LookupEnv` outside the generated loader is a lint finding, and
`config.enforce_typed_access` in `forge.yaml` decides how hard. `error` fails
`forge lint` and CI, `warn` reports, `off` drops the check. `forge project new`
writes `error`, because a new project has no direct reads to report. Adopting
an existing project with `forge project new --in-place` writes `warn`: that
project's existing reads would otherwise fail its first lint. Flip it to
`error` once they have moved onto the typed config. A `forge.yaml` without the
key reads as `warn`. The check itself is forbidigo, configured in
`.golangci.yml`; a config whose forbidigo `forbid` list does not cover
`os.Getenv` checks nothing about env reads, so `forge lint` reports the lane as
could-not-run until the patterns are added.

`sensitive: true` changes three things, each closing a specific leak:

- Manifests carry a `secretKeyRef`, never an inline value.
- There is **no slot in the git-tracked per-env config** to paste a password
  into.
- There is **no CLI flag**, so a secret cannot land in shell history.

Secrets are declared once as a reference and bound per-environment by a
provider — dotenv for local, external for staging and production. KCL stays
pure: no secret value ever appears in rendered output. Forge **refuses** to
render plaintext Secrets into anything but a recognized local cluster.

One piece of guidance worth stating plainly, because the clever version is
wrong: **a connection string is a secret.** Do not split it into a non-secret
template plus a secret password. The value that varies per environment and
the value that must stay out of git are the same string, so splitting buys
nothing and costs a fragile interpolation — Kubernetes expands `$(VAR)`, not
`${VAR}`, and only from variables defined earlier in the same container, so
the composed URL renders with a literal `${DB_PASSWORD}` in it more often
than it works.

## 6. Deployment

Everything that runs is an `fw.Workload`, declared ONCE in
`deploy/kcl/workloads.k` with its runtime-independent facts — build, the
subcommand in `args`, ports, env, probes — and zero Kubernetes vocabulary
(ADR 0002). Each environment binds every workload to a runtime, one binding
per workload; there is no env-level runtime, so one env can mix them.

**The runtime is a binding, not a flag.** `forge.OnHost` runs a local
process whose argv is derived from `build` + `args`; `forge.OnCluster
{target}` renders a Workload record that `pkg/deploy.RenderWorkloads`
expands; `forge.OnHosted {}` publishes the spec to a forge control plane,
which admits it under its Restricted profile and renders it with the same
code; `forge.OnCompose` hands it to docker compose; `forge.BuildOnly`
builds and never runs it. A field a runtime cannot honour — `namespacedRBAC` on a
host process, sidecars on the hosted runtime — fails at render, naming the
workload and field, rather than being silently dropped.

Deploying is one verb for every runtime: `forge env deploy <env>` builds,
cuts an immutable release, prints a plan of what changes, and writes nothing
until the plan is approved; promotion moves a release between environments by
digest, and there is no rollback command, because recovery is a roll forward.
The [environments and deploys](https://docs.reliantlabs.io/forge/environments-and-deploys)
guide walks it.

Maturity is not uniform, and the docs should not pretend otherwise:

| Runtime           | State                                                                 |
| ----------------- | --------------------------------------------------------------------- |
| Cluster           | Production-grade; the deeply-developed path                           |
| Hosted            | Real; the platform owns placement, probes are written into every spec |
| Compose           | Real, thinner; `pull` + `up -d --wait`                                |
| Bucket / Firebase | Frontends only (`forge.OnBucket` / `forge.OnFirebase`)                |
| Host              | Excellent dev loop, not a deploy target                               |

### Failures move to author time

KCL schemas validate when they load, and several checks encode a specific
outage. The guard requiring an explicit `platform` on cloud targets exists
because building from an arm64 laptop pushed arm64 images that
exec-format-errored on amd64 nodes — described in the source as "the class
that broke prod."

### Three safety properties

**You cannot deploy the wrong environment to the wrong cluster.** The kubectl
context is read solely from the environment's KCL. No CLI override, no
fallback to your current context.

**Build once, promote by digest.** `forge env build staging --release v1.4.0` captures
content-addressed digests; `forge env deploy prod v1.4.0` pins the same
ones. The bytes that passed staging are the bytes that ship.

**Preflight before the first apply.** On remote clusters Forge verifies every
referenced Secret key and every image against the _live_ target, reports all
failures at once, and refuses to apply. `ImagePullBackOff` becomes a pre-apply
block instead of a mid-rollout drip.

### Migrations in deployed environments

Migrations are embedded in the binary, because the production image contains
the binary and nothing else — a migrator reading `file://db/migrations` could
only ever fail there.

They apply from an **initContainer, not a Job**:

> The ordering guarantee is Kubernetes' own. It holds under
> `kubectl apply -f -`, under Argo CD, under Flux... A Job in a plain apply
> stream is not ordered against the Deployments at all.

Replicas racing the same migration is safe — the migrator
(`forge/pkg/migratekit`) takes a Postgres session advisory lock, so one
applies and the rest find nothing to do. A
failed migration crash-loops the init container, stalling the rollout with the
**old pods still serving**.

`AUTO_MIGRATE` exists for the host loop, where there is no pod and therefore
no init container. Do not turn it on in a cloud environment to "make
migrations work": replicas racing to migrate on startup, each already serving
its readiness probe, is not a migration strategy.

## 7. Honesty as a design property

This runs through the tool and is worth naming, because it is the part that
makes automated use trustworthy.

**A check that could not run is not a pass.** Forge's status model has five
values, and `skip` and `unknown` deliberately render differently:

> StatusSkip and StatusUnknown are DIFFERENT answers and must never render
> the same. A check that could not determine its answer used to come out as a
> gray "–", byte-identical to a check that legitimately does not apply — so
> `App Health  app port 8080 not discovered` read exactly like
> `tool: mkcert  not required for this project`. One of those is a hole in
> the report and the other is a finished answer.

Undetermined checks roll up as warnings and are counted separately: "N
UNDETERMINED (not a pass — forge could not obtain the facts)." The vulnerability
scanner follows the same rule, "refusing to report a pass it did not verify."

**Errors are runbooks.** `cliutil.UserErr` defines the shape —
`<context>: <what failed> (at <file:line>). Fix: <suggestion>.` — and drops
clauses rather than padding them with `at unknown` or `Fix: see docs`.

Beyond the message: a failed `forge generate` rolls back and says so
explicitly when nothing needed reverting; failing sources are preserved under
`.forge/failed-generate/` for inspection; and compiler output is repeated at
the end "so it is the last thing on screen."

**The surface describes itself.** `forge project capabilities`,
`annotations`, `libraries` and `audit` are enumerated from Forge's own
command tree, recognizers and descriptors. They cannot drift from behavior
the way a document can — which is why this page points at them rather than
copying their tables.

**Non-TTY is a first-class mode.** Without a terminal, `forge env up` starts
everything, prints a summary, and returns. It does not hang waiting for an
interaction that will never come. That is what makes Forge drivable by an
agent unattended.
