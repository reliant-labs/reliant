# Manually fire an existing trigger

`fire_trigger({trigger_id})` delegates to the same owner-authorized `TriggerService.FireTrigger` used by Run now in the app. The owner comes from the calling chat, never from model input. The tool cannot create, enable, edit, delete or repoint an activation, or override its workflow, inputs, machine or connections.

Manual semantics are intentionally the existing API's: enabled and overlap policies are bypassed for this one fire, including a paused activation. Configuration is unchanged. Setup validation and service ownership checks still apply. Each call is a new fire, not an idempotent retry: do not call again to poll.

## Acceptance is not completion

1. `list_triggers` identifies the existing activation.
2. `fire_trigger` returns `trigger_id` and `fire_workflow_id` in text and metadata. This acknowledges asynchronous firing only.
3. Call `list_trigger_events({trigger_id})`. Match the returned `fire_workflow_id` **exactly**, not the newest event or its timestamp. Follow `next_page_token` with `page_token` if necessary. An accepted schedule fire may not have recorded an event yet; poll history, not fire again.
4. Read the matching event's outcome (pending, launched, skipped or failed) and detail. If it has `chat_id`, use `get_run({run_id: chat_id})` to inspect the actual run. A launched event is not proof the run finished successfully.

Event summaries expose identifiers, time, outcome/detail and run state, not raw payloads, sender data or credentials. The additive `TriggerEvent.fire_workflow_id` wire projection comes from the schedule event's stored dedupe key, or the event-derived inbound fire ID; ad hoc launches have none. For an inbound event the identifier alone does not imply the fire workflow started: intake can reject an event before launch.

## Permissions and rollout

Firing can invoke an existing workflow with broader privileges than the caller, so it is orchestrator-tier like `start_run`. Unattended runs must additionally name `fire_trigger` explicitly in their step's tools; a wildcard or tag does not grant it. `list_trigger_events` is read-only at the base tier. The user-directed built-in general `agent` explicitly declares orchestrator tier so an ordinary chat can load standing-work tools, including `fire_trigger`. This fixes the assistant's orchestration policy rather than special-casing this tool or promoting the global default. Spawned children are still capped by their parent's permission. The `structured-agent` and custom-workflow defaults remain mutating. Plan mode narrows both preloaded and loadable tools to planning/shell tags, so its wildcard cannot recover firing tools.

The registry/factories and service adapter execute in the worker. The API also embeds the catalog for metadata/validation. Roll out a build of both API and worker. `call_llm` resolves capabilities each turn; `load_tool` persists name grants for the next turn. A newly deployed worker can discover these tools next turn if the node's tool filter and permission permit them; an already-issued turn retains its recorded capability set. The workflow definition itself is loaded once through `ActivityLoadWorkflow` and recorded in Temporal history: an already-running general-agent workflow can retain the old mutating declaration. Start a new top-level general-agent run after rollout to pick up the new orchestrator declaration; do not claim a deploy rewrites in-flight workflow history. No daemon restart is needed for these server-placed tools. Do not restart the daemon or assume an in-flight turn acquires a new catalog.
