# Agent sandbox first-run audit

What stops an AI agent in a typical cloud sandbox (Claude Code web, Codex
cloud: Linux, **no Docker daemon, no TTY**, outbound network allowed, possibly
no Go toolchain) from going

`forge project new` → `forge scaffold` → `forge generate` → `forge lint` →
`go build` → `forge env up dev` → `task test` → `forge env deploy <env>`.

Audited 2026-10-26 against forge `c7c76e0b0` (VERSION v0.1.46), built from the
checkout. Every step was actually run with stdin closed (`</dev/null`) and
`DOCKER_HOST=unix:///nonexistent`. The host had go 1.27, node/npm, buf, kcl,
air and task on PATH, so "needs X" below is read from the code and the logs,
not from a failure on this box. Fixtures: `forge project new app1 --service
tasks --frontend web` (one `// forge:entity message Task`), and a Vite
`react-ts` app adopted with `forge project new --in-place --kind site`.

## Does `env up dev` need Docker?

**For Postgres and the dev IdP: no.** Forge already runs both as supervised
host processes (`internal/hostinfra/hostinfra.go` — embedded-postgres under
`<UserCacheDir>/forge/embedded-postgres`, data in `.forge/hostinfra/postgres`;
`internal/hostinfra/zitadel.go` — downloads the pinned Zitadel release
`v4.19.5` from GitHub releases, checksum-verified). Nothing needs to be built
for an "embedded/host-postgres fallback": it is the default. The k3d cluster is
also skipped when nothing is bound to it (`nothing in env dev runs in a
cluster, so k3d-app1 is not needed`).

**What does need Docker is the observability default.** The scaffolded
`deploy/kcl/dev/main.k` sets `_observability = True`
(`internal/templates/deploy/kcl/dev/main.k.tmpl:147`), which binds
`clickstack`, `otel-profiles` and `alertmanager` to `forge.OnCompose`. Without
a daemon the compose pull fails and the whole `env up` exits 1 even though
every host process it needs could have started.

## What already works well (keep it)

- Every step tested is **non-interactive**: nothing prompted or hung with stdin
  closed. `env up` detaches without a TTY; `env deploy` refuses to treat "no TTY"
  as consent and names `--yes`.
- Postgres and the dev IdP need **no Docker** (host processes, auto-downloaded).
- KCL is embedded (no `kcl` on PATH needed); air is auto-installed with a
  `go run` fallback.
- The frontend-only site path is sandbox-clean end to end (deploy needs only
  `--yes`).

## Reproduce

```bash
cd forge && go build -o /tmp/forge ./cmd/forge
export DOCKER_HOST=unix:///nonexistent
cd /some/scratch && /tmp/forge project new app1 --service tasks --frontend web \
  --link-forge --forge-root <forge checkout> </dev/null
cd app1 && printf '\n// forge:entity\nmessage Task {\n  string title = 2;\n  bool done = 3;\n}\n' \
  >> proto/services/tasks/v1/tasks.proto
/tmp/forge scaffold </dev/null && /tmp/forge lint --quiet </dev/null && go build ./...
/tmp/forge env up dev </dev/null          # fails: compose clickstack pull
sed -i 's/^_observability = True/_observability = False/' deploy/kcl/dev/main.k
/tmp/forge env up dev </dev/null          # works
task test </dev/null                      # fails: pinned forge lacks `project frontends`
/tmp/forge env deploy prod </dev/null     # fails: docker build
/tmp/forge env down dev
```
