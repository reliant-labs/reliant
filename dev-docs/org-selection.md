# Web organization selection (M1c)

The control-plane contract is `control-plane/docs/orgs.md`. The web's active org is a view preference, not the server's default org. `OrganizationService.ListMyOrganizations` supplies membership and the default; `SetDefaultOrganization` changes that separate default. No client infers an org from ordering or a wallet.

`ActiveOrgBinding` binds the persisted choice to the signed-in user, reconciles it against the membership list (including leaving the last org), and resets org-scoped query families when it changes. Chats and projects belong to an org (below, "Projects and chats belong to an org"). `orgInterceptor` fills an empty `org_id` field using the message descriptor, on the shared authenticated Connect chain. It leaves an explicitly named org alone, including `SetDefaultOrganization`. New org-scoped messages therefore participate without another ad-hoc client wrapper. Identity/observability's required org parameters resolve through `orgs.currentOrgId`, which shares the membership-list query.

The switcher menu appears for everyone with an org, one included, in the app sidebar, Apps header, Settings header and app/organization consoles: it names the org the app acts in and holds "Create organization" (`CreateOrganizationDialog`, which switches to the new org). The phone's Account list and the approve pages stay a pure choice, so they appear only with multiple orgs.

## Members and invitations

Settings › Members (`components/Settings/cloud/members/`) is the roster, seat count ("N of M seats", pending invitations included), invite dialog, pending invitations, leave, the per-permission grant editor (`MemberPermissions`, its Permissions tab) and, for admins and owners, the membership history (`ActivityService.ListMembershipActivity`). Every call names its org explicitly (`services/controlPlane/members.ts`); membership administration is gated on the caller's role, and each refusal reason has its own copy there. Contract: control-plane `docs/design/orgs-and-members.md`, phase 1.

An invitation link is `/accept-invite#rinv_<token>`. `lib/inviteLinkBoot` moves the token from the fragment into localStorage at boot, before the router or telemetry can read the URL (the claim link's pattern), so it survives a sign-in round trip and is never sent anywhere but `GetInvitation`/`AcceptInvitation` request bodies. `/accept-invite` is root-level and unguarded; after `AcceptInvitation` it makes the joined org the active org (`switchToJoinedOrg`). CLI/device approval has an independent choice: the requested org if it is a membership, otherwise the default. It does not change the web's active org. Approval stays unavailable when membership cannot be loaded; Deny remains available.

There are no current direct web calls to ClusterService or BrowserIngestService; any added call carrying `org_id` goes through the same interceptor. User-keyed billing operations and the plan catalogue deliberately carry no org field (M1a exemptions). Environment-bound secret-store calls already authorize their resource, not an implicit default org.

Existing required-org identity, observability, dashboards, activity, alerting, RUM, delivery and LLM calls now receive the selected org through the shared resolver or the billing hooks, not the wallet's organization. Their API wrappers keep passing their explicit `orgId`/scope.

The following Reliant `ForgeService` requests also carry `org_id`: `GetTopology`, `VerifyEnv`, `ListSecrets`, `GetEnvStatus`, `GetEnvShape`, `PlanPromote`, `ApplyPromote`, `PlanDeploy`, `StartDeployPlan`, `StartDeploy`. The API forwards it over NATS; only the daemon reads the filesystem and runs forge. That one child's `RELIANT_FORGE_ORG` selects the helper mint's org, without changing the daemon's process-global current org. Detached deploy jobs retain the org. `GetDeployStatus` only polls the already-started job and has no org selection.

The helper passes it in `TokenService.ExchangeToken.org_id`, then `AccessTokenInternalService.MintForUser.org_id`. The control plane verifies membership and clips scopes in the target org. The caller's scope ceiling, acting user, resource binding and expiry remain intact. Omitted org stays in the session credential's own org; a changed default cannot move it. The helper cache is keyed by endpoint, session and org. See control-plane PR #1413 (stacked on #1365).

Plain HTTP approval call sites also send `org_id`: `Auth/CliLogin.tsx` → `/oauth/approve`; `Auth/DevicePairing.tsx` and `Machines/PairMachinePanel.tsx` → `services/controlPlane/pairing.ts` → `/oauth/device/approve`.

## Projects and chats belong to an org

Every project and chat has one organization, fixed at creation (control-plane `docs/design/orgs-and-members.md` §3 and §5): `projects.org_id`, `chats.org_id`, nullable. The api-server asks control-plane (`AccessTokenInternalService.ResolveOrgMembership`, through `internal/orgs`, cached for `orgs.CacheTTL`) and keeps no copy of membership.

- **Create.** `CreateProject`, `CreateProjectFromRepo` and `StartChat` take an optional `org_id`, which the interceptor fills with the active org. A named org must be a live membership (PERMISSION_DENIED, reason `not_org_member`), a machine credential may name only its own org (`org_mismatch`), and an unverifiable named org is UNAVAILABLE. Unnamed is the caller's default org; if that cannot be resolved the row is created with no org rather than failing. A new chat takes its project's org when the project has one (naming another is FAILED_PRECONDITION), a branch takes its source chat's, and `MoveChatToProject` refuses a project of another org.
- **List.** `ListProjects`, `ListChats`, `ListArchivedChats` and `SearchChats` take an optional `org_id` and then list only that org's rows (`orgs.ListScope`); the caller's default org also lists the rows with no org yet. Unset lists everything the caller owns, as old clients expect. `ListInbox` takes one too: it keeps the items about that org's chats, automations and projects (judged by the first of them whose org was read: the chat's, else the trigger's, else the project's; every item's deciding chat or project is read before the scope applies, and an item whose org cannot be read is left out of every named org, the default included), the default org also keeps those about something with no org yet (a legacy chat, a recovery whose project is gone), and a machine's storage and worktree items, which belong to no org, list in every org. Naming an org the caller is not a live member of is PERMISSION_DENIED on every one.
- **Backfill.** Lazy: the first org-scoped list of a user's default org stamps their rows that have no org with it (a chat takes its project's org when it has one), at most once per `orgs.BackfillInterval` per api-server. No migration reads control-plane, and a row is never moved between orgs.
- **Workflows, triggers and runs** (owner decision, 2026-11-10). `workflow_drafts.org_id` (a saved workflow), `triggers.org_id` and `workflows.org_id` (a run) are the same nullable column. A saved workflow takes the request's org (`CreateWorkflowDraft`, `SaveWorkflow`; an import or an update keeps the existing org). A trigger takes its project's org, else the request's, and `UpdateTrigger` refuses a project of another org. Every chat a trigger launches belongs to the trigger's org (`launch.Spec.OrgID`), so a scheduled run bills it. A run inherits its chat's org on insert (the `workflows_inherit_chat_org` database trigger, which also covers older writers). An agent's `start_run` passes its chat's org, so it cannot start a run in another org's project. `ListTriggers`, `ListRuns` and `ListWorkflows` (saved workflows only) filter by `org_id` like the lists above, and the backfill stamps all three.
- **Access needs live membership.** `internal/authz` decides a resource that has an org (chat, project, saved workflow, trigger) for its owner only while they are a live member of that org, so a removed member loses the org's rows even though they created them. The membership is control-plane's (`internal/orgs`, cached `orgs.CacheTTL` = 30s, which bounds how long a removal can lag). Every process puts it on its contexts once: the API and daemon listeners for each request (`grpc.withMembership`), the worker for each activity (`worker.Options.BackgroundActivityContext`). A failed check denies (fail closed), and so does an org resource decided on a context that carries no membership, logged at ERROR. There is no invalidation event yet; control-plane would publish one on a membership change. A process's background (loops and consumers outside listeners and activities) decides against the membership installed at boot (`authz.SetProcessMembership`).
- **A trigger whose creator left its org pauses itself.** Every run a trigger launches executes as its creator, so once they are no longer a live member of the trigger's org (or of its project's org, for a trigger written before orgs) no firing can launch. The first firing that finds out (the fire's own check, `authz.WriteTriggerDenial`, or the launcher's project check, `launch.OwnerLeftOrg`) is recorded as failed. That firing also pauses the trigger: `enabled = false`, `triggers.paused_reason = 'creator_left_org'`, a `pause` row in its change history, and its Temporal schedule paused (`triggers.AutoPause`). Later firings launch nothing. A firing that was already in flight records a skip, so a burst of firings records one failure. `Trigger.paused_reason` returns the reason. A membership outage is not an answer: `authz.ErrMembershipUnavailable` fails that firing closed and retryably, and never pauses. The trigger resumes the normal way (`SetTriggerEnabled`), which re-checks membership, so it works once the creator rejoins. Enabling, or a person pausing, clears the reason.
- **An org policy refusal is a verdict, not a fault** (control-plane `docs/design/org-policies.md` §5.1). The managed Reliant driver reads a gateway 403 whose `x-forge-error-reason` (or `error.code`) is `model_not_allowed`, `member_spend_cap_reached`, `org_spend_cap_reached` or `provider_not_allowed` as an `orgpolicy.Refusal`. That refusal is never retried, never marks a credential, never benches an account and never fails over. The chat shows the reason through the `RELIANT_ORG_POLICY_REFUSED` marker. A run a person is behind **pauses**. Switching the chat's model, Resume, or the org's policy changing resumes it: the worker's `orgpolicy.Watcher` re-reads the policy of every org a refusal was met in and sends the org's blocked chats a capacity wake when its version changes. An **unattended** run ends with the reason (`OrgPolicyRefusedUnattended`), and its trigger is paused once with `triggers.paused_reason = 'org_policy'` until its owner resumes it.
- **A machine credential acts in exactly one org**, as in control-plane. An access token bound to org A is refused org B's chats, projects, saved workflows and triggers, and a row with no org yet unless A is the caller's default (`authz.WithCredentialOrg`, installed by `auth.WithMachineToken`). The refusal is `PermissionDenied` with reason `org_mismatch` and says how to act in the other org: `reliant auth login` (or `forge login --org <org>`). Release note: a CLI token minted for one org can no longer act on another org's chats or projects; sign in for that org.
- **No control plane** (self-hosted, `AUTH_MODE=apikey`): there are no orgs. Nothing is stamped, `org_id` on requests is ignored, and lists are owner-only, as before.

### In the web

- **A switch.** The product app passes `ActiveOrgBinding` an `onSwitch`, `components/Orgs/followActiveOrg.ts`: it resets the chat list, the archived chats, chat search, the Inbox and every `projectService`, `workflowService`, `triggerService` and `runService` read, so the sidebar, Projects, the Inbox and the Workflows views show the new org's at once; marks chat details stale (the open pane is not blanked); and `projectStore.followActiveOrg` moves the sidebar filter and the context project off another org's project, to the new org's most recent (the old one's workspace state is kept for switching back). The forge shell passes none. Every list and create above carries the org through the interceptor (`api/__tests__/orgInterceptor.test.ts` pins them).
- **The user stream** still carries every org the person is in. Each `UserUpdateData` names the org the stream decided it by (`org_id`: the stored org, else its chat's, project's or saved workflow's). `store/orgUpdateFilter.ts` drops another org's update before it reaches a cache, a list refetch or an OS notification, falling back to the `Chat.org_id` / `Project.org_id` the app holds for an update from an older server. The open chat's updates and those about no org (daemon signals) always pass; the resume cursor moves past every one.
- **Machines.** The registry's list (`DaemonRegistryService.ListDaemons`) does not know a machine's org; control-plane's `Daemon.org_id` does. `hooks/useMachineOrgs.ts` reads `DaemonService.ListDaemons` naming no org (`acrossAllOrgs`, an explicit opt-out of the interceptor, so a machine of another org is known rather than merely absent) and joins it by machine id. With several orgs, the machine pickers (new chat, a folder's or project's machine, an automation's "Runs on"), the sidebar's machine filter, Settings › Machines and the phone's machine list offer the active org's machines, each labelled with its org; a machine whose org is unknown is never hidden, and one recorded before machines had an org is the default org's. A person with one org sees no label, no filter and no extra request.
