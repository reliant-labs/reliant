# Automation attention: implementation contract (owner-approved architecture)

This is the bounded first implementation, additive within public v1. Verified background is in automation-attention-brief.md. Lifecycle, semantic outcome, trigger diagnostic health and `RunEventFailed` remain unchanged. No control-plane workflow is enabled by this PR.

## YAML / wire interface

```yaml
attention:
  key: "repo:{{ inputs.repo }}:pr:{{ inputs.pr }}"
  on_start: recovering
  recovery_timeout: 30m
  on_success: resolved
  on_failure: action_required
```

`Workflow.attention` is new field 25 (producer review retained field 23 for existing permissions), message `WorkflowAttention`: `string key=1`, `string on_start=2`, `string recovery_timeout=3`, `string on_success=4`, `string on_failure=5`. Strings deliberately retain room for additive state vocabulary; validation rejects unsupported values. Absent attention preserves existing behavior. `key` is a nonempty template evaluated ONCE over finalized inputs, before graph execution, and must produce a nonempty string <=512 bytes. No workflow/PR-name inference. `on_start` is absent, `recovering` or `action_required`; `on_success` is absent, `resolved` or `action_required`; `on_failure` is absent or `action_required` (absence defaults to action_required). `recovering` requires recovery_timeout, parsed Go duration in [1s,24h]; other on_start values reject recovery_timeout. A successful execution means completed and outcome != failure. Cancellation/crash/failure outcome escalates; it NEVER resolves an incident. No automatic resolution just because a run succeeded. Observation workflow may declare only key: failure opens attention, unrelated/same-key success does not resolve it. Recovery workflow explicitly opts into recovering on start and resolved on success.

Only root unattended launch runs apply this policy; interactive turns and nested workflows do not mutate incidents. Invalid dynamic key fails the run visibly with durable existing failure diagnostics, retaining legacy notification/inbox fail-safe for that run. Key/schema validation happens for YAML and direct protobuf definitions. New policy must survive YAML marshal/unmarshal and workflow resolution. No new node type in v1 of this feature.

## Durable state and fencing

Identity is `(user_id, project_id, incident_key)`. User is the existing tenancy boundary; all writes derive identity from stored chat and project ownership, NEVER YAML/request-supplied user/project. Cross-project/user correlation is impossible. The incident stores current state, unique episode ID, opened_at, updated_at, current actor run ID and immutable started_at, lease deadline, last chat/trigger, and failure class/detail. Actor run ID is Temporal execution RunID (not reusable workflow ID); order is `(Temporal workflow start time, RunID)` lexicographic. Store never uses activity receipt/completion time as actor ordering. A separate durable actor ledger makes start/finish idempotent and terminal-before-start safe; replays cannot extend a lease, reopen resolved state, or regress an actor's terminal phase. Keep resolved tombstones and ledger records.

Start registers every configured actor even if on_start is empty, and establishes the high-water actor fence. An older actor's later completion cannot change newer state. A no-transition start/success does not itself open/reopen/resolve an incident. A transition from resolved/no incident to recovering/action_required creates a NEW episode ID; transitions while open retain episode ID. Resolution closes only that episode. A fresh failure after resolution creates a new dismissal episode. Dismissal is existing inbox item dismissal keyed `automation-failing:incident:<episode-id>`; never key-only, trigger-wide or chat-wide.

Recovering leases are fixed from immutable run start + timeout, cannot renew on retry, and have an absolute 24h bound. SDK v1.50.0 obtains WorkflowStartTime from the current execution's started event (`internal_task_handlers.go`), so ordinary successor executions order chronologically. Checkpoint/history-compaction continue-as-new nevertheless preserves the original validated policy, evaluated key, actor RunID and StartedAt in an internal `WorkflowInput.AttentionHandoff`: compaction must not renew a recovery lease indefinitely or re-evaluate a mutated input. Duplicate start registration keeps the original lease; late human-wake successors drop the launch marker and attention handoff entirely. Dead owner protection does NOT depend on runtime completion/reconciler: every attention read treats `recovering && lease_until <= now` as `action_required`. That projection is the durable deadline's semantics; no extra scheduler is needed. Store also materializes expiry before mutations. An expired owner may NOT later resolve/suppress the incident, even when it eventually reports success; only a newly started actor may claim it. Crash, unsuccessful work, cancellation, or recovery finishing without an explicit successful resolution => action_required immediately. Expiry preserves episode/dismissal identity. A configured repair trigger's existence never suppresses anything; only an actual registered recovery run does.

## Repository interface shared by implementation units

Core owned types in `internal/db/core/attention.go`:

- `AttentionUpdate { ChatID, RunID string; StartedAt time.Time; Phase string; Key, State string; RecoveryTimeout time.Duration; FailureClass, Detail string }` where Phase is `start` or `finish`; State is empty/recovering/action_required/resolved.
- `AttentionResult { Managed bool; Notify bool }`: Managed means a validated policy actor controls this run's attention, allowing its legacy streak/unread suppression; Notify is first action_required transition of this episode (best effort notification; inbox is durable backstop).
- `AttentionIncident { UserID, ProjectID, Key, EpisodeID, State, ChatID, TriggerID, FailureClass, Detail string; OpenedAt, UpdatedAt time.Time; LeaseUntil *time.Time }`.
- Repo `ApplyAttentionUpdate(ctx, core.AttentionUpdate) (core.AttentionResult,error)` derives scope from ChatID, validates ownership, actor ordering and phase; no supplied tenancy.
- Repo `ListAttentionIncidents(ctx,userID string) ([]*core.AttentionIncident,error)` returns open incidents, with read-time expiry escalation and user/project ownership checked.
- Repo `AttentionManagedChats(ctx,userID string,chatIDs []string) (map[string]bool,error)` returns configured launch chats with a DURABLE backstop: actor.finished OR (actor.start_seen AND immutable start_state IN('recovering','action_required') AND an open incident exists for the same user/project/key). Merely registering an observer is NOT enough: if its terminal attention activity permanently fails, the failed launch must remain visible through legacy projection. A stale recovering start fenced by a resolved tombstone is likewise not managed without an open incident. Exclude managed firings BEFORE the legacy last-success cutoff, via `FiringsSinceLastUnmanagedSuccess` (never suppress source/setup/broken/launch errors). Diagnostic health stays unfiltered. Legacy unmanaged failures in a mixed trigger still surface.

Inbox additive wire fields on `InboxAutomationFailing`: `incident_key=3`, `attention_state=4`, `failure_class=5`, `detail=6`. Existing health remains diagnostic, not actionability. FailureClass is `unsuccessful` for completed outcome failure; `execution_error` for crashes; `recovery_expired` for dead owner. UI says “Job unsuccessful” versus “Execution failed” when known, and “Recovery timed out” for expiry; existing unknown payloads keep their current copy.

## Permanent persistence failure backstop

Every configured status uses one outer SERIALIZABLE transaction containing lifecycle tracking, semantic outcome, opt-in launch run_status receipt, failure workflow-event and attention update. Existing nested RunTx calls join this outer transaction (Repo.RunTx); the incident row lock serializes actors. A missing receipt OR attention transition rolls the entire transaction back. This includes successful orchestration with on_success action_required: it cannot falsely commit a success without the promised incident. Unconfigured statuses retain their previous transaction behavior. If terminal notification retries are exhausted, an armed attention run returns a genuine runtime bookkeeping error to Temporal (the job verdict was not rewritten). The existing reconciler observes FAILED Temporal execution and repairs an active DB row to Failed, cascades it and emits RunEventFailed; evidence: `internal/workflow/reconciliation/reconciler_test.go::TestReconciler_RunningWorkflow_TemporalFailed_Repaired`, `reconciler.go::swapStatus`. Recovery still has its independent fixed lease/read-time expiry backstop even when its owner vanishes.

Control-plane must first pin a Reliant version containing the completed consumer implementation, then add `attention` to observing/recovering workflows using exactly the same key within the same owner/project. Observer uses key only (failure opens; success does not resolve); recovery uses bounded on_start recovering and explicit on_success resolved. A workflow that exhausts repair successfully as orchestration must use on_success action_required instead, not resolved. This initial contract declares terminal policy per workflow, not conditional per-node attention; split recovery/resolution workflows if one graph has multiple incompatible successful terminal meanings. Failure outcomes still emit failed events. This PR does not change active control-plane YAML, release pins or slot_lost classification.
