## 3. Why the existing reclamation did not catch it

Three mechanisms touch this disk. Each missed a specific slice.

### 3a. Reliant's worktree sweep missed 591 locked, finished worktrees (103.3 GiB)

The sweep is server-side `internal/worktreesweep` plus daemon-side
`internal/worktreereclaim`. These 591 worktrees carry reliant's own
`reliant: worktree <id>` lock, so each has a DB row. All were clean and
merged. Most were more than 24h past their last commit. The sweep had them,
yet removed none, because:

1. **Removal only handles ARCHIVED rows.** An active row reaches removal only
   through auto-archive: `Sweeper.archiveFinished` (`worktreesweep/sweep.go:887`),
   which the daemon reaches after it answers `OutcomeIdleDone`. That needs
   all of the following:
   - `RELIANT_WORKTREE_AUTO_ARCHIVE=on`. The default is `dry-run`
     (`ParseAutoArchiveMode`). Prod sets `on`
     (`control-plane/deploy/kcl/prod/config.k:542`), so this is probably
     satisfied, but verify it for this user's server.
   - The daemon's `finished` probe passes (`worktreereclaim/reclaim.go:1082`):
     idle ≥ `DefaultActiveIdleFloor` = **24h**, clean, merged or pushed, not in use.
   - **No non-archived chat has `WorktreeID == wt.ID`** (`sweep.go:896-899`).
     Agent chats and sub-agent threads are almost never archived, so a
     worktree bound to any chat is **never** auto-archived, however finished
     it is. This is the most likely reason most of the 591 sat there.
   - **`len(chats) < liveChatScan` (1000)** (`sweep.go:893`). If the project
     has ≥ 1000 non-archived chats, `archiveFinished` returns at once for
     **every** worktree in the project, and auto-archive is effectively off.
     The reliant-labs project runs hundreds of agents a day. **Verify this
     first**: count non-archived chats for project reliant-labs, and grep the
     server log for `[WorktreeSweep] auto-archive … finished=… archived=…`.
     If `archived` is always 0, this is the cause.
2. **Active locked rows are re-asked once a day.** `due()` (`sweep.go:358-359`)
   returns `LockedAt older than lockRecheck (24h)` for active rows, **before**
   the disk-guard `guardSince` check at line 364. Disk pressure therefore
   speeds up only *archived* held rows, and never the active rows that held
   the space.
3. **Shedding never runs on active rows.** `shed` (`worktreereclaim/strip.go`)
   deletes node_modules and other regenerable paths only for ARCHIVED rows
   held for dirty, unpushed or similar reasons (`shedsFor`). An active row,
   however idle, keeps its node_modules. Stripping the 209 kept worktrees by
   hand freed 29.3 GiB, 26.8 of it under `~/.reliant/worktrees`.
4. **No observability.** The daemon logs only
   `daemon command handled command_type=worktree.reconcile outcome=ok`
   (291 of them between 17Z and 23Z). It does not log the per-worktree outcome
   (locked, idle_done, held/reason, probe_inconclusive). Neither the disk
   banner nor diskwatch's consumers report "N worktrees, X GiB, Y finished
   but unarchived". Nobody could see that the sweep was doing nothing.

### 3b. Nothing owned 188 unlocked worktrees (≈ 40 GiB), including 144 under reliant's root

These worktrees had no reliant lock: 144 in `~/.reliant/worktrees/<name>`
(flat, 30.2G), 18 under `~/.reliant/worktrees/reliant-labs/…`, plus
`~/.reliant/releases` and scattered `~/` dirs. Agents created them with raw
`git worktree add`, not through the worktree tool.

- **Reliant** never sees them. The sweep iterates DB rows only
  (`ListWorktreesForReclaim`), and a worktree without its lock is
  `ReasonUnmanaged` to `worktreereclaim` anyway.
- **forge storage** defers to reliant for everything under reliant's root.
  `forge/internal/storage/worktrees.go:407-409` returns `HoldManaged`
  ("Reliant reclaims its own worktrees") for any worktree under the managed
  root, whether or not it carries reliant's lock. The opt-out,
  `worktree_reap_reliant_managed`, is unset in
  `/var/cache/workspace/forge-storage.json`.
- **forge's worktree reap never runs automatically anyway.** The daemon runs
  `forge storage auto-gc`, which "never removes worktrees"
  (`reliant/internal/diskwatch/reaper.go` header). Only an explicit
  `forge storage gc --apply` reaps them, and the last full gc ran on
  **2026-10-22** (`last-full-gc.json`), 8 days earlier.

So the gap is that forge defers to reliant for the root, and reliant only
knows about rows it created.

### 3c. The Go cache steward is working as designed, and its design cannot hold the budget at this load

- Budget is 40 GiB, and the floor is a flat 2h (`goCacheFloor`,
  `forge/internal/storage/gocache.go:67`). At 50–58 GiB/h, 100–120G is
  always inside the floor. The steward says so in `over_budget`
  ("no trim can reach it … ~50 GiB/h").
- **Its remediation hint is wrong here.** It suggests checking `-trimpath`
  and a toolchain switch. `GOFLAGS=-trimpath` is set in
  `/opt/reliant/go/go.env`, and all three repos pin `toolchain go1.27.3`,
  which matches the installed `go1.27.3`. No switch happens. The volume is
  real: about 1,100 worktrees on different commits each produce distinct
  action IDs, plus `go run forge@<ver>` builds and tool binaries.
- The warning lives only in `last-auto-gc.json` and the audit log. The disk
  guard's reclaimer is the same forge reaper pass
  (`diskwatch.Watcher.Reclaim`), so under pressure it re-runs a pass that
  cannot reach the young bytes. Its message says "build caches and docker".
- `gocache_livebuild.go` already knows "the start of any running Go build".
  The floor could be `min(2h, now - oldest running build start)` instead of a
  flat 2h. With no build older than 20m running, entries older than 20m are
  provably unused.

### 3d. Smaller misses

- `/tmp/go-build*`: `trimGoWorkDirs` (`diskwatch/cachetrim.go:742`) removes
  only dirs whose children are all older than `GoWorkDirAge`. About 17G sat
  there at 23:20Z after the user had already deleted the ones older than 3h.
  This is minor and working as designed.
- The docker build cache GC cap (`defaultMaxUsedSpace` 110.7 GB) is about
  18% of this disk. It never bounds the cache in practice, so the 21.9G with
  0 active records stays until docker crosses that cap.
- The Go module cache was at 22G against a 20G budget, with
  `young_bytes: 0` and `removed: 0`. The module trim reports `shards 0/0` and
  never ran a pass that removes anything.

## 4. Concrete product changes

Ordered by bytes recovered per unit of work.

1. **Auto-archive: replace the chat veto and the 1000-chat bailout**
   (`reliant/internal/worktreesweep/sweep.go` `archiveFinished`).
   - Replace `ListChats(… Limit: 1000)` plus the in-memory scan with a
     targeted store query: `EXISTS (chat WHERE worktree_id = $1 AND NOT archived AND last_activity > now() - ActiveIdleFloor)`.
     That removes the ≥1000 bailout entirely.
   - Treat a chat idle past the floor, with no running or paused run, as
     *not using* the worktree. Archiving the worktree must not archive the
     chat. Unarchive already re-locks and restores.
   - Test: a worktree bound to a chat idle 25h, with the project holding
     1,200 chats, is archived. The same worktree with a chat active 1h ago
     is not.
2. **Shed regenerable paths from ACTIVE idle rows**
   (`worktreereclaim/strip.go`). When the daemon answers `OutcomeLocked` or
   `OutcomeIdleDone` for a row idle ≥ 6h (or ≥ 1h while the disk guard is
   RECLAIMING), not in use, and not "Keep everything", run `shed` (node_modules,
   `.next`, `dist`, build output). This is reversible: the next install
   regenerates it. Manually it freed 26.8 GiB on this machine.
3. **Disk guard must accelerate active rows too.** In `Sweeper.due`
   (`sweep.go:349`), apply the `guardSince` override before the
   `wt.DeletedAt == nil` early return, and pass a shorter
   `ActiveIdleFloor` (e.g. 2h) in requests while the machine's guard is
   RECLAIMING. Today pressure changes nothing for the 591 rows that held
   103 GiB.
4. **Close the unlocked-worktree gap under reliant's root**
   (`forge/internal/storage/worktrees.go` ≈ line 407). Return `HoldManaged`
   only when the worktree carries a `reliant: worktree ` lock
   (`lockReasonPrefix`, `reliant/internal/worktreereclaim/types.go:221`).
   Unlocked worktrees under the root then fall through to forge's normal
   rules (clean, pushed or merged, idle ≥ 24h, not in use).
5. **Run forge's worktree reap from the daemon under pressure.** Add a
   second disk-guard `Reclaimer` that runs forge's worktree pass (the part of
   `forge storage gc --apply` that reaps worktrees, with forge's own holds)
   at most hourly while RECLAIMING. With (4) this covers the 188 unlocked
   worktrees (≈ 40 GiB) that nothing owned.
6. **Stop agents from creating unmanaged worktrees.** The shell tool already
   inspects commands (it refused a `/proc` scan here). Have it detect
   `git worktree add` targeting `~/.reliant/worktrees` and point to the
   worktree tool, or have the daemon adopt such worktrees into a row so (1)–(3)
   apply. 144 flat worktrees there had no row.
7. **Go cache: make the floor track live builds and fix the hint**
   (`forge/internal/storage/gocache.go`, `gocache_livebuild.go`).
   - Floor = `max(15m, now - start of the oldest running go build)`, capped
     at 2h, instead of a flat 2h. At 50 GiB/h, a 30m effective floor holds
     ~25G young instead of ~100G.
   - Show the `-trimpath` hint only when `go env GOFLAGS` in the worktree
     lacks it. Here it was set, and the hint sent readers the wrong way.
   - Put `over_budget` on the heartbeat as a first-class disk-banner line
     with the fill rate, not only in `last-auto-gc.json`.
8. **Observability for the sweep.** Log one line per reconcile batch with
   counts by outcome and held reason, and add a diskwatch consumer "agent
   worktrees: N, X GiB, M finished-but-active". The server's
   `[WorktreeSweep] auto-archive finished=… archived=…` should be a metric,
   with an alert when finished > 0 and archived == 0 across 24h of passes
   (a sign of the 1000-chat bailout or dry-run).
9. **Docker build cache bound.** Seed `builder.gc.defaultMaxUsedSpace` as a
   fraction of the disk (e.g. min(20 GB, 5%)) rather than 110.7 GB, matching
   `build_cache_gib: 20` in forge's policy, which docker never sees.
